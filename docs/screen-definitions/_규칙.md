# 화면 정의서 작성 규칙 (v6 · 기획 관점)

> 이 규칙은 `docs/screen-definitions/SCR-*.md` 에 자동 적용됩니다.
> 단일 출처: `_lint.py` · 자동 검사: `.claude/settings.json` PostToolUse 훅(`_lint_hook.py`).

## 1. 무엇을 쓰는가
"이 화면이 **무엇을 제공하는가**(기획 의도)"와 **화면 설계**를 업무 용어로 작성한다.
버튼이 무엇을 하고 어디로 가는지, 어떤 메시지·상태가 나오는지를 기술한다. **구현 방식은 개발이 정한다.**

## 2. 필수 구조 (7섹션 · 순서 고정)
1. 화면 정보 → 2. 권한 정보 → 3. 진입 / 이탈 경로 및 사용자 시나리오 → 4. 화면 구성별 정리 → 5. 유효성 검사 → 6. 정책 → 7. 미결사항

> **권한 연계**: §2 권한 정보에는 역할별 권한표를 작성하지 않는다. 메뉴 접근·보기·수정은 시스템 관리의 메뉴 관리(SCR-ADMIN-005)·권한 관리(SCR-ADMIN-006)에서 설정한다고만 적는다. 화면 정의서에는 권한 미결사항을 만들지 않고, 업무 단계의 수행 주체는 §3~§6에 업무 흐름으로 기술한다.

## 3. 금지 — 코드 수준 내용
기획 문서에는 다음을 쓰지 않는다(자동 검사가 차단):
- 함수·메서드명(`PG.x`, `EDOC.x`, `renderBody()` 등), 내부 전역/데이터 구조명(`DY_DOCS`, `CHECKLIST_PRESETS`, `APPR` 등)
- DOM 요소 ID(`#policy-target`), CSS 클래스(`sl-...`, `chip-mini`), `data-*` 속성
- 스토리지 API/키(`localStorage`, `dy-edoc-v1`)
- 코드 연산자·수식·메서드 체이닝(`===`, `||`, `.indexOf(`, `% 9000`, `× 137`)
- 소스 파일:라인 참조(`menu.js L12`), 보안/코드품질 분석(`XSS`, `데드코드`, `stale`, `try-catch`)
- 데이터셋 실측 건수 나열은 지양 — 수치보다 기획 의도/규칙을 적는다.

> URL 경로(`docs-preset.html`, `menu.html?m=policy`), PDCA·세트·처리유형 같은 **업무 개념**은 허용된다.

## 4. 판단은 §6에서 끝내고, 외부 입력만 §7에 둔다
- 법령·업무 논리·다른 화면과의 정합으로 정할 수 있는 항목은 **§6 정책에서 결론과 이유까지 확정**한다.
- §7에는 담양군이 제공해야 하는 명단·기관정보·실데이터와 타 기관의 연계 규격·신청 절차만 남길 수 있다. 외부 입력이 늦어도 개발이 막히지 않도록 미수신 상태의 표시와 대체 동작을 §6에 함께 정한다.
- 미결사항이 있으면 §7 표 컬럼을 `ID | 외부 입력 | 미수신 시 동작 | 제공 주체 | 목표 시점`으로 작성한다. 없으면 `없음.`을 명시한다.
- 구현 시점이 뒤인 기능, 프로토타입의 목업, 테스트 데이터 부족은 기획 미결이 아니다. 정해진 계약과 현재 한계를 각각 §4·§6에 적는다.

## 5. 전 화면 공통 기능 계약

아래 규칙은 개별 정의서가 다른 값을 명시한 경우를 제외하고 모든 화면에 적용한다.

- **조회·필터** — 검색어 앞뒤 공백을 제거하고 화면에 명시된 대상 필드의 부분 일치로 찾는다. 영문은 대소문자를 구분하지 않는다. 여러 필터는 모두 충족하는 조건으로 결합한다. 검색 실행과 조건 변경 시 첫 페이지로 이동하며, 초기화는 검색어·필터·페이지를 함께 기본값으로 돌린다. 결과 0건과 자료 미등록은 다른 문구로 표시한다.
- **쪽 나눔·정렬** — 기본 20건, 선택값 20·50·100건이다. 같은 정렬값은 고유 식별값 순으로 고정해 페이지 이동 중 행이 흔들리지 않게 한다. 상세에서 목록으로 돌아오면 검색·필터·정렬·페이지를 복원한다.
- **비동기 상태** — 최초 조회, 불러오는 중, 정상·0건, 오류, 마지막 성공 자료 표시의 다섯 상태를 구분한다. 실패 시 원인 요약과 [다시 시도]를 제공하고, 마지막 성공 자료가 있으면 조회 시각과 함께 낡은 자료임을 표시한다. 숫자 0을 미등록·조회 실패로 대신하지 않는다.
- **입력 검증** — 필수값은 공백 제거 뒤 판정하며 묵시적 기본값으로 누락을 감추지 않는다. 필드 아래 오류와 상단 요약을 함께 내고 첫 오류로 초점을 옮긴다. 화면 검증과 서버 검증은 같은 규칙을 사용하며, 여러 건 등록도 개별 등록과 같은 규칙을 적용한다.
- **첨부** — 일반 업무 증빙은 `hwp·hwpx·pdf·doc·docx·xls·xlsx·ppt·pptx·jpg·jpeg·png`, 파일당 20MB 이하, 제출 단위당 최대 10개다. 이미지 전용 화면은 `jpg·jpeg·png·gif`, 파일당 10MB 이하, 최대 5개다. 일괄등록은 `xlsx` 1개, 20MB 이하로 제한한다. 업로드 전에 파일명과 거절 사유를 보여 준다. 새 파일은 이전 파일을 덮지 않고 버전으로 남긴다.
- **식별값·버전** — 내부 식별값은 생성 뒤 바꾸거나 재사용하지 않는다. 화면 표시번호는 업무 접두어·연도·연속번호로 중복 없이 발급하고 취소 건도 번호를 반환하지 않는다. 사용 이력이 있는 기준정보·양식은 삭제하지 않고 사용중지하며, 확정 문서의 개정은 이전 버전을 보존한 새 버전으로 만든다.
- **기한·지연** — 미완료 건만 `기한 초과 / 오늘 / 1~7일 / 8~30일 / 31일 이후 / 기한 없음`으로 서로 겹치지 않게 분류한다. 완료 건은 기한이 지났어도 지연으로 세지 않는다. 내부 알림은 D-7, D-1, D+1에 보내고 이후 완료될 때까지 7일마다 반복한다.
- **알림** — 1차 채널은 시스템 내부 알림이다. 발생 업무·대상 식별값·수신자·발생시각·연결 화면·사용자별 읽음 상태를 저장한다. 문자·메일은 별도 연계가 들어오기 전까지 보내지 않으며 화면이 성공으로 가장하지 않는다.
- **외부 연계** — 온나라·FMS·행정포털·법제처 연계는 시스템별 연결 모듈을 거친다(인사·조직도는 행정포털 축이다). **파일 실물(파일관리)과 알림 외부 채널(문자발송체계)도 원천이 밖에 있지만 상태 모니터(SCR-ADMIN-004)의 대상이 아니다** — 연계 상태를 세는 문장에는 위 네 곳만 쓰고, 이 두 축은 그 값을 쓰는 화면이 미수신 동작을 각자 밝힌다. 개수를 세는 자리에서 여섯으로 말하면 화면·정의서가 어긋난다. 같은 요청을 다시 보내도 중복 반영되지 않아야 하고 요청·응답·처리자·시각·결과를 남긴다. 실패는 자동으로 다시 보내지 않고 담당자가 최대 3회까지 직접 재시도하며, 그 뒤에는 재시도 수단을 거두고 담당자 재처리 대상으로 전환한다 — 규격 오류·인증 만료·상대 시스템 점검처럼 몇 번을 보내도 같은 결과인 실패가 대부분이라, 자동 재시도는 이력을 같은 실패로 채워 진짜 원인을 덮는다. 연계가 없으면 파일 내려받기·수기 반영 같은 화면별 대체 동작을 사용하며 성공 상태로 바꾸지 않는다.

## 6. 검사 방법
- 로컬: `python3 docs/screen-definitions/_lint.py [파일...]`
- 자동(작성 즉시): Write/Edit 시 훅이 검사 → 위반하면 수정 피드백.
- 빌드: `python3 docs/screen-definitions/_build-data.py` 가 재생성 시 위반 요약을 함께 출력.

## 7. 새 규칙 추가/완화
규칙은 `_lint.py` 의 `REQUIRED_SECTIONS` / `FORBIDDEN` 한 곳에서 관리한다. 수정하면 훅·빌드·로컬 검사에 모두 반영된다.
