# 화면 정의서 — 알림 발송 시뮬레이션

## 1. 화면 정보

| 항목 | 내용 |

| 화면 유형 | 팝업(짧은 안내) |

업무 처리 중 **누군가에게 알림이 나갔다는 사실**을 그 자리에서 보여 주는 공통 수단이다. 담당자 배정·독촉·기한 임박처럼 사람에게 전달돼야 처리가 이어지는 업무가 많아, 발송 시점을 화면에서 확인시키지 않으면 "보냈는지 안 보냈는지" 를 알 수 없다. 화면 요소는 짧은 안내 한 줄과 알림 기록 적재 두 가지이며, 쌓인 기록은 전역 알림 드롭다운(SCR-COM-004)에서 조회한다.

## 2. 권한 정보

- 메뉴 접근·보기·수정은 시스템 관리의 메뉴 관리(SCR-ADMIN-005)와 권한 관리(SCR-ADMIN-006)에서 설정한다.
- 이 화면 정의서에서는 역할별 권한과 열람 범위를 별도로 정하지 않는다.
- 발송을 유발하는 행위(배정·독촉·확정 등)의 권한이 곧 이 안내를 볼 권한이며, 이 수단이 따로 권한을 갖지 않는다.

## 3. 진입 / 이탈 경로 및 사용자 시나리오

| 구분 | 연결 화면 | 조건 / 트리거 |
|---|---|---|
| 진입 | 각 업무 화면 | 담당자 배정·독촉·상태 변경 등 사람에게 알려야 하는 처리를 마쳤을 때 |
| 이탈 | 전역 알림 드롭다운 | 쌓인 알림을 나중에 다시 볼 때(SCR-COM-004) |

| 단계 | 사용자 행동 | 화면 반응 |
|:--:|---|---|
| 1 | 알림이 필요한 처리를 실행한다 | 처리 결과와 함께 발송 사실을 알린다 |
| 2 | 안내를 확인한다 | 별도 조작 없이 잠시 뒤 사라진다 |
| 3 | 나중에 다시 확인한다 | 전역 알림 목록에서 시각·채널·내용을 조회한다 |

### 분기 로직

- **채널이 문구를 가른다** — 어느 경로로 보냈는지(문자·시스템 알림 등)를 안내에 함께 적는다. 채널을 밝히지 않으면 받는 사람이 어디를 봐야 하는지 알 수 없다. 채널을 지정하지 않으면 기본 채널로 처리한다.
- **발송과 기록이 한 동작이다** — 안내만 띄우고 기록을 남기지 않으면 나중에 "보냈다"를 증명할 수 없다. 두 가지를 나누지 않는다.
- **알림 목록은 최근 것만 유지한다** — 오래된 것부터 밀려난다. 상한을 두는 이유는 이 목록이 조회 보조 수단이지 이력 대장이 아니기 때문이다 — 남겨야 하는 이력은 각 업무의 처리 이력에 별도로 쌓인다.

### 예외·경계 시나리오

| 상황 | 화면 반응 |
|---|---|
| 프로토타입에서 실행 | **실제로 문자·메일을 보내지 않는다**는 사실을 밝힌다 — 숨기면 보냈다고 믿고 기다리게 된다 |
| 같은 처리를 반복 실행 | 실행할 때마다 기록이 쌓인다 — 중복을 합치지 않는다. 몇 번 보냈는지가 재촉 이력의 핵심이다 |
| 알림 목록이 상한을 넘김 | 오래된 것부터 밀려나며, 밀려난 것을 되살리지 않는다 |
| 수신자가 시스템에 없는 사람 | 이 수단이 판단하지 않는다 — 수신자 확정은 그 업무 화면의 책임이다 |

## 4. 화면 구성별 정리

### 4-1. 발송 안내

- 구성: 채널 이름과 보낸 내용을 한 줄로 보여 주는 짧은 안내.

| 트리거 | 동작 결과 | 이동 / 메시지 |
|---|---|---|
| 알림 발송 실행 | 채널과 내용을 함께 알린다 | "(채널) 알림 발송 — (내용)" |
| 채널을 지정하지 않음 | 기본 채널로 표시한다 | — |

- 상태: **표시 / 사라짐** 둘이며 사용자가 닫지 않아도 잠시 뒤 사라진다. 조작을 요구하지 않는 것이 의도다 — 확인을 눌러야 사라지면 처리 흐름이 끊긴다.

### 4-2. 알림 기록 적재

- 구성: 발송 시각·채널·내용을 알림 목록의 맨 위에 쌓는다.

| 트리거 | 동작 결과 | 이동 / 메시지 |
|---|---|---|
| 알림 발송 실행 | 목록 최상단에 추가한다 | 전역 알림 드롭다운에서 조회(SCR-COM-004) |
| 목록이 상한에 도달 | 가장 오래된 것을 밀어낸다 | — |

- 상태: **비어 있음 / 쌓임** 둘이다. 조회 전용이라 이 수단으로 지우거나 고칠 수 없다.

## 5. 유효성 검사

해당 없음 — 사용자 입력이 없는 시스템 동작이다. 무엇을 누구에게 보낼지의 검증은 발송을 유발한 업무 화면이 담당한다(예: SCR-EDU-005 독촉, SCR-RISK-001 재촉).

## 6. 정책

- **알림은 자동으로 나가지 않는다** — 사람이 처리를 실행한 결과로만 나간다. 시스템이 스스로 보내면 받는 쪽은 누가 왜 보냈는지 알 수 없고, 잦아지면 결국 무시된다.
- **발송 사실을 반드시 화면에서 확인시킨다** — 조용히 보내면 보낸 사람도 보냈는지 모른다.
- **보내지 않았으면서 보냈다고 하지 않는다** — 프로토타입은 실제 발송을 하지 않으며 그 사실을 밝힌다.
- **외부 채널(SMS·메일·Push)은 본개발 연계 구현 범위다** — 정본 스펙은 알림 관리(SCR-ADMIN-002 §4 「외부 발송 관리」)다. 이 화면은 발송 시뮬레이션이고, 연계 전 실발송 채널은 **시스템 내부 알림뿐**이며 외부 발송 성공을 가장하지 않는다.
- **이 목록은 이력 대장이 아니다** — 상한을 두고 오래된 것을 밀어낸다. 남겨야 하는 기록은 각 업무의 처리 이력에 따로 쌓이며, 그쪽은 지우지 않는다.
- **법령 근거를 붙이지 않는다** — 알림 전달은 업무를 잇는 수단이지 법령이 명한 의무의 직접 이행 수단이 아니다. 근거 없음도 정보이며 규칙은 공통 근거 연계(SCR-COM-008)를 따른다.

---

## 7. 미결사항

없음. 발송 시점·채널 표기·기록 적재와 상한·외부 채널의 소속(정본 스펙은 SCR-ADMIN-002)·프로토타입 표기는 모두 §6에서 확정했다.

실제 발송 연계는 미결이 아니라 **본개발 구현 범위**이며, 내부 알림으로 시작한다는 방향은 §6에 정해져 있다.
