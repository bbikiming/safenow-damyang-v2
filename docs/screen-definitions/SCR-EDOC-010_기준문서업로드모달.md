# 화면 정의서 — 기준문서 업로드 모달

> 화면 ID: SCR-EDOC-010 · 화면 유형: 팝업 · 기획 관점(v6) · 구현 정합 2026-08-11
> 판단이 필요했던 항목은 §6 정책에서 확정했습니다.

## 1. 화면 정보

| 항목 | 내용 |
|---|---|
| 화면 ID | SCR-EDOC-010 |
| 화면명 | 기준문서 업로드 모달 |
| URL 경로 | 문서 열기 공통 동작 — 처리유형이 첨부파일일 때 |
| 상위 메뉴 | 전자문서(공통) > 기준문서 업로드 모달 |
| 화면 유형 | 팝업 |

처리유형이 **첨부파일**인 업무문서에 실제 파일을 올리는 팝업이다. 안전보건 업무 문서의 상당수는 시스템 안에서 작성하는 것이 아니라 이미 만들어진 한글·PDF 파일을 보관하는 형태여서, 그 문서들의 유일한 입력 지점이 여기다. 화면은 문서 정보 머리와 업로드 영역 두 덩어리이며, 업무 목록(SCR-DOC-002)·기준문서함(SCR-DOC-001)에서 문서를 열 때 처리유형에 따라 이 팝업이 뜬다.

## 2. 권한 정보

- 메뉴 접근·보기·수정은 시스템 관리의 메뉴 관리(SCR-ADMIN-005)와 권한 관리(SCR-ADMIN-006)에서 설정한다.
- 이 화면 정의서에서는 역할별 권한과 열람 범위를 별도로 정하지 않는다.
- 이 팝업을 여는 권한은 그 문서를 여는 화면의 권한을 따르며, 업로드 수행 주체는 §3~§6의 업무 흐름을 따른다.

## 3. 진입 / 이탈 경로 및 사용자 시나리오

| 구분 | 연결 화면 | 조건 / 트리거 |
|---|---|---|
| 진입 | 업무 목록·기준문서함·문서 상세 | 문서를 열었고 그 문서의 처리유형이 **첨부파일**일 때 |
| 이탈 | 호출한 화면 | 업로드 또는 취소 후 되돌아간다 |
| 이탈(분기) | 전자문서 폼 | 처리유형이 전자문서면 이 팝업 대신 폼이 열린다(SCR-EDOC-001~007) |
| 이탈(분기) | 연결 화면 | 처리유형이 프로그램이면 팝업 없이 그 화면으로 이동한다 |

| 단계 | 사용자 행동 | 화면 반응 |
|:--:|---|---|
| 1 | 문서를 연다 | 처리유형을 보고 이 팝업을 띄울지 결정한다 |
| 2 | 문서명·법적 근거·버전을 확인한다 | 무엇에 올리는 파일인지 먼저 보여준다 |
| 3 | 파일을 고르거나 끌어다 놓는다 | 지원 형식·용량·개수 안내를 함께 낸다 |
| 4 | [업로드] | 파일을 붙이고 버전 이력을 남긴다 |

### 분기 로직

- **처리유형이 이 팝업의 존재 자체를 가른다** — 문서를 여는 동작은 하나지만 결과가 셋이다. **첨부파일**이면 이 팝업, **전자문서**면 입력 폼, **프로그램**이면 팝업 없이 그 화면으로 이동한다. 사용자는 같은 자리를 누르지만 업무 성격에 맞는 곳으로 간다.
- **문서 정보는 보여 주기만 한다** — 문서명·법적 근거·버전은 이 팝업에서 고치지 않는다. 문서 자체를 바꾸려면 업무 등록·수정(SCR-DOC-007)에서 한다.
- **업로드는 덮어쓰기가 아니라 버전 추가다** — 새로 올려도 이전 파일이 사라지지 않고 버전 이력이 쌓인다.

### 예외·경계 시나리오

| 상황 | 화면 반응 |
|---|---|
| 존재하지 않는 문서를 열려 함 | 팝업을 열지 않는다 |
| 파일을 고르지 않고 업로드 | 업로드하지 않는다 — 빈 버전을 만들지 않는다 |
| 지원하지 않는 형식·용량 초과 | 고르는 단계에서 걸러지며 그 기준을 안내에 상시 표시한다 |
| 여러 파일을 한 번에 올림 | 허용한다 — 한 문서에 여러 증빙이 붙는 경우가 실제로 있다 |
| 이미 파일이 있는 문서에 다시 올림 | 이전 파일을 지우지 않고 버전을 더한다 |
| 프로토타입에서 업로드 | 실제 파일이 서버로 가지 않는다는 사실을 결과 안내에 밝힌다 |

## 4. 화면 구성별 정리

### 4-1. 문서 정보 머리

- 구성: 처리유형 배지 · 법적 근거 배지 · 버전 배지 · 문서명.

| 트리거 | 동작 결과 | 이동 / 메시지 |
|---|---|---|
| 팝업 열림 | 어느 문서에 올리는지 먼저 보여준다 | 파일을 고르기 전에 대상을 확인시킨다 |
| 법적 근거가 없는 문서 | 근거 배지를 그리지 않는다 | 억지로 조문을 붙이지 않는다 |

- 상태: 조회 전용이며 비는 경우가 없다 — 문서가 있어야 팝업이 열리기 때문이다. 근거 배지만 있고 없음이 갈린다.

### 4-2. 업로드 영역

- 구성: 클릭·끌어놓기로 파일을 고르는 영역 + 지원 형식·용량·개수 안내 + 다중 첨부와 버전 이력 자동 기록 안내.

| 트리거 | 동작 결과 | 이동 / 메시지 |
|---|---|---|
| 영역 클릭 또는 파일 끌어놓기 | 파일 선택을 연다 | 키보드로도 같은 동작을 할 수 있다 |
| 형식·용량 기준을 벗어난 파일 | 고르는 단계에서 걸러진다 | 기준은 안내에 상시 표시된다 |
| [업로드] | 파일을 붙이고 버전 이력을 남긴다 | "업로드되었습니다" |
| [취소] | 올리지 않고 닫는다 | — |

- 상태: **파일 미선택 / 선택됨 / 업로드됨** 세 단계다. 업로드 진행 표시와 실패 처리는 실서비스에서 이 시스템 공통 규칙을 따른다.

## 6. 정책

- **첨부파일 문서의 유일한 입력 지점이다** — 이 유형의 문서는 시스템 안에서 내용을 만들지 않는다. 그래서 이 팝업이 하는 일은 파일을 받는 것 하나이며, 문서 자체의 속성은 여기서 고치지 않는다.
- **덮어쓰지 않고 버전을 쌓는다** — 이전 파일을 지우면 "그때 무엇을 근거로 판단했는가"를 잃는다. 새 파일은 항상 새 버전이다.
- **업로드 기준은 시스템 공통 기준을 쓴다** — 지원 형식·용량·개수를 화면마다 따로 적지 않는다.
- **없는 동작을 약속하지 않는다** — 프로토타입은 실제 파일을 서버로 보내지 않으며, 고르고 검증하고 기록하는 데까지만 동작한다는 사실을 밝힌다.
- **법령 근거는 문서가 갖고 이 팝업이 갖지 않는다** — 문서마다 근거가 다르고 이 팝업은 그릇이다. 근거 배지는 문서에 붙은 값을 표시할 뿐이며 규칙은 공통 근거 연계(SCR-COM-008)를 따른다.

## 7. 미결사항

없음. 처리유형별 분기·문서 정보의 편집 가능 여부·버전 처리 방식·업로드 기준의 출처·프로토타입 표기는 모두 §6에서 확정했다.

실제 파일 보관 방식과 업로드 진행·실패 표시는 미결이 아니라 **본개발 구현 범위**이며, 이 시스템 공통 규칙을 따른다.
