# 화면 정의서 — 경영방침

> 화면 ID: SCR-SBM-001 · 화면 유형: 목록 · 등록(제정/개정/최초) · 상세 · 기획 관점(v6)
> 판단이 필요했던 항목은 §6 정책에서 확정했습니다.
> 본 정의서는 프로토타입 v2의 **현재 구현 상태**(버전 목록형 경영방침 관리 + 현행본 기준 이행점검)를 기준으로 작성되었다. v7.1에서 유효성 검사(§5)·예외·경계 시나리오(§3)·데이터 정합성(§6)을 기획 관점에서 보강했다. 판단이 필요했던 항목은 모두 §6 정책에서 확정했다.

**목적·설명** — 담양군의 안전·보건 목표와 경영방침을 **버전 단위(제정/개정/최초)** 로 등록·관리하고, 각 버전을 온나라 결재에 상신하여 확정하며, 확정된 **현행본**에 대해 반기 1회 이행점검과 게시·주지(게시 전/후 증빙)를 수행하는 안전보건관리체계 최상위 업무 화면이다.

화면은 공통 셸(페이지 타이틀 + 요약 바) 위에 얹히며, 그 아래 **3개 서브탭**(경영방침 / 이행 점검 / 게시 현황)으로 골격을 이룬다. 각 서브탭은 **목록(list)** 을 기본으로 하고, 행을 클릭하면 **공유 상세(detail)** 로 진입한다(세 탭이 동일 상세를 공유). 경영방침 탭에서는 추가로 **등록 화면(form)** 으로 전환된다.

핵심 설계 원칙 두 가지:
1. **현행본 = 결재 승인완료된 확정 문서** — 버전 숫자가 아니라 *결재가 승인완료된 문서 중 시행일이 가장 최근인 버전*을 현행본으로 본다. 이행점검 작성·게시·증빙 등록은 **현행본에서만** 가능하다.
2. **버전의 상태는 셋이다 — 현행 / 결재 대기 / 이력** — 현행이 아닌 것을 모두 '이력'이라 부르면 **방금 만들어 아직 상신하지 않은 방침이 과거 것으로 읽혀** 담당자가 상신해야 한다는 사실을 놓친다. 판정은 **결재 상태**로 한다(승인을 받은 적 없으면 결재 대기, 승인받았지만 현행이 아니면 이력). 시행일로 재면 승인완료된 옛 버전까지 대기로 잡힌다. 현행이 아닌 버전은 어느 쪽이든 점검·게시·증빙의 신규 작성/수정/삭제가 불가하며 읽기만 가능하되, **막는 이유를 상태에 맞게 달리 안내한다** — 결재 대기는 “먼저 상신하세요”, 이력은 “지나간 버전입니다”.

반기 이행점검에서 부적합(X) 판정된 항목은 개선조치(SCR-IMP 계열)로 자동 연계된다.

현재 프로토타입의 데이터는 `window.POLICY_STATE`(인메모리 SSOT)에 보관되어 **SPA 세션 동안 유지**되며(버전 추가·게시·증빙·점검 결과 반영), 전체 새로고침 시 초기 시드로 리셋된다. 단, 이행점검표 인스턴스는 e-Doc 엔진에 별도 보관된다(세션 종료 후에도 유지). 실제 영구 저장·발송·온나라 연계 규칙은 §6에서 확정했다.

연관 화면: 이행관리(SCR-CMP 계열, 점검 상태 표시·역진입), 개선조치(SCR-IMP 계열, 부적합 항목 유입), 업무 목록(docs-preset.html?menu=policy).

## 4. 화면 구성별 정리

### 4-1. 공통 셸 — 페이지 타이틀 / 법령 근거 (경영방침 고유 아님)

- 구성: 페이지 타이틀("경영방침") + 서브타이틀("안전보건관리체계 > 경영방침 · SFR-005 · 관련 업무문서 N건") + **법령 근거 칩**. 전 메뉴가 공유하는 셸이며 이 화면 고유 영역이 아니다.
- **법령 근거는 셸이 자동으로 붙인다** — 화면 모듈이 자체 근거 UI 를 그리지 않는다. 근거가 없는 화면은 칩이 뜨지 않으며, 그것도 정보다.

| 트리거 | 동작 결과 | 이동 / 메시지 |
|---|---|---|
| 화면 진입 | 제목·부제·법령 근거 칩을 낸다 | 별도 로딩 표시 없이 즉시 낸다 |
| 근거 칩 ⓘ | 조문 원문을 그 자리에서 펼친다 | 모달을 새로 띄우지 않는다 |

- 상태: 이 셸에는 이행률·시기도래 같은 **집계 지표를 두지 않는다** — 경영방침은 버전 단위 문서라 '이행률'이라는 축이 성립하지 않고, 이행 여부는 게시 현황(4-9)과 이행 점검(4-6)이 각자의 축으로 낸다. 부제의 건수는 이 업무에 딸린 업무문서 수다.

### 4-2. 서브탭 바 (경영방침 / 이행 점검 / 게시 현황)
- 구성: 3개 서브탭 버튼(`.psub-tabs`). 현재 활성 탭이 강조된다. 클릭 시 해당 목록으로 전환되며, 상세 화면은 세 탭이 공유한다(상세에서 [‹ 목록]을 누르면 직전 활성 탭의 목록으로 복귀).

| 트리거 | 동작 결과 |
|---|---|
| [경영방침] | 버전 목록(4-3) 표시 |
| [이행 점검] | 이행점검 목록(4-6) 표시 |
| [게시 현황] | 게시 현황 목록(4-9) 표시 |

- 상태: 라우팅은 인메모리 SSOT(`POLICY_STATE.tab/view/ver`)로 관리된다. 서브탭 전환 시 view는 목록(list)으로 초기화된다.

### 4-3. 경영방침 목록 (서브탭: 경영방침)
- 구성: 카드 제목 "경영방침 (N건)" + [+ 등록] 버튼. 표 컬럼 — 버전(`vX.X` + 제정/개정/최초 칩) · **상태(현행/결재 대기/이력)** · 방침명 · 반기 점검 · 온나라 결재 상태.
- **어느 것이 지금 방침인지가 이 목록의 첫 정보다** — 점검·게시가 전부 현행본 기준이므로 상태를 다른 탭에 가서 알게 하면 안 된다. 종전에는 결재 상태(승인완료)만 있어 세 버전이 똑같아 보였다.
- 등록된 방침이 하나도 없으면 빈 안내 + [최초 등록] 버튼만 표시된다.
- 시드 데이터: v2.0(제정·승인완료·현행), v1.1(개정·승인완료), v1.0(최초·승인완료).

| 트리거 | 동작 결과 | 이동 / 메시지 |
|---|---|---|
| 행 클릭 | 상세(4-5)로 진입 | — |
| [+ 등록] | 등록 구분 선택 팝업(4-4) | 버전이 없으면 곧바로 '최초'(v1.0) 등록 화면으로 |

- 상태: 목록의 빈 상태는 **버전 0건**이며, 이때는 표 대신 최초 등록 안내만 낸다. 행 단위 상태는 세 축이 겹친다 — **버전 구분**(최초/개정/제정) · **반기 점검**(미점검 / 점검 완료) · **결재**(미상신 / 결재중 / 승인완료 / 반려). 여기에 **현행본 표시**가 얹히며, 현행은 승인완료 중 시행일이 도래한 최신 1건이라 항상 0건 또는 1건이다. 시행일이 아직 오지 않은 승인본은 시행 예정으로 구분한다.

### 4-4. 경영방침 등록 (구분 선택 팝업 → 등록 화면)
- **구분 선택 팝업**: 현재 최신본 기준으로 [개정](+0.1)/[제정](+1.0)을 선택. 각 버튼에 다음 버전 번호와 성격(개정=소폭 보완·갱신, 제정=전면 재수립)이 표기된다. 버전 번호 규칙 — 최초=1.0, 개정=직전 +0.1, 제정=정수부 +1.0.
- **등록 화면(form)**: 상단 취소 바("경영방침 {구분} 등록 · v{번호}") + 입력 그리드.
  - 목표(슬로건, 텍스트, 필수 — 미입력 시 "목표를 입력하세요" 토스트로 저장 차단)

  - 점검자(읽기전용 표시 + [조직도] 버튼 → 조직도 트리 오버레이)
- 방침 제호는 "담양군 안전·보건 경영방침"으로 고정. 시행일은 등록일로 채워지고 결재 상태는 '미상신'으로 시작.

|---|---|---|
| 팝업 [개정]/[제정] | 구분·버전 확정 후 등록 화면으로 | — |
| [+ 세부 방침 추가] | 세부 방침 입력 줄 1개 추가 + 포커스 | — |

### 4-9. 게시 현황 — 부서 전수 점검 (서브탭: 게시 현황)

- **기준 단위가 버전이 아니라 부서다** — 종전에는 버전별 게시 건수(1~2건)를 셌는데, 실제 의무는 **전 부서·사업장이 각자 게시**하는 것이라 그 수를 세는 것이 의미가 없었다. 그래서 부서 축 전수 표로 바꿨고, 의무 이행점검과 **같은 표**를 쓴다 — 경영방침 원본은 계획에서, 게시 여부는 부서별 점검에서 확인한다는 결론이라 축이 같다.
- 구성: 부서 명단 갭 안내 + 요약 지표(전체·게시·미게시·해당없음·게시율) + 부서별 표(부서·사업장 / 게시 여부 / 게시 위치 / 확인일 / 게시 사진 / 관리).
- **게시로 등록하려면 게시 위치와 게시 사진이 있어야 한다** — 위치도 증빙도 없이 "게시했다"고 적을 수 있으면 전수 점검이 성립하지 않는다.
- **‘해당없음’은 사유 없이 저장할 수 없다** — 종이 서식에서 실제로 나타난 실패 모드가 미게시가 아니라 **해당 없음으로 적고 빠져나가는 것**이었다. 사유가 없는 기존 데이터는 그 행에 **“사유 미기재 — 확인 필요”**로 계속 드러낸다.
- **게시 확인의 회차 축은 방침 버전이다** — 연도로 묶으면 방침을 개정해도 옛 방침 게시 기록이 그대로 '게시함'으로 남아, 새 방침을 아직 붙이지 않은 부서가 완료로 보인다. **현행본이 바뀌면 게시 현황은 전 부서 미게시에서 다시 시작한다** — 방침이 바뀌면 다시 붙여야 하기 때문이다. 이전 버전의 게시 기록은 지워지지 않고 그 버전에 남는다.
- **부서 명단 갭을 감추지 않는다** — 확인된 대상은 과·사업소 39개인데 등록된 것은 11개뿐이라, 표 위에 그 사실과 나머지가 표에 나타나지 않는다는 것을 밝힌다. 명단을 받으면 조직도 한 곳만 늘리면 두 화면이 함께 따라온다.
- **상세 화면에는 게시 카드를 두지 않는다** — 같은 화면에서 "게시율 0%"와 "게시완료 2건"이 동시에 보이면 어느 쪽이 사실인지 알 수 없다. 상세에는 이 탭으로 가는 안내와 이동 수단만 둔다.

| 트리거 | 동작 결과 | 이동 / 메시지 |
|---|---|---|
| 서브탭 [게시 현황] | 부서별 전수 표로 바꾼다 | 버전 목록이 아니라 부서 목록이다 |
| 부서 행 [확인 등록] | 게시 여부·위치·확인일·게시 사진을 받는 입력을 연다 | **자기 부서와 주관부서만** 나타난다 |
| 게시 여부 ‘게시’ 선택 후 저장 | 위치와 사진이 있어야 저장된다 | 없으면 무엇이 비었는지 알린다 |
| ‘해당없음’ 선택 후 저장 | 사유가 없으면 저장을 막는다 | 사유 입력을 요구한다 |
| 게시 사진 [×] | 그 증빙을 지운다 | **조작 권한이 있는 행에만** 나타난다 |
| 부서 행 [독촉] | 미게시 부서에 확인을 요청한다 | 발신자는 누른 사람으로 남는다 |
| 상세의 [게시 현황 탭 열기] | 이 탭으로 이동한다 | 상세에서 직접 등록하지 않는다 |

- 상태: 부서 한 곳의 상태는 **미게시 / 게시 / 해당없음** 셋이며, 해당없음은 **사유 있음 / 사유 미기재**로 다시 갈려 뒤쪽은 행에 경고로 드러난다. 조작 권한 축은 **조작 가능**(자기 부서 담당자·주관부서 담당자)과 **조회 전용**(관리·감독 계층, 그 밖의 부서)이고, 조회 전용일 때는 **조작 수단을 내지 않고 왜 없는지 표 위에 상시 밝힌다** — 버튼을 눌렀을 때만 알리면 버튼이 없으므로 그 안내에 도달할 길이 없다.

### 4-10. 문서 미리보기 전체화면 팝업
- 구성: 상세 PDF 패널의 [전체화면]으로 열리는 **전체화면 오버레이**(화면 대부분을 채우는 큰 크기). 헤더("경영방침 vX 문서 미리보기" + [PDF 다운로드] + ×닫기) + 본문(문서 용지를 크게 렌더 — 760px·14px). 배경 클릭 또는 ×로 닫기.
- 재개편 전 작은 패널 미리보기를 대체하여 문서를 크게 확인할 수 있도록 변경되었다.

| 트리거 | 동작 결과 | 이동 / 메시지 |
|---|---|---|
| [PDF 다운로드] | 안내만 표시 | "PDF 다운로드 (프로토타입)" |
| ×/배경 클릭 | 팝업 닫기 | — |

- 상태: **열림 / 닫힘** 둘이며 조회 전용이다. 문서 내용은 그 버전의 저장값에서 그대로 그리므로 빈 화면이 되는 경우가 없다. 담양군 고유값(처리과 기호·주소·관인 등)이 아직 없는 자리는 **미등록**으로 표시하고 비워 두지 않는다 — 빈칸은 값이 없는 것인지 안 넣은 것인지 구분되지 않는다. 인쇄에서 빼야 할 편집 크롬은 지면에 나타나지 않는다.

### 4-11. 이행 점검표 읽기 뷰어 (점검표 보기 모달)
- 구성: [점검표 보기]로 열리는 **읽기 전용** 점검표(넓은 모달). 상단 메타(점검일·점검자·종합 결과 칩) + 요약(적합·부적합·텍스트 건수) + 영역별 섹션. 각 항목은 질문 + 관련 근거 태그(**호버 시 법령 상세 툴팁**) + 결과(O·적합 / X·부적합 칩 또는 텍스트 서술). 부적합이 있으면 "부적합 N건은 개선조치(IMP)로 자동 등록되었습니다" 안내. 푸터 [닫기]/[인쇄]/[PDF 다운로드].
- 종합 결과(적합/부적합/보완 필요)에 따라 표시되는 O/X 분포가 달라진다(데모 산출).

| 트리거 | 동작 결과 | 이동 / 메시지 |
|---|---|---|
| 관련 근거 태그 호버/포커스 | 법령 상세 툴팁 표시(법령·조·항·제목·조문) | — |
| [인쇄] / [PDF 다운로드] | 안내만 표시 | "인쇄/PDF 다운로드 (프로토타입)" |

- 상태: **점검 이력이 있는 버전에서만** 열린다. 종합 결과 축은 **적합 / 부적합 / 보완 필요** 셋이고 항목 단위로는 **적합 / 부적합 / 텍스트 서술 / 해당없음**이 있다. 부적합이 1건이라도 있으면 종합은 자동으로 부적합이 되며 점검자가 임의로 바꿀 수 없다. 부적합 건수와 자동 등록된 개선조치 건수는 같아야 하고, 그 사실을 안내로 함께 낸다. 읽기 전용이라 이 모달에서 값을 고칠 수 없다.

### 5-5. 공통 검증 요약

- **빈 값 자동 대체 금지** — 게시 위치·게시일은 비어 있으면 저장을 차단하고 해당 필드를 표시한다. 증빙 파일명은 선택한 파일의 원래 이름을 사용하며 임의 기본값으로 대체하지 않는다. 마스터 항목명도 빈 값이면 저장하지 않는다.
- **삭제 확인 절차** — 게시 카드·증빙·세부 방침 줄 삭제에 확인 단계가 없다. 되돌릴 수 없는 삭제에는 확인 단계를 두고, 연결된 점검 항목이 있으면 그 건수를 함께 밝힌다(§6 확정).
- **선행조건 검증** — 미상신·미점검 상태에서도 상신·확정·게시가 가능하다. 상신은 본문이 채워진 뒤, 게시·공표는 결재 승인완료 뒤, 점검 확정은 전 항목 판정 뒤로 각각 선행조건을 둔다(§6 확정).

## 6. 정책 (업무 규칙 · 데이터 정합성)

### 법령 근거의 성격 (2026-08-12 검증)

- **이 화면의 직접 근거는 중대재해처벌법 시행령 제4조제1호 하나다** — *"사업 또는 사업장의 안전·보건에 관한 목표와 경영방침을 **설정할 것**"*. 조문이 요구하는 것은 **설정**이다.
- **게시를 명시한 조문은 없다.** 게시는 설정한 방침이 실제로 구성원에게 닿았는지 확인하는 **이행 수단**이지 별도의 법정 의무가 아니다. 화면도 그렇게 밝힌다 — 근거가 없는 것을 있는 것처럼 보이게 하지 않는다.
- **종전에 게시 현황에 붙어 있던 「산업안전보건법」 제14조는 잘못된 근거였다(제거).** 그 조문은 *「상법」 제170조에 따른 **주식회사** 중 대통령령으로 정하는 회사의 **대표이사**가 안전보건계획을 이사회에 보고·승인받는 의무*이며, **지방자치단체인 담양군에는 적용되지 않는다**. 조문 번호만 보고 붙이면 이런 일이 생긴다.
- **같은 법의 제34조(법령 요지 등의 게시)도 근거가 아니다** — 그 조문이 게시하라고 정한 것은 *법령의 요지와 **안전보건관리규정***이고, 경영방침은 그 대상이 아니다.
- **반기 이행 점검은 경영방침 자체의 의무가 아니다** — 시행령 제4조에서 *반기 1회 이상 점검*을 요구하는 것은 제3호(유해·위험요인)·제5호(책임자 평가)·제7호(종사자 의견청취)·제8호(대응 매뉴얼)·제9호(도급 기준)이며 **제1호에는 그 문구가 없다**. 이 화면의 점검표는 방침에 담긴 목표(KPI)가 실제로 달성되고 있는지를 **경영책임자 관점에서 묶어 보는 관리 수단**이고, 각 항목은 그 항목의 근거 조문을 따로 단다(점검표의 항목별 근거 표시). 방침 자체를 반기마다 점검할 법정 의무가 있다고 쓰지 않는다.

- **작성·상신·게시는 되돌리기 어려운 순서를 이룬다** — 방침은 결재를 거쳐 공표되는 문서라, 상신 이후에는 내용을 고치는 것이 아니라 새 버전을 만들어 다시 결재를 받는다. 게시·공표는 대외로 나가는 행위이므로 결재 승인완료를 선행 조건으로 삼는다. **결재 주체는 결재선이 정하고, 결재선은 코드에 고정하지 않는다(SBM-01 확정)** — 최종 결재권자와 그 앞단은 **지자체 위임전결규칙** 소관이라 조직 개편·규칙 개정으로 바뀐다. 기본값만 조직도에서 직위로 파생하고 변경은 조직도 선택기로 받는다. **결재선은 기안 → 검토 → 결재 3단계이고 기안·검토·결재가 서로 다른 계정이어야 한다**(2026-08-27 확정) — 상신은 결재선 전체를 한 번에 온나라로 넘기므로 한 계정이 두 단계에 들어가면 결재선이 성립하지 않는다. 규칙과 판정은 공통 권한 정의 §7 이 정본이고, 상신 앞에 **결재선 지정 단계**를 둔다. **결재 결과는 회신으로 받는다**(2026-08-28 확정 · 공통 §7-4) — 승인완료라야 현행본이 되고 이행점검·게시가 열리므로, 회신이 없으면 새 방침이 결재중에 갇혀 현행본이 되지 못한다.
  - **자체 결재가 아니다** — 온나라가 보낸 결과를 옮겨 적는 자리이며 화면에 「연계 전 수동 기록」임을 밝힌다. 연계가 붙으면 온나라 응답이 대신한다.
  - **승인 단계·처리자는 그 버전의 결재선에서 파생**한다. 고정된 이름·단계를 쓰지 않는다.
  - 회신 등록은 결재가 아니므로 **결재선과 무관하게 담당자가** 한다. **반려는 사유 없이 등록되지 않는다.**
  - **결재 상태를 임의로 세팅하는 수단을 두지 않는다** — 상태는 상신과 회신 등록 두 경로로만 바뀐다. **게시·공표는 결재 승인완료를 선행 조건**으로 삼는다(SBM-06 확정) — 승인 전에 게시하면 결재 절차가 사후 추인이 된다. 상신은 **본문(목표·세부방침)이 채워진 상태**에서만 가능하며, 이행점검은 상신의 선행 조건이 아니다 — 점검은 방침을 정한 뒤에 하는 일이다.
- **현행본 판정 기준(단일성)** — 현행본은 `결재 승인완료` 버전 중 **시행일 최신본**으로 산출한다(버전 숫자 아님). 시스템 관점에서 현행본은 항상 0건 또는 1건이어야 한다. 결재 승인된 버전이 둘 이상이면 시행일이 가장 최근인 것을 현행으로 보며, **현행 전환은 시행일 도래 시점**이다(SBM-04 확정) — 승인 즉시로 하면 아직 시행되지 않은 방침이 현행으로 게시된다. 시행일이 오기 전까지는 이전 본이 현행이고 새 본은 "시행 예정"으로 표시한다. **시행일이 같은 승인본이 둘 이상이면 나중에 승인된 것을 현행**으로 보고, 그런 상태가 생기면 목록에 경고를 띄운다 — 정상적인 상황이 아니라 담당자가 확인해야 할 신호다.
- **버전 번호 정합성** — 최초=1.0, 개정=+0.1, 제정=정수부 +1.0의 자동 채번이다. 버전 번호는 중복되지 않아야 하며(자동 채번이라 충돌 가능성은 낮으나), **자동 채번을 유지한다**(SBM-11 확정) — 수동 지정이나 연도 기반으로 바꾸지 않는다. 수동 지정은 중복과 건너뜀을 만들고, 연도 기반은 한 해에 두 번 개정하면 곧바로 무너진다. 자동 채번은 중복이 구조적으로 생기지 않고, 개정(+0.1)과 제정(+1.0)의 차이가 번호만 보고도 읽힌다.
- **편집 잠금 경계** — 현행본만 이행점검 작성·게시 추가/삭제·증빙 추가/삭제가 가능하고, 이전 버전은 점검표·게시·증빙을 읽기만 한다(목록 액션·상세 버튼·직접 호출 모두 동일 가드). **이전 버전은 본문도 고칠 수 없다**(SBM-05 확정) — 결재를 거쳐 공표된 문서라 고치는 순간 "그때 무엇을 공표했는가"를 잃는다. 잠금 대상은 본문·점검·게시·증빙 **전부**이며, 고쳐야 하면 개정으로 새 버전을 만든다. 오탈자 하나도 예외로 두지 않는다 — 예외를 두면 어디까지가 오탈자인지 다투게 된다.
- **점검 결과 ↔ 개선조치 일관성** — 이행점검 확정 시 X(부적합) 항목마다 개선조치가 자동 생성된다. 점검표의 X 건수와 자동 생성 개선조치 건수가 일치해야 하며, **기한은 점검 확정일부터 30일, 담당자는 그 부서의 책임자**를 기본으로 지목하고 부서가 실제 담당자로 바꾼다(SBM-08 확정) — 주관부서가 남의 부서 담당자를 정하지 않는다는 원칙과 같다. 항목의 법령 근거는 개선조치로 그대로 전이한다.
- **점검항목 마스터 단일화(SBM-18 확정)** — 점검표 관리 모달과 F5 점검표는 **서식 유형·버전별 하나의 점검항목 마스터**를 함께 쓴다. 관리 모달에는 현재 사용 중인 F5 항목 7건을 빠짐없이 표시하고 추가·수정·사용중지를 그 마스터에 저장한다. 새 F5를 만들 때 당시 사용 중인 항목을 문서에 스냅숏으로 복사하며, 마스터 변경은 이미 작성 중이거나 확정된 F5에 소급하지 않는다. 따라서 운영 마스터와 새 문서의 항목은 일치하고 과거 문서의 감사 이력도 보존된다.
- **필수 라벨 ↔ 실제 강제 정합** — 게시 위치·게시일은 `필수` 라벨과 동일하게 실제 저장 검증에서도 강제하며, 한 항목이라도 비면 저장하지 않고 첫 오류 항목으로 초점을 옮긴다.
- **필수는 본문과 게시 정보다(SBM-02 확정)** — 저장을 막는 것은 **목표 · 세부방침(1건 이상) · 시행일** 셋이고, 게시 등록에서는 **게시 위치 · 게시일**이다. 필수 라벨을 붙여 놓고 빈 값을 자동 대체하는 지금 동작은 **라벨과 실제가 어긋나 담당자를 속인다** — 자동 대체를 없애고 실제로 막는다. 점검자·증빙은 이행점검 단계의 값이라 방침 저장의 필수가 아니다.
- **전 항목 판정을 강제하고 X에는 사유를 받는다(SBM-09 확정)** — 미판정 항목이 있으면 점검을 확정할 수 없고, 무엇이 비었는지 밝힌다. **X(부적합)에는 사유가 필수**이고 **"해당없음"에도 사유를 받는다** — 사유 없는 해당없음이 종이 서식의 가장 흔한 회피 경로이고, 그대로 두면 그 문제를 시스템으로 옮기는 것이 된다. 텍스트 서술 항목은 판정 항목과 달라 빈 값을 허용한다.
- **삭제는 무엇이 지워지는지 밝히고 확인을 받는다(SBM-12 확정)** — 게시 카드·증빙·세부방침 줄 모두 확인 단계를 거친다. 세부방침 줄은 이행점검 항목과 이어져 있을 수 있으므로 **연결된 점검 항목이 있으면 그 사실과 건수를 함께** 밝힌다. 되돌리기는 두지 않는다 — 되돌리기가 있으면 확인을 대충 하게 되고, 삭제 전 확인이 이미 그 역할을 한다.
- **마스터 모달도 같은 검증을 받는다(SBM-17 확정)** — 근거법령·고려사항·점검 항목을 추가할 때 **빈 값으로 행이 생기지 않게** 막는다. 지금은 기본값이 자동으로 들어가 "제목 없는 항목"이 목록에 쌓이는데, 그렇게 생긴 행은 아무도 지우지 않고 남아 점검표를 어지럽힌다. 항목명은 필수이고 나머지는 선택이다.
- **저장 경계(영구화)** — 버전 추가·게시·증빙·점검 결과는 인메모리 SSOT(`POLICY_STATE`)에 반영되어 세션 동안 유지되나 전체 새로고침 시 초기 시드로 리셋된다. 이행점검표 인스턴스만 e-Doc 엔진에 별도 보관되어 세션 종료 후에도 유지된다. **본개발 영속 계약**: §6에서 확정한 모든 저장 행위(버전 추가·게시·증빙·점검 결과·결재 상태 전이)가 즉시 영속 대상이다. 현행 인메모리 리셋은 프로토타입 한계(구현 차이)다.
- **상신·게시 선행조건** — 미상신·미점검 상태에서도 상신·게시가 가능하다. 선행 조건은 위 결재 정책에서 확정했다 — **상신은 본문이 채워진 상태에서, 게시·공표는 승인완료 이후**다.
- **온나라 결재 전환·채번** — 결재 상태 전환은 시뮬레이션이며 권한·결재선·선행조건이 적용되지 않는다. [확정] 정식 문서번호는 **온나라 채번을 정본**으로 하며(실연계 시 자동 수신, 미연계 시 결재 완료 후 담당자 수동 입력, 결재 전 '미채번'), 실제 온나라 연동은 본개발 구현 범위이며, **승인되면 그 버전이 잠기고 시행일에 현행으로 전환되며, 반려되면 미상신으로 풀리고 반려 사유가 함께 표시**된다(SBM-07 확정).

## 7. 미결사항

없음. 결재 주체와 결재선·입력 유효성·현행본 판정과 전환 시점·편집 잠금 범위·상신과 게시의 선행 조건·문서번호 채번·개선조치 자동 연계 기준·이행점검 판정 규칙·버전 번호 규칙·삭제 확인 절차·표시값 산정·상태 처리·마스터 모달 검증은 모두 §6에서 확정했다.

온나라 **실연계**와 실서비스 영구 저장은 미결이 아니라 본개발 구현 범위이며, 승인·반려가 무엇을 바꾸는지는 §6에 정해져 있다.
