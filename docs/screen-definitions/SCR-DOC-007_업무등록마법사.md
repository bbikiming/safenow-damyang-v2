# 화면 정의서 — 업무 등록·수정 (마법사)

> 화면 ID: SCR-DOC-007 · 화면 유형: 등록·수정 (팝업) · 기획 관점(v6)
> 판단이 필요했던 항목은 §6 정책에서 확정했습니다.

---

## 1. 화면 정보

| 항목 | 내용 |
|---|---|
| 화면 ID | SCR-DOC-007 |
| 화면명 | 업무 등록·수정 (마법사) |
| URL 경로 | docs-preset.html · docs-exec.html (업무 등록 버튼 → 팝업) / doc-detail.html (편집·삭제) |
| 상위 메뉴 | 업무문서 > 업무 목록 · 이행 목록 |
| 화면 유형 | 등록·수정 (팝업) |

**목적·설명** — 업무문서를 새로 등록하고, 등록한 문서를 수정·삭제하는 팝업형 입력 화면이다. 하나의 팝업 안에서 4단계로 진행한다 — ① 분류(법령 분류·세트·PDCA 단계 지정) ② 처리유형 선택(첨부파일·전자문서·프로그램) ③ 처리유형별 상세 입력 ④ 확인·저장. ②에서 무엇을 고르느냐에 따라 ③단계의 입력 항목이 달라지며, 담당자 지정은 세 처리유형 모두에 공통으로 들어간다. 등록·수정·삭제 결과는 업무 목록·이행 목록·문서 상세에 즉시 반영된다.

---

## 2. 권한 정보

- 이 요소는 자체 메뉴를 갖지 않는다. 접근·보기·수정은 **호출한 화면의 메뉴 권한**을 따르며, 그 설정은 시스템 관리의 메뉴 관리(SCR-ADMIN-005)·권한 관리(SCR-ADMIN-006)에서 한다.
- 이 화면 정의서에서는 역할별 권한과 열람 범위를 별도로 정하지 않는다.
- 업무 등록·정정·삭제는 §3~§6의 업무 흐름과 상태 전이 조건을 따른다.

## 3. 진입 / 이탈 경로 및 사용자 시나리오

**진입 / 이탈**

| 구분 | 연결 화면 | 조건 / 트리거 |
|---|---|---|
| 진입(등록) | 업무 목록 · 이행 목록 | [업무 등록] 버튼 클릭 → 등록 팝업 |
| 진입(수정) | 업무 목록 행 · 문서 상세 | [편집] 클릭 → 기존 값이 채워진 수정 팝업 |
| 진입(삭제) | 업무 목록 행 · 문서 상세 | [삭제] 클릭 → 삭제 확인 팝업 |
| 이탈 | 원래 목록 / 문서 상세 | 저장·삭제 완료 시 팝업 닫힘 + 목록·상세 갱신 |
| 이탈 | 원래 화면 유지 | [취소]·[닫기] 시 입력 취소 |

**사용자 시나리오**

| 단계 | 사용자 행동 | 화면 반응 |
|:--:|---|---|
| 1 | [업무 등록] 클릭 | 1단계(분류) 표시. 현재 보고 있던 대메뉴가 기본 선택 |
| 2 | 법령 분류(대메뉴) 탭 선택 | 해당 분류의 세트 목록으로 갱신 |
| 3 | 세트·PDCA 단계 선택 후 [다음] | 2단계로 이동. 미입력 필수값이 있으면 안내 |
| 4 | 처리유형(첨부파일/전자문서/프로그램) 선택 후 [다음] | 선택한 처리유형에 맞는 상세 입력 폼 표시 |
| 5 | 담당자 지정 + 처리유형별 항목 입력 후 [다음] | 확인 단계로 이동 |
| 6 | 확인 단계에서 요약 검토 후 [등록 완료] | 저장 → 팝업 닫힘 + "등록되었습니다" 안내, 목록에 새 문서 표시 |
| 7 | (수정) [편집] | 기존 값이 채워진 팝업 → 변경 후 [저장] |
| 8 | (삭제) [삭제] → 확인 팝업에서 [삭제] | 목록·문서 상세에서 제거 |

**분기 로직**

- **2단계에서 고른 처리유형이 3단계 입력 폼 전체를 결정한다** — 첨부파일이면 문서명·주기·법적 근거·파일 목록·보존 연한, 전자문서면 문서명·연계 양식(선택 시 미리보기 필드 표시), 프로그램이면 연결 메뉴와 그 메뉴의 화면 선택으로 갈린다. 담당자만 세 유형에 공통이다.
- **프로그램 유형은 문서명을 묻지 않는다** — 고른 화면의 이름이 그대로 문서명이 된다. 그래서 문서명 입력란이 나타나지 않고, 필수 검사도 이 유형에서는 문서명을 보지 않는다.
- **연결 메뉴를 바꾸면 화면 목록이 다시 그려지고 화면 선택은 첫 항목으로 돌아간다** — 이전 메뉴의 화면이 남아 있으면 존재하지 않는 조합이 저장된다.
- **저장할 항목이 처리유형에 따라 갈린다** — 주기·법적 근거·파일·보존 연한은 첨부파일에서만, 연계 양식은 전자문서에서만, 연결 화면 정보는 프로그램에서만 저장된다. 다른 유형에서는 빈 값으로 남는다.
- **등록과 수정은 같은 마법사를 쓰되 시작 상태가 다르다** — 수정은 기존 값이 채워진 채로 열리고 [삭제]가 함께 나오며, 마지막 단계 버튼이 [등록 완료] 대신 [저장]이 된다.
- **세트는 고르지 않아도 진행된다** — 미선택이면 "세트 미지정"으로 등록되어 업무 목록의 미지정 묶음에 들어간다(SCR-DOC-002). 법령 분류와 PDCA 단계는 반대로 고르지 않으면 다음 단계로 갈 수 없다.

**엣지케이스**

- **처리유형을 바꿔도 이미 입력한 값은 지워지지 않는다** — 문서명·담당자처럼 공통으로 쓰이는 항목은 그대로 이어지고, 그 유형에서 쓰지 않는 항목은 화면에서 사라질 뿐 저장 시 반영되지 않는다. 되돌아가면 값이 다시 보인다.
- **[이전]으로 돌아가도 입력값이 유지된다** — 단계를 오가며 확인하는 동선이 실제로 쓰이기 때문이다.
- **파일은 [파일 추가]를 눌러야 목록에 쌓인다** — 파일명·설명을 적어 두기만 하고 추가하지 않으면 저장되지 않는다. 파일명 없이 추가하면 "파일명을 입력하세요"로 막는다. 추가된 파일은 행별로 지울 수 있다.
- **필수값이 비면 해당 항목을 지목해 막는다** — 법령 분류 미선택, PDCA 단계 미선택, 처리유형 미선택, 담당자 미지정, 문서명 미입력(첨부파일·전자문서), 연계 양식 미선택(전자문서)이 각각 다른 안내로 나온다.
- **담당자는 직접 타이핑하지 않는다** — 조직도에서 한 명을 고르면 담당부서가 함께 채워진다. 부서만 따로 고르는 수단은 두지 않는다.
- **삭제는 사용자가 등록한 문서에만 열린다** — 기본 제공 문서는 수정 모드로 들어가지 않으므로 [삭제]도 나타나지 않는다.
- **저장 없이 팝업을 닫으면 입력이 사라진다** — 별도 확인을 두지 않으며, 확인 단계 신설 여부는 §6에서 확정했다.

## 4. 화면 구성별 정리

### 4-1. 단계 표시(스텝) / 이동
- 구성: 4단계 진행 표시(분류 · 처리유형 · 상세입력 · 확인), [이전]·[다음], 마지막 단계는 [등록 완료](수정 시 [저장]), 수정 모드에서는 [삭제] 함께 노출.

| 트리거 | 동작 결과 | 이동 / 메시지 |
|---|---|---|
| [다음] | 현재 단계 필수값 검사 후 다음 단계로 | 미입력 시 해당 항목 안내 |
| [이전] | 입력값을 유지한 채 이전 단계로 | — |
| [등록 완료]/[저장] | 입력 내용 저장 | 팝업 닫힘 + "등록/수정되었습니다" |
| [취소]·[닫기] | 입력 취소 | 원래 화면 유지 |

- 상태: 현재 진행 단계(분류→처리유형→상세입력→확인)를 항상 표시한다. 등록 모드와 수정 모드를 구분하며, [삭제]는 수정 모드에서만 노출한다.

### 4-2. 1단계 — 분류
- 구성: 법령 분류(대메뉴) **탭 선택**, 세트 선택, PDCA 단계 선택(P 계획·D 실행·C 점검·A 조치) **단일 선택**.

| 트리거 | 동작 결과 | 이동 / 메시지 |
|---|---|---|
| 대메뉴 탭 클릭 | 해당 분류의 세트 목록으로 갱신 | — |
| 세트 선택 | 선택한 세트의 PDCA 구성을 안내로 표시 | — |
| PDCA 단계 선택 | 한 단계만 선택 | — |

- 상태: 세트를 고르지 않으면 "세트 미지정"으로 등록할 수 있음(안내).

### 4-3. 2단계 — 처리유형 선택
- 구성: 첨부파일 / 전자문서 / 프로그램 중 하나 선택(아이콘·한 줄 설명 포함).

| 트리거 | 동작 결과 | 이동 / 메시지 |
|---|---|---|
| 처리유형 선택 | 3단계의 상세 입력 폼 구성을 결정 | "선택에 따라 다음 단계 입력 폼이 달라집니다" |

- 상태: **미선택**과 **선택됨**(첨부파일 / 전자문서 / 프로그램 중 하나) 둘이며, 고르지 않으면 다음 단계로 갈 수 없다. 여기서 고른 값이 3단계 입력 폼 전체를 가르므로 이 화면의 분기 지점이다. 수정 모드에서 유형을 바꾸면 그 유형에서만 뜻이 있는 값이 버려지므로 무엇이 버려지는지 밝히고 확인을 받는다.

### 4-4. 3단계 — 상세 입력 (담당 공통 + 처리유형별 분기)
- 공통(담당): 담당부서는 조직도에서 담당자를 지정하면 자동 표시(직접 선택하지 않음), [담당자 지정] 버튼으로 조직도에서 담당자를 고른다. 담당자는 세 처리유형 모두 필수.
- 첨부파일: 문서명 · 담당 · 주기 · 법적 근거(직접 입력) · 파일 첨부(파일명·설명 입력 후 [파일 추가] → 첨부파일 목록에 누적, 행별 삭제) · 보존 연한.
- 전자문서: 문서명 · 담당 · 연계 양식 선택(표준 양식 또는 전자문서 빌더 양식, 선택 양식 미리보기, [새 양식 만들기]로 전자문서 빌더 이동) — 그 외 항목은 전자문서 양식 안에서 입력.
- 프로그램: 담당 · 연결 메뉴 선택 → 연결 화면(뎁스) 선택 — 문서명은 선택한 화면 이름으로 자동 설정.

| 트리거 | 동작 결과 | 이동 / 메시지 |
|---|---|---|
| [담당자 지정] | 조직도 팝업 열림 → 1명 선택 시 담당부서·담당자 동시 설정 | 버튼에 선택한 담당자 표시 |
| [파일 추가](첨부파일) | 입력한 파일명·설명을 첨부파일 목록에 추가 | 파일명 미입력 시 안내 |
| 목록의 [삭제](첨부파일) | 해당 파일을 목록에서 제거 | — |
| 연계 양식 변경(전자문서) | 선택 양식의 미리보기 항목을 갱신 | — |
| [새 양식 만들기](전자문서) | 전자문서 빌더 화면으로 이동 | admin-presets.html |
| 연결 메뉴 변경(프로그램) | 해당 메뉴의 화면(뎁스) 목록으로 갱신 | — |

- 상태: 신규 등록 문서의 초기 상태는 "미시행"이다. 전자문서는 등록 이후 문서 상세에서 작성중 → 등록완료 → 확정(결재 상신) 흐름으로 이어진다(SCR-DOC-005 · SCR-EDOC 계열 연계). 처리유형을 바꿔도 입력값은 비워지지 않는다 — 그 유형에서 쓰지 않는 항목이 화면에서 사라질 뿐이고, 저장 시에는 고른 유형의 항목만 반영된다(§3 엣지케이스).

### 4-5. 4단계 — 확인·저장
- 구성: 입력 요약(법령 분류·세트·PDCA·처리유형·문서명·연계 대상·담당) + [저장].

| 트리거 | 동작 결과 | 이동 / 메시지 |
|---|---|---|
| 요약 검토 | 저장 전 입력 내용을 한눈에 확인 | — |
| [등록 완료]/[저장] | 문서 저장 후 목록·상세 반영 | 팝업 닫힘 + 안내 |

- 상태: 저장 직후 결과가 목록·상세에 즉시 반영된다(신규는 해당 분류·세트·PDCA 위치에 추가, 수정은 기존 항목 갱신, 삭제는 목록·상세에서 제거).

### 4-6. 조직도 담당자 선택 팝업
- 구성: 부서별 구성원 목록에서 1명 선택. 선택 시 담당부서·담당자를 함께 설정하고 팝업을 닫는다.

| 트리거 | 동작 결과 | 이동 / 메시지 |
|---|---|---|
| 부서 펼치기 | 해당 부서 구성원 표시 | — |
| 구성원 선택 | 담당부서·담당자 설정 후 팝업 닫힘 | "담당자 지정" 안내 |

- 상태: **미지정**과 **지정됨** 둘이며 한 명만 고를 수 있다. 지정하면 담당부서가 함께 정해지고 팝업이 닫힌다 — 부서를 따로 고르게 하지 않는 이유는 사람과 부서가 어긋나는 것을 막기 위해서다. 조직도가 비는 경우는 없다(전 부서·전 인원이 대상).

### 4-7. 삭제 확인 팝업
- 구성: 대상 문서명 표시 + [삭제]·[취소]. 사용자 등록 문서만 삭제 대상.

| 트리거 | 동작 결과 | 이동 / 메시지 |
|---|---|---|
| [삭제] | 문서 제거 후 목록·상세 갱신 | "삭제되었습니다" |
| [취소] | 삭제 취소 | 팝업 닫힘 |

- 상태: **사용자 등록 문서**에서만 열린다. 기본 제공 문서에는 삭제 수단 자체가 나타나지 않으며, 고쳐 쓰려면 복제해 등록한다. 되돌리는 수단은 두지 않으므로 이 확인 단계가 마지막 방어선이고, 대상 문서명을 반드시 함께 보여준다.

## 6. 정책

- **사용자 등록 문서 구분** — 새로 등록한 문서는 기본 제공 문서와 구분해 관리하며, 수정·삭제는 사용자 등록 문서에 한한다.
- **기본 제공 문서는 고치지 않고 복제해 쓴다(REG-05 확정)** — 기본 제공 문서는 법정 의무에서 도출한 목록이라 담양군이 고치면 "원래 무엇이었는지"를 잃고, 목록이 갱신될 때 고친 내용이 덮인다. 대신 **[이 문서를 복제해 등록]**을 제공해 사용자 등록 문서로 만든 뒤 자유롭게 고치게 한다. 원본은 조회만 가능하고, 복제본에는 어느 기본 문서에서 나왔는지를 남긴다.
- **처리유형에 따른 상세 동작** — 문서 상세에서 첨부파일=미리보기·다운로드, 전자문서=입력 폼, 프로그램=연결 화면으로 이동으로 갈린다(SCR-DOC-004·005·006 연계).
- **전자문서 양식 연계** — 전자문서는 표준 양식 또는 전자문서 빌더에서 만든 양식 중에서 고른다(SCR-EDOC 계열·프리셋 양식 관리 연계).
- **프로그램 연결 대상** — 시스템 내 화면(메뉴 → 화면)을 골라 연결한다.
- **분류 기준은 법적의무 재분류 하나다(REG-03 확정)** — 업무 목록과 동일하며, **기존 분류 기준에서는 등록을 허용하지 않는다**. 두 기준 모두에서 등록을 받으면 같은 문서가 기준마다 다른 자리에 놓여 어느 쪽이 정본인지 알 수 없게 된다. 기존 분류는 과거 문서를 찾아보는 조회 수단으로만 남긴다.
- **세트는 기존 것에 배정만 한다(REG-02 확정)** — 등록 중에 새 세트를 만들지 않는다. 세트는 업무의 묶음 단위라 목록 전체 구조에 영향을 주는데, 문서 하나를 등록하다가 만들면 비슷한 세트가 여러 개 생긴다. 마땅한 세트가 없으면 **미지정으로 두고 등록**하며, 세트 신설은 업무 목록에서 별도로 한다 — 등록이 세트 때문에 막히지 않게 하는 것이 더 중요하다.
- **처리유형은 바꿀 수 있되 입력값이 있으면 확인을 받는다(REG-04 확정)** — 유형을 바꾸면 그 유형에서만 뜻이 있는 값(첨부파일, 전자문서 입력, 연결 화면)이 쓸모없어진다. **비어 있으면 조용히 바꾸고, 값이 있으면 무엇이 버려지는지 밝힌 뒤 확인**을 받는다. 다만 **확정된 전자문서가 있으면 유형 변경을 막는다** — 확정 문서는 기록이라 유형을 바꾸는 순간 그 기록이 어디에도 속하지 않게 된다. 바꾸려면 문서를 새로 등록한다.
- **양식 만들기로 나갈 때 등록값을 보존한다(REG-06 확정)** — 전자문서 빌더로 이동했다가 돌아오면 작성 중이던 값이 그대로 있어야 한다. 사라지면 담당자는 양식을 먼저 만들고 등록을 다시 시작하게 되고, 그 과정에서 이미 입력한 것을 잊는다. 돌아왔을 때 **방금 만든 양식이 선택된 상태**로 이어진다.
- **문서번호는 이 화면이 부여하지 않는다(REG-07 확정)** — 정식 문서번호는 공문이 나갈 때 온나라가 채번한다. 등록 문서에 자체 번호를 붙이면 온나라 번호와 두 개가 도는데, 담당자는 어느 것을 공문에 적어야 하는지 알 수 없다. 목록 안에서 구분할 **내부 식별자만** 두고 화면에 문서번호로 표시하지 않는다. 업무 자동발행이 문서번호 필드를 두지 않는 것과 같은 이유다.
- **담당자는 조직도에서 고르고 외부 인력은 넣지 않는다(REG-09 확정)** — 출처는 행정포털 조직도이며 이 시스템이 명단을 따로 갖지 않는다. **용역·위탁 인력은 담당자로 지정하지 않는다** — 업무 문서의 담당자는 그 의무를 이행할 책임이 있는 사람이고, 그 책임은 외부에 넘길 수 없다. 외부가 실제 작업을 하더라도 문서 담당자는 소관 부서의 공무원이다.
- **반영 범위** — 등록·수정·삭제 결과는 업무 목록·이행 목록·문서 상세에 동일하게 반영된다.

## 7. 미결사항

없음. 세트 신규 생성·분류 기준 적용 범위·처리유형 변경 허용 범위·기본 제공 문서 편집·양식 만들기 동선의 값 보존·문서번호 채번·담당자 지정 범위는 모두 §6에서 확정했다.

실서비스 저장 방식과 결재·파일 보관 연동은 미결이 아니라 **본개발 구현 범위**다 — 무엇을 저장하고 어디에 잇는지는 §4·§6에 정해져 있다.
