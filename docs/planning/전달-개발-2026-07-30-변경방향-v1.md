## 0. 먼저 — 이번 변경을 관통하는 원칙 4가지

개별 항목을 하나씩 보면 산발적으로 보이지만, **거의 모든 변경이 아래 4가지 중 하나에서 나왔습니다.** 개별 스펙이 헷갈릴 때 이 원칙으로 되돌아오면 판단이 섭니다.

### 원칙 1 — 시스템이 사람의 판단을 대신하지 않는다

발주처가 반복해서 거부한 것이 **자동 처리**입니다.

> *"이게 다 직접 타이핑 하셔야 돼. 이거는 자동으로 못 만들어드리고"* (공문 본문)
> *"부서마다 이런 걸 작성을 못해요. 실질적으로 능력이 안 돼요"* (위험도 계산표 → 그래서 **양식을 주는 것**으로 해결)

자동화해도 되는 것과 안 되는 것의 경계가 분명합니다.

| 시스템이 한다 | 사람이 한다 |
|---|---|
| 붙임파일 **연결** | 공문 **본문 문장** |
| 수치 **계산·집계** | 유해위험요인·개선조치 **작성** |
| 양식 **제공**(다운로드) | 위험도 **판정** |
| 기한·상태 **추적** | 완료 **확인** |

**→ 개발 시 판단 기준**: "이 값을 시스템이 만들어도 되나?"를 물었을 때, 그 값이 **책임의 근거가 되는 문장·판단**이면 사람이 칩니다. 계산·연결·추적이면 시스템이 합니다.

### 원칙 2 — 선언이 아니라 증빙으로 완료한다

가장 많은 변경이 여기서 나왔습니다.

> *"지금 제일 중요한 거는 개선 전 개선 후가 없어요. 이 개선 후를 사진을 올리기만 하면 돼요 … 사진 첨부해서 이렇게 하면은 이게 법적으로 한 거예요"*
> *"도시과 뭘 해야 되는데 원래 해야 돼요 해당 없어 나 이해가 안 되네"* (종이 서식의 실패 모드)

"했다"는 체크만으로 완료되던 곳을 전부 **증빙 필수**로 바꿨습니다.

- 개선조치 완료 → **개선 후 사진 없으면 완료 불가**
- 완료 확인 → **전자서명(누가 언제)** 기록
- 이행점검 `이행` → **증빙 사진 + 위치** 필수
- 이행점검 `해당없음` → **사유 없이 저장 불가**
- 조치 완료 → **제3자(주관부서) 확인** 단계 신설 ← 이번에 새로 생김

**→ 개발 시 판단 기준**: 상태를 `완료`로 바꾸는 모든 경로에 "무엇으로 소명하나"를 물으십시오. 소명 수단이 없으면 그 상태 전이는 막아야 합니다.

### 원칙 3 — 순서가 곧 통제다

교육의 `[결재 상신]` 버튼을 발주처가 **두 번** 지우라고 했습니다. 기능이 틀린 게 아니라 순서가 틀렸습니다.

> *"왜 갑자기 뜬금없이 결재 상신이 있지"*
> *"결재 상신을 눌러요. 그럼 공문 내용이 있을 거 아니에요? **작성을 하고** … 붙임 파일에 넣어놨었잖아요. 그러면은 끝나는 거죠"*

**→ 개발 시 판단 기준**: 결재/제출 버튼을 만들 때 **그 앞에 무엇이 완성돼 있어야 하는지**를 먼저 정하고, 그것이 없으면 버튼을 **비활성이 아니라 아예 다른 안내**로 바꿉니다. 게이트가 곧 업무 순서입니다.

### 원칙 4 — 못 하는 것은 감추지 말고 화면에 드러낸다

> *"공문을 여기다 첨부하면은 문서들에 대한 기록이 남잖아요. 그러면 더 이상 수정이 안 돼요. 이건 문서 위조예요"*

데이터가 없거나 확정되지 않은 곳을 **그럴듯하게 채우지 않습니다.**

- 부서 명단 → `11 / 39개 등록 · 나머지 28개 명단 미확보`
- 특별교육 대상 작업 → `목록 미등록 — 별표5 수집 후 제공`
- 공문 기관정보 → `미등록` / `미확정`
- 온나라 연동 → `연동 미구현 — 결과 수신 시연`

**→ 개발 시 판단 기준**: 빈 값을 임의값으로 채우면 발주처가 그걸 "된 것"으로 오인하고 결정을 안 내립니다. **빈 상태를 드러내야 결정이 넘어옵니다.**

## 1. 되돌린 것 — 기존 구현을 **제거·중단**한 부분

개발자가 가장 혼란스러울 부분입니다. **이미 만든 기능을 없앤 것**이라, 왜 없앴는지 모르면 되살리기 쉽습니다.

### 1-1. 보고서 자동 파싱·검수 화면 **폐지** (위험성평가)

| | 기존 구현 | 변경 후 |
|---|---|---|
| 흐름 | 용역업체 통합보고서 업로드 → **시스템이 항목을 추출** → 검수 화면에서 확인 | 보고서 업로드 → **빈 작성표** 생성 → 담당자가 `[＋행 추가]`로 **직접 작성** |
| 데이터 | 파싱 결과 | 사람이 입력한 행 |

**왜** — 회의에서 통합보고서 자동 분배안이 **논의 중 뒤집혔습니다.** 참석자1이 먼저 제안했으나 반론을 받고 *"차라리 그게 나을 것 같죠? 그냥 그렇게 할게요… 차라리 전체 파일 한 것보다"* 로 **부서별 분할 업로드**로 결정됐습니다. 부서별 한글 파일이 용역업체에서 이미 쪼개져 오므로 추가 부담도 없습니다.

> ⚠️ **다시 만들지 마십시오.** 실 개발에서 "PDF/HWP 파싱하면 편하지 않나?"는 유혹이 다시 옵니다. 이건 기술 문제가 아니라 **책임 문제**입니다 — 시스템이 옮긴 항목이 틀리면 누구 책임인지 정해지지 않습니다.

### 1-2. 교육 결재 상신 **진입점 차단** (제거 아님)

| | 기존 구현 | 변경 후 |
|---|---|---|
| 상신 버튼 | 8개 화면에 산재 | **전부 안 보임** |
| 코드 | — | `EDUAPV.SUBMIT_ENABLED = false` **스위치 하나** |
| 모듈 | — | 렌더러·결재선·상태 스토어·이력 **전부 살아 있음** |

**왜** — 원칙 3(순서). 공문 작성 단계 없이 결재만 올라가는 순서가 틀렸기 때문입니다.

**되살리는 조건** — *"결재 전에 공문 작성 화면이 먼저 뜨는 흐름"* 이 생기면 **리터럴 하나만** `true`로 되돌립니다. 화면 8곳은 손대지 않습니다.

> ⚠️ **화면을 고쳐서 버튼을 지우지 마십시오.** 8개 화면에 흩어 놓으면 되살릴 때 8곳을 다시 찾아야 합니다. 이번에 위험성평가 쪽에 공문 작성 흐름이 생겼으므로(§2-3), **되살릴 조건은 이미 충족**됐습니다. 다만 교육 도메인 적용은 별도 판단 사안으로 남겨 뒀습니다.

### 1-3. 개선조치 **독립 메뉴 제외** (파일·데이터는 보존)

| | 기존 | 변경 후 |

**왜** — 개선조치는 정기·수시평가 안에서 처리하는 것이지 별도로 찾아 들어가는 목록이 아닙니다.
**주의** — 그룹 소속·`DYLAW.MAP`·딥링크가 살아 있어야 `my-work`·대시보드에서 넘어오는 링크가 깨지지 않습니다.

> *"왜 취소는 왜 할 필요가 왜 있는지 모르겠네. 수정을 차라리 수정 버튼을 누르는 게 낫지"*

- 탭 `전체 / 미이수 / 이수` **3개** (구 `교육 건` 탭 제거 — 되살리지 말 것)

### 1-5. 기타교육 5종 → **법정 3유형**

| 기존 5종 | 변경 후 3유형 |
|---|---|

**왜** — 구 5종은 **법정 교육구분이 아닙니다.** 산안법 시행규칙 별표4가 정한 구분만 남겼습니다.

### 2-2. ⑧ 완료 확인 — 왜 필요한가, 어떻게 구현하나

**문제** — 기존 구조에서 부서가 완료를 누르면 그대로 평가까지 끝났습니다. 주관부서에 남은 수단은 재촉뿐인데, **재촉 버튼은 완료되는 순간 사라집니다.** 즉 부서의 **자기 선언이 곧 확정**이었습니다.

**구현 시 반드시 지켜야 할 것 — `status`를 건드리지 마십시오.**

프로토타입 기준 `status === 'DONE'` 이분법으로 세는 곳이 **8군데**입니다(부서별 집계·평가 진행률·카드 완료율·목록 필터·대시보드·내 할일 2곳·자동 완료 판정). 여기에 `CONFIRMED` 같은 4번째 값을 넣거나 완료 시점을 확인 이후로 미루면 **8곳이 동시에 어긋납니다.**

```
확인은 status 가 아니라 별도 축이다

improvement.confirm = {
  state  : WAIT | OK | RETURNED   // 없으면 WAIT 로 파생 (기존 데이터 마이그레이션 불필요)
  by, at                          // 누가 언제
  reason                          // RETURNED 일 때 필수 — 없으면 저장 거부
  round                           // 제출 회차, 재제출마다 +1
}
```

**반려해도 `status`를 되돌리지 않습니다.** 되돌리면 평가 자동완료를 되돌릴 수 없어(단방향 전이) 평가가 잠긴 채 개선조치만 미완료인 모순이 생깁니다. 대신 실질 제재를 둡니다.

1. **공문 기안이 막힌다** — 전 건 `OK`여야 기안 진입점이 열림
2. **담당자 화면에 반려 사유·회차가 상시 표시**

> 감수한 대가: 반려 건도 완료로 집계됩니다(완료율 100%인데 반려 2건). 배지·요약 배너로 드러내는 것으로 갚습니다. 완료율 게이지를 확인 기준으로 바꾸면 담당자 화면에서 *"내가 다 했는데 100%가 아닌"* 문제가 생겨 일부러 바꾸지 않았습니다.

**확인 UI 요건**
- 새 화면·새 모달을 띄우지 않고 **개선조치 카드 안 인라인 패널**로 펼침
- 증빙 요약(개선 전 N장 / 개선 후 N장 · 완료일 · 전자서명 · 조치내용) 표시
- **`열람했습니다` 체크 전에는 `[확인]` 비활성** — 오확인 방지
- 재제출 건이면 경고(같은 사진 재사용 여부는 **막지 않고 알리기만**)
- 상신 후에는 확인 결과 변경 불가

### 2-3. ⑨~⑪ 공문 → 온나라 — 순서와 서식

**순서 (원칙 3)**

```
[공문 기안] ──▶ [문서 미리보기] ──▶ [온나라로 결재 상신]
   작성 폼          표준 공문 지면         확인 모달 → 잠금
   상신 버튼 없음    여기에만 상신 버튼
```

기안 폼에서 **곧바로 상신하는 버튼을 만들지 마십시오.** 그게 발주처가 교육 결재를 지운 이유입니다.

**서식 — 표준 공문서 서식을 따릅니다**

「행정업무의 운영 및 혁신에 관한 규정 시행규칙」 **별지 제1호서식**(기안문·시행문)은 **전 행정기관 공통**입니다. 담양군 고유 양식이 따로 있지 않습니다.

```
              담 양 군                      ← ① 행정기관명 (중앙, 자간)
━━━━━━━━━━━━━━━━━━━━━━━━━━━
수 신   수신자 참조(…)   (경유)             ← ② 내부결재면 "내부결재"
제 목   2026년 정기 위험성평가 …
━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. 관련: …                                  ← ③ 본문 항목 체계
2. 위 호와 관련하여 …                          1. → 가. → 1) → 가)
   가. 대상 부서: 2개 부서                     상위보다 두 칸씩 들여쓰기
   나. 개선조치: 3건
붙 임   1. 부서별 개선조치 확인 결과표 1부.    ← ④ 붙임 + "끝."
        2. 개선 전·후 증빙 사진철 1부.   끝.       (붙임 없으면 본문 끝에 "끝.")

          담 양 군 수    (관인)              ← ⑤ 발신명의 — 외부발송만
──────────────────────────
기안자 … 검토자 … 결재권자 …                 ← ⑥ 서명란은 **하단** (상단 아님)
협조자 -
시 행  재난안전과-101(2026-08-03)  접 수  -   ← ⑦ 접수는 외부발송만
우 (미등록) … / www.damyang.go.kr           ← ⑧ 기관정보 — 외부발송만
전화 (미등록) / 공개구분 (미확정)
```

**내부결재 / 외부발송은 지면이 실제로 다릅니다** — 하나로 합치지 마십시오.

| | 내부결재 | 외부발송(시행문) |
|---|---|---|
| 수신 | `내부결재` | 수신자 지정 + `(경유)` |
| 발신명의·관인 | **없음** | `담 양 군 수` + 관인 |
| 접수란·기관정보 | **없음** | 있음 |

**주의사항**
- **큰 표를 본문에 넣지 않습니다** — 부서별 결과표는 **붙임 별지**로 분리(인쇄 시 새 장)
- **보고서 서식으로 그리지 마십시오** — 절 구분(Ⅰ/Ⅱ/Ⅲ)·KPI 카드는 공문에 없습니다 *(초판이 이 오류를 냈고 v1.1에서 교체했습니다)*
- **결재란 칸 수는 결재선에서 파생** — 코드에 고정 금지. 결재권자는 법령이 아니라 **지자체 위임전결규칙** 소관이라 조직개편·규칙개정으로 바뀝니다
- 재상신은 **이전 건을 덮어쓰지 않고** 별도 이력으로 쌓고, 최신이 아닌 건은 상태 변경을 막습니다(이력 변조 방지)

### 2-4. 부서 전수 이행 체크리스트 (경영방침 · 의무 이행점검)

> *"과 쭈르륵 사업소 쭈르륵 해가지고 돼 있는지 안 돼 있는지"*

두 화면이 **같은 부서 축**을 공유합니다(공용 엔진 1개).

| | 기존 | 변경 후 |
|---|---|---|
| 경영방침 게시 | 버전별 게시 건수(1~2건) | **전 부서 게시 여부 · 위치 · 게시사진** |
| 의무 이행점검 | §4/§5 조문 축만 | 조문 축 + **부서 전수 축**, 중대산업/중대시민 **2탭** |

**필수 검증 2가지** (원칙 2)
- `이행`으로 저장하려면 **증빙 + 위치**가 있어야 함
- `해당없음`은 **사유 없이 저장 불가** ← 발주처가 종이 서식에서 지목한 실패 모드

**상태는 코드로 저장하고 문구는 화면이 정합니다** — 이행점검은 `이행/미이행`, 경영방침은 `게시/미게시`로 읽혀야 하는데, 표시 문구를 저장하면 라벨을 바꿀 때 데이터가 깨집니다.

### 3-1. FMS 시설물 연계 — 무엇을 어디에 저장하나

시설물은 **평가 단위가 아니라 행(유해위험요인) 단위**로 붙습니다. 정기평가는 부서 단위 연 1건이고 용역 보고서 한 건에 여러 시설물의 지적사항이 섞여 나오므로 "시설물 1건 = 평가 1건"이 성립하지 않습니다.

```
정기: 검수 행 {facilNo, facilNm, facilNa}  ──┐
                                             ├─→ 개선조치 hazard{facilNo, facilNm, facilNa} ─→ 시설물 상세 역조회
수시: 등록 행 {facilNo, facilNm, facilNa}  ──┘
```

**시설물 축은 두 값이 아니라 세 상태입니다.** 빈 값 하나로 두 가지 뜻을 나르면 다음 단계에서 구분할 수 없습니다.

| 상태 | 저장 | 뜻 | 다음 단계에서 |
|---|---|---|---|
| 지정 | `facilNo` 있음 | 이 시설물이 대상이다 | 시설물명을 표시하고 역조회에 잡힌다 |
| 해당 없음 | `facilNo` 빈 값 · `facilNa = true` | **확인한 결과** 시설물에 붙지 않는 요인이다 | "해당 없음"을 표시한다 — 되돌아가 확인할 필요가 없다는 신호 |
| 미지정 | `facilNo` 빈 값 · `facilNa = false` | **아직 아무도 판단하지 않았다**(기본값) | 줄 자체를 만들지 않는다 |

셋 다 오류가 아니고 어느 것도 저장·전달·완료를 막지 않습니다. **비워 둔 것을 '해당 없음'으로 읽지 마십시오** — 미입력을 판단으로 단정하는 것은 이 시스템이 다른 축에서도 금지한 실패 모드입니다(부서 이행 체크의 '해당 없음' 사유 강제와 같은 근거).

| 항목 | 규칙 |
|---|---|
| **잇는 키** | `facilNo`(FMS 시설물번호). `facilNm`은 **표시용**이며 키로 쓰지 않습니다 — 동명 시설물이 실재하고(삼지교 2건) 개명·통폐합됩니다 |
| **필수 여부** | **선택**. 세 상태 모두 정상이며 오류가 아닙니다. 작업행동·화학물질·보건 요인은 시설물에 붙지 않습니다(산안법 §36①이 '건설물'과 '작업행동'을 병렬로 둠) — 그런 행은 '해당 없음'으로 표시하는 것이 정확합니다 |
| **배타성** | `facilNo`와 `facilNa`는 동시에 서지 않습니다. 시설물을 지정하면 `facilNa`는 자동으로 풀립니다 |
| **승계** | 개선조치 생성 시 `hazard` 객체로 복사됩니다. 이 객체는 **화이트리스트**라 필드를 늘리면 승계 지점도 함께 늘려야 합니다(실제로 여기서 한 번 유실됐습니다) |
| **역조회** | 시설물 상세는 `hazard.facilNo`가 같은 개선조치를 모아 보여줍니다 |
| **전파 범위** | 개선조치 목록·상세·공용 카드·내 할일이 같은 값을 표시합니다. **미지정만** 줄을 만들지 않고 '해당 없음'은 그대로 냅니다 — 감추면 담당자가 앞 단계로 되돌아가 같은 확인을 다시 합니다. 네 화면이 **표시 판정 함수 하나**를 공유하므로 화면마다 조건을 다시 쓰지 마십시오 |

### 3-2. 시설물 데이터 — 소유권이 둘로 갈립니다

| 소유 | 내용 | 규칙 |
|---|---|---|
| **FMS 소유** | 시설물관리대장 기본현황(수신분) + 반영키 | 화면에서 **편집 불가**. 정정은 FMS로 수정 전송 후 재수신으로만 |
| **자체 소유** `ext{}` | `safetyGrade` `deptNm` `lastInspectYmd` `nextInspectYmd` `defectYn` `defectType` `repairStatus` `sizeValue` `sizeUnit` `dailyUsers` `hazmatYn` `lat` `lng` `adjacentRisk` | **수신이 덮어쓰지 않습니다.** 이 경계가 무너지면 대장을 받을 때마다 담당자가 채운 값이 사라집니다 |

> **소유권은 옮겨질 수 있습니다** — 안전등급·점검이력·중대결함·규모는 원래 FMS의 다른 연계업무 소관인데 아직 수신하지 않아 자체 입력으로 둔 것입니다. 추가 연계가 붙으면 FMS 소유로 이관되고 직접 입력은 닫습니다. 스키마 설계 시 이 이관을 전제로 잡아 주세요.

**시설물 레코드에는 생애 상태가 필요합니다.** 화면 정의서(SCR-FAC-004 §6, FSY-04)가 *"없어진 시설물은 지우지 않고 폐지로 표시한다"* 로 확정했는데, 지금 프로토타입의 레코드에는 그 상태를 담을 자리가 없습니다 — **개발 시 반드시 두십시오.**

| 상태 | 뜻 | 화면에서 |
|---|---|---|
| 사용 | 정상 | 기본 목록·위험도·관리대상 판정에 포함 |
| 폐지 | FMS 수신 목록에서 사라졌고 사람이 확인함 | 기본 목록에서 빠지고 **조회 조건으로만** 보인다. 딸린 보완입력·위험도·개선조치 이력은 **그대로 남는다** |

- **자동으로 폐지하지 않습니다.** 수신 파일이 일부만 담고 있었을 때 멀쩡한 시설물이 통째로 폐지됩니다. 차이 미리보기에 "받은 목록에 없음 N건"으로 올리고 사람이 확인합니다(현재 차이 판정은 신규·변경·동일 세 갈래뿐이라 **네 번째 갈래를 추가**해야 합니다).
- **레코드를 지우는 경로는 만들지 마십시오.** 그 시설물에 달린 개선조치 이력은 "그때 그렇게 판단했다"는 기록이라 시설물이 없어져도 남아야 합니다.

**표시명은 대장에서 매번 찾습니다 — 저장된 이름은 폴백입니다.**

개선조치가 들고 있는 `hazard.facilNm` 은 조치를 만들 때 복사해 둔 **스냅샷**입니다. FMS 가 시설물을 개명해 보내면 대장은 새 이름인데 개선조치는 옛 이름으로 남습니다. **잇는 키(`facilNo`)는 멀쩡해서 역조회는 되므로 오류로 드러나지 않고 보이는 이름만 조용히 갈립니다** — 담당자가 현장에서 그 이름의 시설물을 못 찾습니다. 그래서 표시할 때는 ① 대장에서 현재 이름을 찾고 ② 없으면 저장된 스냅샷 ③ 그것도 없으면 시설물번호 순으로 떨어뜨립니다. 스냅샷을 지우지 않는 이유는 폐지된 시설물이 대장에서 빠질 수 있고, 그때 이름조차 없으면 지난 이력이 "번호만 남은 줄"이 되기 때문입니다.

### 3-3. 기한이 없는 개선조치가 실제로 생깁니다

수시평가는 조치기한이 **선택**이라 기한 없는 개선조치가 만들어집니다. 이 건들은 **기한 초과 집계에서 빠집니다.** 화면에는 빈칸이 아니라 `기한 미지정`으로 표시하도록 통일했습니다(목록·카드·내 할일 3곳). 실 개발에서 기한을 필수로 바꿀지는 발주처 확정 대상입니다.

**주의 — 첨부파일**
프로토타입은 일부 경로가 **파일명 문자열만** 저장합니다. 실 개발에서는 개선조치 증빙처럼 **실제 파일 저장소 + 메타(원본 해상도·용량·업로더·업로드시각)** 가 필요합니다. 증빙 사진은 소명 자료이므로 원본 보존 정책(보존기간·삭제 금지)을 함께 정해야 합니다.

|---|---|---|---|

| 관리감독자 | 실과장·사업소장·읍면장 | 소속 부서 | 조회 + **재촉**(산안법 §16 지휘·감독) |
| 업무담당자 | 주무관 | 자기 부서 | 완료 처리·제출·전자서명 |
| ┗ 주관부서 실무자 | 재난안전과 | 전 부서 + 시스템 관리 | 위 + **평가 운영·완료 확인·공문 기안** |

**판정 규칙 2개** (이 두 개로 전부 갈립니다)

```
canAct()     = tier === 'staff' && 내 소속 === 보고 있는 부서
               → 완료 처리·제출·전자서명

canManage()  = 소속 === 주관부서(재난안전과)
               → 평가 생성·보고서 접수·검수·조치기한·완료 확인·공문 기안
```

**설계 원칙**
- **조회는 막지 않습니다** — 진행 상황을 보는 건 총괄·감독의 정당한 권한입니다
- **대리 서명은 막습니다** — 군수·과장이 담당자 이름으로 완료 서명하면 **문서 위조**입니다
- 권한이 없으면 버튼을 **비활성이 아니라 다른 것으로 교체**하고, **왜 없는지 밝힙니다**
- 화면에서 버튼을 숨기는 것으로 끝내지 말고 **함수 진입부에도 가드**를 둡니다(콘솔·딥링크 우회)

### 5-0. 이번 전달 범위 — 내 할일(my-work)은 다음 차수

`내 할일`은 화면 정의서를 쓰지 않았습니다. 이 화면이 위험성평가 흐름의 부서 담당자 쪽을 맡고 있어 그대로 두면 이 축만 떼어 개발할 수 없으므로, **2026-08-11에 의존을 끊었습니다.**

- **설문조사표 제출** → 정기 위험성평가 화면 안에서 한다(`내 부서 진행 상황` 1단계). 제출자·제출일은 실제 접속자로 기록되고, 주관부서의 **대리 등록**과 이력에서 구분된다.
- **개선조치 완료·재제출** → 개선조치 목록 → 상세에서 한다(원래 자족 경로였다).
- 시연 투어 9단계도 같은 자리를 가리키도록 다시 배선했다.

권한 판정은 `DYROLE.canAct` 단일 출처를 그대로 쓴다 — 제출은 **자기 부서 담당자 본인**만 하고, 관리·감독 계층에는 버튼이 나타나지 않으며 전역 호출로도 뚫리지 않는다.

**`내 할일`을 되살릴 때 주의** — 한 도메인의 수행 경로를 그 화면에만 두지 마세요. 모아 보는 편의 화면이어야 하고, 각 도메인은 자기 화면 안에서 닫혀야 합니다.

### 5-3. 위험성평가 기록·보존 — 확정된 요구사항

시행규칙 §37의4가 정하는 **기록 필수 항목 3가지**입니다. 현재 프로토타입에 ①은 있고 ②·③은 없으므로 **개발에서 채워야 합니다.**

| 항목 | 근거 | 프로토타입 |
|---|---|---|
| ① 위험성평가 실시 시기 및 담당자 | §37의4①1호 | 있음 |
| ② 참여한 근로자 및 근로자대표 | §37의4①2호 | **없음 — 신규 개발** |
| ③ 파악한 유해·위험 요인, 위험성 수준 결정 결과, 개선대책 수립 내용 및 이행 결과 | §37의4①3호(→§37의3제2호) | 부분 — 개선대책 **이행 결과**까지 한 화면에서 보이지 않음 |
| **보존 3년** | §37의4② | **없음 — 신규 개발** |

여기에 **근로자 참여**(§37의2 — 사업장 순회 점검이 원칙, 설문조사·면담 병행 가능)와 **근로자 공유**(§37의3 — 실시 전 일정, 실시 후 결과와 이행 결과) 두 축이 더 있습니다. 프로토타입에 이 두 화면이 없어 **법령 근거 칩도 붙이지 않았습니다** — 하지 않는 일을 한다고 쓰지 않는 규칙 때문입니다. 개발 범위에는 포함해 주세요.

### 5-4. 시설물 위험도 배점 — 확정값

| 변수 | 배점 | 왜 이 값인가 |
|---|---|---|
| 안전등급 | A 0 · B 8 · C 18 · D 34 · E 45 | 시행령 별표8이 D를 "사용제한 여부를 결정해야 하는 상태", E를 "즉각 사용을 금지"로 정의합니다. C→D를 가장 크게 벌린 이유가 이 문장입니다 |
| 중대결함 있음 | 40 (단일 최대) | 시행령 §18의 결함은 그 자체가 구조안전에 중대한 영향을 미치는 것으로 인정된 사유이고, 통보받으면 2년 내 착수 의무가 따라옵니다 |
| 경과연수 | 40년↑ 30 · 30년↑ 22 · 20년↑ 12 · 그 밖 5 | 노후는 상태가 아니라 개연성이라 안전등급보다 낮게 둡니다. 0점 구간을 두지 않는 것은 새 시설도 위험이 0은 아니기 때문입니다 |
| **점검 주기 초과** | 한 주기 이내 초과 8 · 그 이상 16 · 초과 없음 0 | **변경됨** — 종전의 "최근점검 경과 연수"를 폐기했습니다. 별표3이 등급별 주기를 정하므로(A~C 반기 1회 · D·E 연 3회) 같은 1년 경과라도 의미가 다릅니다. 연수로만 재면 D·E 시설의 지연이 과소평가됩니다 |
| 이용인원 | 1000↑ 12 · 300↑ 7 · 그 밖 3 | 피해 규모 축. 중대시민재해가 이용자를 보호 대상으로 삼으므로 넣되 상태 변수보다 낮게 둡니다 |
| 종별 | 2종 10 · 3종 6 | 종별은 규모·중요도이지 현재 상태가 아닙니다 |
| 내진 | 미적용 6 · 적용 0 | 특정 재난에만 걸리는 조건부 위험이라 낮게 둡니다 |
| **구간** | 55↑ 높음 · 30↑ 보통 · 그 밖 낮음 | 55점은 "안전등급 D(34) + 노후 20년(12)이면 높음", 30점은 "단일 변수 하나로는 높음이 되지 않는다"는 선입니다 |

산정 변수는 **7종**이고 표시 분모도 7입니다. 중대결함은 **있음/없음을 확인했으면** 확보로 셉니다 — '있음'일 때만 세면 결함 없는 시설물이 영원히 분모를 못 채웁니다.

**핵심 변수 2종(안전등급·최근점검)이 모두 없으면 점수를 만들지 않고 `산정불가`로 둡니다.** 없는 값을 0으로 처리하면 정보가 가장 부족한 시설물이 가장 안전해 보입니다. **이 규칙은 배점이 바뀌어도 유지해 주세요.**

배점은 상수로 분리해 주세요. 운영하며 조정할 수 있으나, 조정하면 **그때까지의 순위와 비교할 수 없게 되므로** 변경 시점과 변경 전 배점을 함께 남겨야 합니다.

### 5-5. FMS 삭제·폐지 — 스키마 결정

**하드 삭제를 두지 않습니다.** 받은 목록에 없는 시설물은 **폐지 표시 후 보관**합니다.

- 기본 목록에서는 빠지고 조회 조건으로만 보입니다.
- 딸린 보완입력·위험도·개선조치 이력은 **그대로 유지**됩니다. 그 이력은 "그때 그렇게 판단했다"는 기록이라 시설물이 없어져도 남아야 합니다.
- **폐지 처리를 자동으로 하지 않습니다** — 수신 파일이 일부만 담고 있었을 때 멀쩡한 시설물이 통째로 폐지됩니다. 차이 미리보기에 "받은 목록에 없음 N건"으로 올리고 사람이 확인합니다.

영향 범위: 시설물 대장 · 평가 행 · 개선조치 · 시설물 상세 역조회.
