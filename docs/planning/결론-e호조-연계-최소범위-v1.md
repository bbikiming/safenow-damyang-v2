# 결론 — e호조+ 연계 최소 범위

> 작성 2026-09-21 · **RFP 요구 기준으로 최소화한 확정안**
> 선행 분석: [`분석-e호조-계약연계-대체설계-v1.md`](분석-e호조-계약연계-대체설계-v1.md) · [`분석-e호조-예산연계-대체설계-v1.md`](분석-e호조-예산연계-대체설계-v1.md)
> 이 문서가 **범위 정본**이다. 위 두 분석은 「무엇이 가능한가」이고, 이 문서는 「무엇을 할 것인가」다.

---

## 0. 결론 한 장

**e호조 API 291종 중 3종만 쓴다. 필드는 8개다.**

| | |
|---|---|
| **쓰는 API** | `TFC1250M 계약관리대장` + `TCM3030C 공통상세코드` + `TCM2060C 부서코드` |
| **가져오는 필드** | **8개** (아래 §3) |
| **채워지는 화면** | 도급관리(`m=contract`) · 조직 공사별 선임 현황 |
| **RFP 근거** | SFR-007 · SFR-010 · SFR-013 |
| **쓰지 않는 것** | **예산(BM·FE) 전부** · 하도급 · 감독자 · 현장대리인 · 입찰 · 지출 |

**예산은 연계하지 않는다.** RFP 가 SFR-008 의 연계 대상을 **전자결재 하나로** 못박았고 e호조를 적지 않았다. 기술적으로 가능한 것과 요구된 것은 다르다(§5).

---

## 1. RFP 가 실제로 요구한 문장 — 전부 3개다

RFP §3 「외부 연계 시스템 정리」가 차세대 e호조에 배정한 SFR 은 **007·010·013** 셋뿐이고, 각 SFR 본문에서 e호조를 말하는 문장은 **하나씩**이다.

| SFR | 문장 | 요구하는 데이터 |
|---|---|---|
| **007** | *"차세대 e호조와 연계하여 **도급사업목록**을 기반으로 도급사업 위험성평가 실시 점검표를 생성한다"* | **목록** |
| **010** | *"차세대 e호조와 연동하여 **공사정보**를 연동한다"* + *"공사별 현황에는 **발주처, 공사명, 공사기간, 공사금액, 안전관리자** 정보를 제공한다"* | **공사 4항목** |
| **013** | *"차세대 e호조와 연동한다. 타 회계 시스템 이용 시 직접 등록 기능을 제공한다"* + *"관리 항목은 **공사관련, 용역관련, 구매설치관련, 위탁사업, 기타**로 구성한다"* | **목록 + 5분류** |

**요구의 실체는 둘이다 — ① 계약(도급·용역·위탁) 목록 ② 그 목록의 구분과 공사 정보.** 셋 다 같은 것을 다른 화면에서 쓴다.

## 2. 그래서 필요한 API 는 3종이다

| # | 테이블 | URL | 왜 필수인가 |
|---|---|---|---|
| 1 | **`TFC1250M` 계약관리대장** | `/FE/openAPI/TFC1250M` | **본체.** 목록·구분·기간·금액·부서가 전부 여기 있다 |
| 2 | `TCM3030C` 공통상세코드 | `/CM/openAPI/TCM3030C` | `ctrtKndCd` 가 **코드값**이다. 없으면 화면에 「용역」 대신 `2` 가 뜬다 |
| 3 | `TCM2060C` 부서코드 | `/CM/openAPI/TCM2060C` | `deptCd` 7자리 → 부서명. 동상 |

2·3 은 **월 1회 갱신이면 충분한 기준정보**다. 실질적으로 **일 배치는 `TFC1250M` 하나**다.

> ⚠ **FC 테이블의 URL·인터페이스ID 는 `FE` 계열이다** — `/FE/openAPI/TFC1250M`, `LR_FE_LAF_SA_00067`. 테이블명에서 영역을 추측하면 전건 404.

## 3. 필드 매핑 — 8개

**화면 A** = 도급관리 `menu.html?m=contract` (`CONTRACT_BIZ_STATE`)
**화면 B** = 조직 공사별 선임 현황 (`ORG_CONSTRUCTION_STATE`, `js/menu.js:948`)

| # | 우리 값 | 화면 | ← e호조 필드 | 타입 | RFP 근거 |
|---|---|:--:|---|---|---|
| 1 | `id` | A·B | **`ctrtLdgrMngNo`** 계약대장관리번호 | STRING(12) | 목록의 키 (SFR-007·013) |
| 2 | `name` | A·B | **`ctrtTrgtNm`** 계약대상명 | STRING(300) | SFR-010 **공사명** |
| 3 | `cat` | A | **`ctrtKndCd`** 계약종류코드 → `TCM3030C` | STRING(1) | SFR-013 **5분류** |
| 4 | `dept` | A | **`deptCd`** 부서코드 → `TCM2060C` | STRING(7) | 목록의 소관 |
| 5 | `period` 시작 / `from` | A·B | **`bgcsYmd`** 착공일자 | STRING(8) | SFR-010 **공사기간** |
| 6 | `period` 종료 / `to` | A·B | **`cmcnScdYmd`** 준공예정일자 | STRING(8) | SFR-010 **공사기간** |
| 7 | `amount` | A·B | **`smzCtrtTottAmt`** 총괄계약총금액 | NUMBER(20) | SFR-010 **공사금액** |
| 8 | `signed` | A | **`smzCtrtYmd`** 총괄계약일자 | STRING(8) | 계약 시점 |

**필드로 안 받는 것 2개**

| 우리 값 | 처리 | 근거 |
|---|---|---|
| `owner` 발주처 | **고정값 `담양군`** | `lafCd` 로 이미 필터하고 받으므로 필드로 받을 이유가 없다 |
| `src` 출처 | **`e호조` 리터럴** | 직접 등록분과 섞이지 않게 하는 우리 축(§4-3) |

### 3-1. ⚠ `bgcsYmd`(착공일자)는 공사 축이다

용역·구매설치·위탁은 착공 개념이 없어 **비어 있을 수 있다.** 그때는 `smzCtrtYmd`(계약일)로 떨어뜨린다 — **지어내지 말고 폴백 사실을 화면이 밝힌다**(「계약일 기준」). 현재 시드도 10건 중 9건이 기간 미상이라 같은 문제를 이미 안고 있다.

## 4. 범위에서 뺀 것과 그 이유

### 4-1. 안전관리자 — RFP 가 요구하지만 **e호조가 못 준다**

SFR-010 의 공사별 현황 5열 중 **`안전관리자` 하나만 e호조에 없다.** e호조는 재정 시스템이라 산안법 선임 정보를 담지 않는다.

- `TFC1910L 현장대리인`(건설기술진흥법) · `TFC1190L 계약감독자`(감독공무원)가 있지만 **둘 다 다른 지위**다. 안전관리자 열에 넣으면 **선임 공백을 선임된 것으로 표시**하게 된다.
- **확정 동작** — 안전관리자는 **직접 등록 유지**(`ORG_APPOINT_STATE`). 화면이 4열은 연계·1열은 직접 등록임을 밝힌다.
- **이건 우리 누락이 아니라 e호조의 범위다.** 정의서 §6 에 그렇게 적는다.

### 4-2. 업체명(`co`) — RFP 문언에 없다. **2차로 미룬다**

SFR-010 의 5열에도, SFR-013 의 요구에도 업체가 없다. 그런데 **현재 화면에는 `co` 열이 있고 수급인 평가 목록이 거기서 파생**된다.

- 빼면 지금 있는 열이 사라지는 **퇴행**이다. 그래서 **없애지 않고 직접 등록으로 유지**한다.
- 연계로 채우려면 `TFC1420L 공동계약내역`이 필요한데, **단독계약에도 행이 생기는지가 미검증 전제**다(계약 분석 §3-2). RFP 요구도 아닌 것 때문에 **미검증 전제를 1차 범위에 넣지 않는다.**
- 검증 ②가 통과하면 **2차에서 필드 1개(`cltNm`) 추가**로 끝난다. 그때 API 가 1종 늘어 4종이 된다.

### 4-3. 예산(BM·FE) 전부 — **RFP 요구 밖**

RFP §3 표가 SFR-008 에 배정한 연계는 **「전자결재 — 예산 편성/집행 관리 점검표 승인」** 이고, SFR-008 본문의 `integrations` 도 **`전자결재`** 하나다. **e호조가 없다.**

- [`분석-e호조-예산연계-대체설계-v1.md`](분석-e호조-예산연계-대체설계-v1.md)가 찾은 것(단일 API `TFE3233A` 로 편성·집행·분기·전년동기 확보)은 **사실이지만 요구가 아니다.**
- 그리고 그쪽은 **담양군이 「무엇이 안전보건 예산인가」를 지정해야** 시작된다(EXT-21). 요구도 아닌데 발주처 작업을 유발한다.
- **확정 동작** — 예산 편성액·집행액은 **수기 입력 유지**. RFP 대로다.
- 그 분석은 **폐기하지 않는다** — 발주처가 나중에 원하면 그때 꺼낸다. 「가능한데 안 한다」와 「모른다」는 다르다.

### 4-4. 그 밖에 뺀 것

| 뺀 것 | 이유 |
|---|---|
| `TFC1490L` 당년도계약내역 (차수·변경) | 계약 변경 이력은 RFP 요구에 없다. **다만 기간 연장을 놓친다**(§6 후속) |
| `TFC1820M` 하도급계약 | 중처법 §5 제3자 축이나 RFP 요구 아님 |
| `TFC1710L` 입찰내역 · `TFC2350M` 하자 · `TFC1770L` 지체상금 | 요구 아님 |
| `TFC2200L`·`TFC2270M` 대금지급 | 요구 아님 |
| `lctnNm` 위치명 · `ctrtCnltYn` 해지여부 | **같은 API 응답에 이미 포함돼 온다.** 받아는 두되 **1차에서 화면에 쓰지 않는다** — §6 참고 |

## 5. 「가능한 것」과 「요구된 것」 대조표

선행 분석이 찾은 것 중 **이번 범위에 드는 것은 회색 칸뿐**이다.

| 발견 | 가치 | RFP 요구 | 1차 범위 |
|---|---|:--:|:--:|
| 계약 목록·구분·기간·금액·부서 | 높음 | **O** | **✅ 포함** |
| 계약기간(공개목록에 없던 것) | 높음 | **O** | **✅ 포함** |
| `ctrtLdgrMngNo` 불변키 | 높음 | 암묵 | **✅ 포함** |
| 업체명·사업자등록번호 | 중간 | ✗ | 2차 |
| 해지여부 `ctrtCnltYn` | 중간 | ✗ | 받아만 둠 |
| 현장 위치 `lctnNm` | 중간 | ✗ | 받아만 둠 |
| 현장대리인·계약감독자 | 중간 | ✗ | 제외 |
| 하도급(제3자) | 높음(법) | ✗ | 제외 |
| 예산 편성·집행 | 높음 | **✗ (전자결재)** | **제외** |
| 계약↔예산 연결 | 높음 | ✗ | 제외 |

## 6. 1차에서 「받아만 두고 안 쓰는」 2개 — 왜 그렇게 하나

`ctrtCnltYn`(해지여부)·`lctnNm`(위치명)은 **`TFC1250M` 을 호출하면 어차피 같은 응답에 담겨 온다.** 버리는 것이 오히려 일이다.

- **저장은 하고 화면에는 내지 않는다.** 화면에 내려면 「해지된 계약을 목록에서 어떻게 다룰 것인가」라는 **운영 판단**이 필요한데 그건 EXT-14(점검 대상 선별) 와 같은 갈래다.
- 다만 **해지 계약을 점검 대상으로 내보내면 안 된다** — 끝난 계약의 반기 점검표를 만드는 것은 명백한 오작동이다. **필터에는 쓰되 열로 보여주지 않는다**가 1차 동작이다.

## 7. 여전히 남는 선행 조건

### 7-1. 인증 3건 (없으면 호출 자체가 안 된다)

| 항목 | 어디서 |
|---|---|
| 서비스 URL·포트 | 별도 공지 |
| **API 인증키** | e호조+ 자치단체게시판 **81707** 「자체시스템 API 연계 관련 파일 배포」. 첨부가 안 보이면 **기준정보관리자**가 81708 에서 첨부 사용여부를 「사용」으로 |
| 암복호화 키 | 동상 (문서암호는 콜센터 1522-7536) |

**암복호화 키는 1차 범위에 필요 없다** — 8개 필드에 `ecrp*` 가 하나도 없다. 업체(2차)를 붙일 때 필요해진다.

### 7-2. EXT-14 — 선별 기준은 여전히 담양군 몫

RFP 는 *"도급사업목록을 기반으로 점검표를 생성"* 하라는데, 담양군 계약은 **연 4,173건**이고 155만원짜리 폐기물처리용역까지 들어 있다. 전건으로 점검표를 만들면 수천 장이다.

- **바뀐 것** — 종전 제약 *"공개목록에 기간 열이 없어 손으로 못 옮긴다"* 는 **해소**됐다. 금액·기간·구분이 다 오므로 **화면에서 필터를 걸 수 있다.**
- **안 바뀐 것** — **무엇을 거를지**는 담양군 판단이다. 우리가 정하면 실측과 어긋난다(담양군 확인 2026-08-31: 문서 분류 이후 확정).
- **1차 동작** — 연계로 목록을 **받아만 두고**, 점검 대상 지정은 지금처럼 **사람이 고른다**. 기준이 정해지면 그 자리에 필터를 넣는다.

### 7-3. 부서코드 매핑

e호조 `deptCd` 는 7자리, `DYV2.ORG` 는 `safety`·`water` 문자열이다. **`DYV2.ORG` 노드에 `ehojoDeptCd` 를 더하는 것이 단일 출처 원칙(§3)에 맞는 자리**다.
⚠ `DYV2.ORG` 등록 부서는 **11개**, 담양군 과·사업소는 **39개**다. 계약은 39개 전부에서 나오므로 **매핑 없는 부서의 계약을 버리지 말고 「조직도 미등록」으로 드러낸다.**

## 8. 착수 판단

### 8-1. 1차 (이번 범위)

```
API 3종 · 필드 8개 · 화면 2개
TFC1250M ──┬─→ 도급관리 목록 (SFR-007·013)
           └─→ 조직 공사별 선임 현황 4열 (SFR-010)
TCM3030C ──→ 구분 5분류 해석
TCM2060C ──→ 부서명 해석
```

**검증은 2건이면 된다** (계약 분석 §6 의 7건 중):

| # | 호출 | 확인 | 실패 시 |
|---|---|---|---|
| ① | `TFC1250M` (fyr=2026) | `totalCnt` · **`cmcnScdYmd` 채움률** · `bgcsYmd` 채움률 | 기간이 비면 **SFR-010 공사기간이 여전히 미충족** |
| ⑤ | `TCM2060C` | 부서코드 체계 · `DYV2.ORG` 11개와 매핑 가능 수 | §7-3 불가 |

**①의 `cmcnScdYmd` 채움률이 이 연계의 성패다.** 그 열 하나 때문에 연계를 하는 것이다.

### 8-2. 2차 (RFP 밖 · 발주처가 원하면)

| 후보 | 추가 API | 조건 |
|---|---|---|
| 업체명 | `TFC1420L` | 검증 ②(단독계약 행 존부) 통과 |
| 계약 변경 이력 | `TFC1490L` | 기간 연장 누락이 실제 문제가 되면 |
| 하도급(제3자) | `TFC1820M` | 중처법 §5 논증이 필요해지면 |
| 예산 | `TFE3233A` 외 3종 | **EXT-21 지정 선행** · 별도 분석 문서 있음 |

### 8-3. 지금 코드를 고치지 않는다

인증 3건이 전부 미설정이고, `99_미결사항목록` EXT-15 의 확정 동작이 *"연계 전제를 화면에 만들지 않는다"* 다. **순서는 인증키 → 검증 ①⑤ → 정의서 개정 → 착수**이고, 검증 ①의 결과에 따라 범위가 다시 갈릴 수 있다.
