- 검토일: 2026-08-18
- 대상 문서: [`자료-업무관리-구현참고-발주측-v1.md`](자료-업무관리-구현참고-발주측-v1.md) (발주측 제공, 회의 확정 구조 전달본)
- 대조 대상: 현행 구현 `cmp-status.html`(이행 관리) · `cmp-docs.html`(문서 목록) + `DYDOCT` 데이터
- 성격: **기획 갭 점검**이다. 이 문서는 구현 지시가 아니라 무엇을 바꿔야 하는지 목록이며, §19("Claude 가 임의로 확정하면 안 되는 항목")를 지켜 판단이 필요한 것은 확정하지 않는다.

## 0. 한 줄 결론

정보구조(법령→이행항목→업무단계→증빙)와 3계층·다중 매핑·누락 점검은 **이미 부합**한다. 그러나 참고 문서의 **핵심 요구인 「업무 유형 분기」가 통째로 빠져 있다** — 지금은 168개 업무단계가 전부 `＋ 새 문서 등록` 하나로 수렴하는데, 문서는 그 구조를 명시적으로 부정한다(§6.1 *"모든 업무를 단순히 새 문서 등록으로 처리하지 않는다"*, §3 추가 검토 대상).

## 1. 바꿔야 할 것 (우선순위 순)

### G-1. 업무 유형 3분기와 유형별 CTA — **가장 큼** (문서 §6.1·§7·§12·§16)

| | 문서 요구 | 현행 |
|---|---|---|
| 유형 | `PROGRAM` / `ELECTRONIC_DOC` / `ATTACHMENT` | **축 자체가 없음** |
| CTA | `[위험성평가 실시]` `[교육 등록]` / `[업무문서 작성]` / `[결과 등록]` | 전 단계 `＋ 새 문서 등록` 단일 |
| 이동 | PROGRAM 은 문서등록 팝업이 아니라 **그 업무 메뉴로 이동** | 없음 |

- 데이터 계층에도 필드가 없다 — `DYDOCT.STAGES` 는 `id·itemId·name·law·legalCycle·opCycle·timing·target·actor·ex·docs2025·collect·st2025` 13개뿐이고 문서가 요구한 `taskType`·`targetMenu`(§16)가 없다.
- ⚠ `DYDOCT` 는 **생성물**이다(CLAUDE.md §5). 필드를 늘리려면 원본 CSV + `tools/build-docs-seed.py` 를 고쳐 재생성해야 하고, 손으로 고치면 안 된다. **유형 판정 자체가 사람 판단**이므로 CSV 에 열을 추가하는 것이 정공법이다.
- 누락 점검의 행 액션도 함께 갈린다 — 문서 §12 는 `[업무 수행]`·`[결과 등록]`·`[비해당 처리]` 3종인데 현행은 `[해당 — 문서 등록]`·`[비해당]` 2종이다.

### G-2. 완료 판단 기준을 업무단계별로 (문서 §2.2)

문서: *"단순히 문서 `0건 = 무조건 미이행`으로 하드코딩해서는 안 된다"* — 결과가 시스템 내부 데이터·결재문서·첨부·외부 수행결과 중 무엇이냐에 따라 다르므로 **단계별 완료 판단 기준을 둘 수 있는 구조**를 요구한다.

현행 `DYCMP.judge()` 는 **문서 건수 하나로만** 판정한다(주기형은 `min(문서수, 필요회차)`, 상시는 `문서수>0`). 위험성평가·교육처럼 전용 화면에 이미 완료 판정이 있는 축도 문서가 없으면 미이행으로 찍힌다.

- 참고 선례가 이미 프로젝트 안에 있다 — 업무 자동발행의 `DYWORK.deptDone(t)` 는 `doneProbe` 로 **그 도메인의 판정을 읽어온다**(CLAUDE.md §14-2). 같은 방식으로 `PROGRAM` 유형 단계는 도메인 판정을 읽고, 못 대는 도메인은 첨부로 강등하는 규칙이 그대로 적용 가능하다.
- ⚠ 단 §14-2 의 경고도 같이 온다 — 판정 기준을 업무 실체와 맞추지 못하면(예: 이수율 100% 를 완료로 잡으면) 영원히 미완료가 된다.

### G-3. 프로그램형 업무 매핑 대장 (문서 §9·§10·§20) — **산출물이 없다**

문서는 CSV 업무단계와 현재 메뉴를 비교해 **`명확 / 문서 / 첨부 / 확인 필요` 4분류**로 표시하고, `확인 필요`는 임의 구현하지 말고 별도 목록으로 남기라고 한다(§9·§19).

현행에는 이 대장이 없다. 규모만 미리 재 보면(단계명 키워드 기준, **추정치이며 확정 아님**):

| 도메인 | 해당 단계 수 | 현재 프로토타입 메뉴 |
|---|---|---|
| 안전보건교육 | 17 | 있음(`edu-*` 9메뉴) |
| 시설물·승강기·놀이시설 | 11 | 있음(`fac-*`) |
| 예산 | 7 | 있음(`bgt-*`) |
| 의견청취·산업안전보건위원회·협의체 | 6 | 있음(`opinion`) |
| 위험성평가 | 3 | 있음(`rsk-*`) |
| 작업환경측정 | 3 | 있음(`work-env`) — **문서 §9 가 «검토» 로 지목한 항목** |
| 건강진단 | 3 | 있음(`health-exam`) |
| 의무이행 점검 | 3 | 있음(`menu.html?m=comply`) |
| 경영방침 | 1 | 있음(`menu.html?m=policy`) |
| 인력 업무수행 평가 | 1 | 있음(`evl-*`) |
| **소계** | **약 55** | |
| 나머지 | 약 113 | 문서/첨부/확인 필요로 갈릴 대상 |

→ 이 표는 **키워드 매칭 추정**이다. 실제 분류는 단계별로 사람이 확인해야 하고, 그 결과가 §20 의 개발팀 전달 데이터가 된다.

### G-4. 메뉴 명칭·계층 (문서 §4)

| | 문서 | 현행 |
|---|---|---|
| 대메뉴 | `이행관리` / `업무관리` / `시스템관리` | `업무 관리`(cmp) 하나에 둘을 담음 |
| 하위 | 이행 목록 → 이행 상세 / 업무 목록 | 이행 관리 / 문서 목록 |
| 기존 문서 메뉴 | *"별도 `기존 문서` 성격 메뉴가 있다면 제거하거나 업무목록에 통합"* | 기존 `업무문서` GNB 3메뉴 **병행 보존**(사용자 지시) |

- 명칭이 뒤집혀 있다 — 문서는 `이행관리`가 대메뉴이고 그 아래 `이행 목록`인데, 현행은 `업무 관리`가 대메뉴이고 그 아래 `이행 관리`다.
- 기존 업무문서 GNB 병행은 **사용자가 지시한 사항**이고 문서는 통합을 권한다.
- **결정(2026-08-18): 보류 — 현행 유지.** 메뉴 명칭·계층도 지금 구조(`업무 관리` > `이행 관리`·`문서 목록`)를 그대로 두고, 기존 `업무문서` GNB 3메뉴도 병행 보존한다. 통합·개명은 발주처 확인 뒤로 미룬다.

### G-5. 작년 문서 기능의 수위 (문서 §11)

문서: *"현재 HTML 의 `올해 문서로 등록` 기능을 **최종 스펙으로 간주하지 않는다**"* — 우선은 「지난해 실적 목록 + `[지난해 문서 보기]`」 수준을 권하고, 복사 지원 시에도 제목·수발신자·매핑 상속·첨부·결재문서 복제를 **각각 별도 검토**하라고 한다.

**결정(2026-08-18): 복사 범위는 «전부» — 구현 완료.** 문서 §11 이 "별도 검토"로 남긴 5개 항목을 아래와 같이 확정했다.

| 항목 | 결정 | 구현 |
|---|---|---|
| 제목 복사 | 복사(연도 치환) | 고정 — 끌 수 없다 |
| 수발신자 | 복사 | 기본 켜짐 |
| 보고일자 | 복사(연도 치환) | 기본 켜짐(종전 기본 꺼짐에서 변경) |
| **업무단계 매핑 상속** | **원본이 걸려 있던 전부** | 기본 켜짐. 종전에는 «지금 보고 있는 단계 1개»만 남겨 **나머지 연결이 끊겼다** — 참고문서 §7.3(한 문서가 여러 업무단계에 해당) 위반이었다. 실측: 11개 단계 원본이 11개 그대로 승계 |
| 첨부파일 | 복사 | 기본 켜짐. 단 **2025 원장은 메타데이터만 보유**해 복사할 첨부가 없다 — 화면이 그 사실을 밝힌다 |
| 결재문서 복제 | **하지 않는다** | 온나라 연동 전이라 원본이 없고, 결재는 새로 받아야 한다. 체크 항목 자체를 두지 않는다(없는 기능을 약속하지 않는다) |

체크박스는 남겨 두되 기본값을 전부 켰다 — 와이어프레임의 «불러올 항목» UI 를 지키면서 결정을 기본값에 반영한 형태다. 이어받기(문서 상세)도 같은 범위로 맞췄다.

### G-6. 업무 목록 컬럼 (문서 §8)

문서가 요구한 필드 중 현행에 없는 것: **업무유형**(G-1 종속) · **담당부서**(원장에 값이 없어 미노출 — 갭으로 이미 표기) · **증빙(첨부/결재문서)** 구분.

### G-7. 법령 관리 마스터 (문서 §13, Priority 3)

문서: 기존 법령 관리 화면을 그대로 쓰지 않고 **법령 ↔ 이행항목 ↔ 업무단계 ↔ 업무유형 ↔ 연결메뉴**를 잇는 마스터로 확장. 현행 `admin-law` 는 조문·매핑 검토 대장이라 이 축이 없다.

- ⚠ `DYLAW` 는 법제처 스냅샷 **생성물**이고 매핑 탭은 **편집 UI 를 두지 않기로 확정**돼 있다(CLAUDE.md §10). 이 확장은 그 원칙과 충돌할 수 있어 설계 전 확인이 필요하다.

### G-8. 이행 목록 필터 (문서 §5.3)

문서가 든 필터 6종 중 **부서**가 L1·L3 에는 없다(현행은 L2 에만). 다만 L1 은 군 단위라 부서 축이 성립하지 않으므로 **그대로 두는 것이 맞을 수 있다** — 문서의 필터 목록은 화면 공통 예시로 읽힌다.

# 5. 「누가 봐야 하나」 — 법령 근거로 알 수 있는 것과 없는 것 (2026-08-18 질의 답)

업무유형(§G-1)과 수행주체를 정할 때 **어디까지 법령 근거로 도출되고, 어디부터 담양군 확인인지**를 가른다. 이 구분을 하지 않으면 이미 데이터에 있는 값을 다시 물어보게 되고, 반대로 물어야 할 것을 우리가 임의로 정하게 된다(참고문서 §19 금지).

## 5-1. 이미 데이터에 있다 — 물을 필요 없음

`DYDOCT.STAGES` 168행이 단계마다 아래를 들고 있다.

| 필드 | 내용 | 종류 |
|---|---|---|
| `law` | 법령 근거 조문 | 단계마다 |
| `actor` | **이행주체** — 실제로 그 업무를 하는 역할 | **31종** |
| `target` | **적용대상** — 그 업무가 걸리는 범위 | **28종** |
| `legalCycle` / `opCycle` | 법정주기 / 재난안전과 운영주기 | |
| `timing` | 수행시점 조건 | |

`actor` 예: `경영책임자(군수) · 전담조직` · `관리감독자(실과단소장·읍면장) · 안전보건담당자` · `각 부서 관리감독자` · `발주부서 · 계약부서 · 전담조직` · `위탁 전문기관 · 점검 대상부서` …

→ **"누가 하는 업무인가"는 법령에서 이미 나와 있고 데이터에 들어 있다.** 화면도 `수행 주체` 열로 이미 보여준다.

## 5-2. 법령으로는 알 수 없다 — 우리가 채울 수 있음

**「시스템 어디서 수행하는가」**(참고문서 §16 `taskType`·`targetMenu`). 이건 법이 아니라 **우리 프로토타입에 그 기능이 있느냐**의 문제다. 법령을 아무리 읽어도 "위험성평가는 `rsk-list` 에서 한다"는 나오지 않는다.

→ 단계명·이행항목을 현행 메뉴와 대조하면 개발측이 초안을 만들 수 있다(§G-3 의 55개 후보가 그 대조 결과다). **다만 §19 가 임의 확정을 금지하므로 `확인 필요`는 남긴다.**

## 5-3. 담양군만 답할 수 있다 — 반드시 물어야 함

| 물어야 할 것 | 왜 |
|---|---|
| **실제 수행 부서** | `actor` 는 «관리감독자»·«시설 관리주체» 같은 **역할**이지 부서명이 아니다. 담양군 39개 과·사업소 중 어디인지는 조직·업무분장 자료가 있어야 한다(현행 `DYV2.ORG` 는 11개만 등록) |
| **비해당 여부** | 그 해에 그 부서에 해당하지 않는 업무(예: 건설공사 발주가 없는 부서) — 법이 아니라 **그 해 사업 유무**가 정한다 |
| **외부 수행 업무의 결과 형태** | 용역·외부기관 점검이 결과보고서로 오는지, 시스템에 등록되는지 |

## 5-4. 정리 — 확정 절차

```
법령 근거(있음) ─┬─ 무엇을 해야 하나 ........ 데이터에 있음(업무단계 168)
                 ├─ 왜 해야 하나 ............ 데이터에 있음(law)
                 ├─ 언제 해야 하나 .......... 데이터에 있음(주기·시점)
                 └─ 누가 해야 하나(역할) .... 데이터에 있음(actor 31종)

법령 밖 ─────────┬─ 어디서 수행하나 ......... 개발측 초안 + 확인 필요 표시
                 ├─ 어느 부서인가(실명) ..... 담양군 확인
                 └─ 해당/비해당 ............. 담양군 확인
```

# 6. 법령 관리 확장 — 무엇을 정해 주어야 하나 (2026-08-18 질의 답)

참고문서 §13 은 법령 관리를 «법적 의무와 시스템 업무를 잇는 마스터»로 확장하라고 한다. 그런데 현행 `admin-law` 는 **조문·매핑을 편집하지 않는 검토 대장**으로 확정돼 있어(CLAUDE.md §10) 그대로 늘리면 원칙이 깨진다. 그래서 **아래 3가지만 정해 주면** 나머지는 설계로 풀 수 있다.

## 결정 1. 이 표를 **어디서** 관리하나 (택 1)

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 원본 CSV + 재생성** (권장) | `taskType`·`targetMenu` 열을 원본 CSV 에 추가하고 `build-docs-seed.py` 로 재생성. 화면은 **조회만** | 기존 원칙(조문·매핑은 생성물, 편집 UI 없음) 유지 · 추적 가능 | 값을 바꾸려면 CSV 를 고쳐 재생성해야 한다(개발 작업) |
| B. 화면에서 편집 | 법령 관리에 업무유형·연결메뉴 편집 UI 신설 | 담당자가 직접 고침 | **CLAUDE.md §10 과 정면 충돌**(매핑 편집 UI 를 두지 않기로 확정) · 생성물과 수기값이 섞임 |
| C. 별도 매핑 파일 | `law-map` 처럼 사람 판단 기록 파일을 따로 둠 | 원칙 유지 + 갱신 쉬움 | 파일이 하나 더 늘고 두 곳을 봐야 함 |

→ **A 를 권한다.** 업무유형은 자주 바뀌는 값이 아니고, 바뀔 때는 «시스템에 기능이 생겼다»는 뜻이라 어차피 개발이 따라온다.

## 결정 2. 이 화면을 **누가** 보나 (택 1)

| 안 | 내용 |
|---|---|
| **A. 시스템 관리자만** (권장) | 현행 `admin-law` 안에 탭으로. 담당자는 이행 목록에서 결과만 본다 |
| B. 전담조직(재난안전과) 담당자도 | 매핑 검토를 실무가 함 |
| C. 전 부서 조회 | 우리 부서 업무가 어디에 걸리는지 누구나 확인 |

## 결정 3. **무엇까지** 보여주나

참고문서 §13 이 제시한 10개 열 중 **현행 데이터로 지금 채울 수 있는 것과 없는 것**이 갈린다.

| 열 | 현행 | 비고 |
|---|---|---|
| 법령명·조문 / 이행항목 / 업무단계 / 이행주기 / 수행조건 / 적용대상 / 수행주체 | **있음** | 그대로 표로 낼 수 있다 |
| 적용수준(L1/L2/L3) | **파생 추정** | 문자열 파생이라 확정 대상(§G-3 와 같은 갭) |
| **업무유형** | **없음** | 결정 1 로 채운다 |
| **연결메뉴** | **없음** | 결정 1 로 채운다 |

→ 즉 **결정 1만 정해지면 10개 열 중 8개는 즉시 채워진다.** 나머지 2개가 이번 확장의 실체다.

## 이 결정이 필요한 이유

§G-1(업무유형 3분기)·§G-2(단계별 완료 판정)·§G-3(매핑 대장)이 **전부 같은 두 열**(`taskType`·`targetMenu`)에 얹힌다. 이 열을 어디에 두느냐가 정해지지 않으면 세 작업 모두 시작할 수 없다.
