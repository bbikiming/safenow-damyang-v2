## 0. 클로드에게 바로 전달할 지시

당신은 공공기관 안전보건 업무 시스템을 다루는 시니어 프로덕트 디자이너이자 프론트엔드 엔지니어다. 기존 정적 HTML 프로토타입의 디자인 시스템과 전역 스크립트 구조를 유지하면서, `업무문서 > 이행 목록`과 `업무문서 > 업무 목록`을 아래 요구사항으로 전면 개편하라.

이 작업은 단순한 문구·CSS 변경이 아니다. 기존의 **PDCA 세트 중심 문서 분류**를, 첨부된 담양군 실데이터에 근거한 **법정 이행항목 → 하위 업무단계 → 증빙 문서** 구조로 바꾸는 정보구조 개편이다.

### 0-1. 작업 방식 — 바로 코딩하지 말 것

이 프로젝트는 프로토타입이지만 정적인 시안이 아니다. 먼저 사용자가 수행할 업무와 화면 상태를 기획하고, 그 기획을 화면 정의서에 반영한 다음, 기존 디자인 시스템으로 구현하고, 실제 브라우저에서 핵심 흐름을 끝까지 수행해 검수하라.

반드시 다음 순서를 지킨다.

1. **현행 조사** — 기존 화면·디자인 토큰·공용 컴포넌트·유사 흐름·데이터·권한을 확인한다.
2. **UX 기획** — 사용자 목표, 정보구조, 핵심 흐름, 상태 전이, 권한, 오류·빈 상태를 문서화한다.
3. **화면 정의서 정합화** — 구현 전에 SCR-DOC 정의서를 새 구조로 갱신한다.
4. **구현** — 승인된 디자인 시스템과 공용 컴포넌트를 재사용해 핵심 상호작용이 실제로 동작하게 만든다.
5. **기능 검수** — 담당자·관리자 시나리오, 데이터 집계, 저장·복원, 필터·딥링크를 검증한다.
6. **시각·UX·접근성 검수** — 브라우저 캡처와 실제 조작을 근거로 문제를 찾고 수정한다.
7. **회귀 검수·문서화** — 기존 메뉴·상세·공용 인프라가 깨지지 않았는지 확인하고 결과를 기록한다.

1~3단계 산출물 없이 화면 코드부터 수정하지 마라. 다만 아래 확정 정책을 다시 승인받기 위해 작업을 멈추지는 말고, 기존 디자인 시스템을 시각 기준으로 삼아 연속해서 진행하라. 확정 정책과 충돌하는 새로운 판단이 생길 때만 질문한다.

### 0-2. 이 작업의 완료 정의

완료는 HTML이 렌더되거나 버튼이 보이는 상태가 아니다. 다음이 모두 충족되어야 한다.

- 담당자가 이행항목을 찾고 → 파일을 올리고 → 업무단계를 여러 개 고르고 → 저장해 `진행중`으로 만드는 흐름이 동작한다.
- 관리자가 증빙을 확인하고 → `완료 처리`하여 → 카드의 완료 단계 수와 진행률이 바뀌는 흐름이 동작한다.
- 전년도 문서 단건·다건을 골라 → 첨부파일을 그대로 복사하거나 교체하고 → 새 연도 업무로 가져오는 흐름이 동작한다.
- 업무 목록에서 상세필터를 조합하고 → 문서 상세 또는 온나라 PDF를 확인하고 → 돌아왔을 때 검색 맥락이 유지된다.
- 주요 빈 상태·오류·중복·권한 없음·파일 누락·결과 0건 상태가 설계되고 동작한다.
- 기존 담양군 디자인 시스템과 공용 UX 패턴에서 이탈하지 않는다.
- 검수에서 발견된 중대·높음 이슈가 0건이며, 남은 제한사항은 근거와 함께 문서화된다.

### 0-3. 시각 기준

## 1. 이번 개편의 제품 목표

### 1-1. 이행 목록

사용자가 “법적으로 어떤 이행항목이 있고, 그 아래 업무단계별로 무엇이 진행됐는가”를 카드 목록에서 빠르게 확인하고, 증빙 파일을 올려 여러 업무단계에 연결하며 진행상태를 갱신할 수 있어야 한다.

### 1-2. 업무 목록

온나라 결재 상신 문서, 시스템 전자문서, 사용자가 올린 첨부 문서를 한곳에서 조회한다. 기존처럼 세트·PDCA를 보여주는 카드/그룹 화면이 아니라, 채용 사이트의 상세 검색처럼 조건을 세밀하게 조합할 수 있는 **평면 문서 목록**이어야 한다.

### 1-3. 공통 원칙

- 이행 목록은 **업무단계의 이행 현황을 보는 화면**이다.
- 업무 목록은 **문서 자체를 찾는 화면**이다.
- 두 화면은 같은 문서·매핑 데이터를 공유하지만, 화면의 기본 단위와 사용 목적은 다르다.
- 문서 1건은 여러 업무단계에 연결될 수 있고, 업무단계 1개에는 여러 문서가 연결될 수 있다.
- 기존 PDCA 세트는 이번 두 화면의 전면 UI와 신규 등록 흐름에서 제거한다.
- 과거 코드가 다른 화면에서 `DYSETLIST`를 참조할 수 있으므로 사용처를 확인하지 않고 파일이나 전역 API를 삭제하지 않는다.

## 3. 용어와 데이터 모델

기존의 `세트`, `PDCA`, `대메뉴` 중심 모델을 이번 화면의 주 모델로 재사용하지 말고 다음 엔터티를 명확히 나눈다.

### 3-1. ImplementationItem — 법정 이행항목

```js
{
  id: "IND-03",
  name: "유해·위험요인 확인·개선 절차 마련 및 위험성평가 실시",
  stageIds: ["IND-03-01", "IND-03-02", "..."],
  lawBases: ["산업안전보건법 제36조", "..."],
  targetLabels: ["전 부서(39개)"],
  actorLabels: ["관리감독자 ..."],
  hasOperatingCycle: true
}
```

### 3-2. WorkStage — 하위 업무단계

```js
{
  id: "IND-03-01",
  itemId: "IND-03",
  name: "위험성평가 실시계획 수립 및 시행",
  lawBasis: "산업안전보건법 제36조, ...",
  legalCycle: "정기평가 연 1회 이상",
  operatingCycle: "연 1회",
  timingCondition: "",
  target: "전 부서(39개)",
  actor: "관리감독자 ...",
  evidenceExample: "...",
  collectionStatus2025: "확인됨"
}
```

### 3-3. Document — 문서

```js
{
  id: "DOC-2025-0001",
  title: "2025 담양군 중대재해 예방 종합계획(안)",
  senderReceiver: "",
  reportDate: "2025-02-12",
  sourceType: "unknown", // onnara | electronic | upload | unknown
  workflowStatus: "unknown",
  approvalStatus: null,
  pdfUrl: null,
  attachments: [],
  createdBy: null,
  department: null,
  mappingStatus: "mapped" // mapped | unmapped
}
```

### 3-4. DocumentStageMap — 문서와 업무단계의 다대다 매핑

```js
{
  documentId: "DOC-2025-0001",
  itemId: "IND-01",
  stageId: "IND-01-01",
  year: 2025,
  source: "2025_csv"
}
```

### 3-5. StageProgress — 연도별 업무단계 진행상태

```js
{
  stageId: "IND-03-01",
  year: 2026,
  status: "not_started",
  evidenceDocumentIds: [],
  confirmedAt: null,
  confirmedBy: null,
  updatedAt: null,
  updatedBy: null
}
```

`StageProgress`는 문서 존재 여부와 완전히 같은 값이 아니다. 업무를 업로드하면 선택한 단계가 `in_progress`가 되고, 관리자 확인을 거쳐야 `complete`가 된다. 완료 확인된 단계만 이행항목 진행률의 분자에 포함한다.

### 3-6. Preset — 전년도 설정 재사용

```js
{
  id: "PRESET-2025-DOC-...",
  sourceYear: 2025,
  targetYear: 2026,

  stageIds: ["..."],
  attachmentMode: "copy", // copy | replace
  copiedAttachmentIds: ["FILE-2026-..."],
  createdAt: "...",
  createdBy: "..."
}
```

## 4. 메뉴·라우팅 변경

현재 `업무문서` 메뉴는 다음 세 항목을 가진다.

1. 기준문서함 — `docs-archive.html`
2. 업무 목록 — `docs-preset.html`
3. 이행 목록 — `docs-exec.html`

메뉴명과 URL은 딥링크 호환을 위해 유지하되, 2번과 3번의 본문은 전면 교체한다.

- `기준문서함`은 이번 범위에서 변경하지 않는다.
- `업무 목록`은 기존 세트/PDCA 그룹 테이블을 제거하고 평면 문서 검색 목록으로 교체한다.
- `이행 목록`은 기존 세트 카드에서 **법정 이행항목 카드**로 교체한다.
- `js/layout.js`의 “같은 데이터 — 격자 카드형 보기” 같은 낡은 설명을 새 목적에 맞게 고친다.
- 두 화면의 page title, subtitle, breadcrumb도 새 개념으로 수정한다.
- 기존 쿼리 `?ver=v1|v2`, `?menu=...`는 새 화면에서 의미가 없으므로 새 딥링크로 안전하게 치환하거나 무시하되 콘솔 오류가 나지 않게 한다.
- 새 딥링크는 최소 `?year=2026`, `?item=IND-03`, `?stage=IND-03-01`, `?source=upload`, `?status=...`를 지원한다.

## 5. 화면 A — 이행 목록 리뉴얼

### 5-1. 화면 기본 단위

- 카드 1개 = **법정 이행항목 1개**
- 카드 제목 = CSV의 `법정 이행항목명`
- 카드 안 목록 1행 = `하위 업무단계명`
- 업무단계 행 오른쪽 = 해당 연도·기간의 진행상태 태그
- 기존 PDCA 도트, P/D/C/A 라벨, PDCA 검증 배너, 세트명, 세트 진행률, 분류 버전 토글을 제거한다.

### 5-2. 권장 레이아웃

화면 상단 순서는 다음과 같다.

1. 페이지 제목·설명
2. 기준연도 선택(`2026` 기본)과 주요 액션
   - `전년도 프리셋 불러오기`
   - `업무 업로드`
3. 요약 영역
   - 이행항목 수
   - 업무단계 수
   - 완료/진행/미이행 수
   - 미분류 문서 수
4. 조회 조건
   - 이행항목명·업무단계명·코드 통합검색
   - 진행상태
   - 운영주기
   - 취합상태
   - 적용대상/이행주체
   - 적용 조건 초기화
5. 이행항목 카드 목록

카드는 데스크톱에서 2열, 좁은 화면에서 1열을 권장한다. 기존 3열 카드는 긴 업무단계명과 우측 상태 태그를 담기 어렵다. 카드 내부 단계가 많으면 처음에는 일부만 보여 주고 `업무단계 N개 모두 보기`로 펼친다. 펼침 상태는 같은 렌더 안에서 유지한다.

### 5-3. 카드 상세

카드 헤더:

- 이행항목코드
- 이행항목명
- 업무단계 수
- 법령근거 요약 또는 `법령 N건` 링크/인라인 펼침
- 조건부 항목이면 조건 표기

퍼센티지 바:

- **주기가 있는 이행항목에만** 렌더한다.
- 운영주기가 있는 업무단계가 하나도 없으면 바의 자리 자체를 만들지 않는다.
- `0%`도 숨기지 않는다.
- 산식은 `해당 이행항목의 완료 업무단계 수 ÷ 해당 이행항목의 전체 업무단계 수 × 100`이다.
- 운영주기 횟수를 연간 예상 건수로 환산하거나 월 12회·분기 4회처럼 분모를 늘리지 않는다.
- 이행항목에 주기가 있는지 여부는 퍼센티지 바의 **노출 조건**으로만 사용한다.
- 바 옆에 `완료 N / 전체 M개 단계`를 함께 표시해 퍼센트의 의미를 설명한다.
- `완료` 상태만 완료 수로 센다. `진행중`, `미이행`, `해당없음`은 분자에 포함하지 않는다.

업무단계 행:

- 업무단계코드
- 하위 업무단계명
- 운영주기 또는 수행시점조건
- 연결 문서 수
- 우측 진행상태 태그
- 행 선택 시 해당 업무단계로 필터된 `업무 목록`으로 이동
- 문서가 0건인 단계도 `연결 문서 0건`과 미이행 상태로 표시

### 5-4. 상태 표시

상태는 색만으로 구분하지 말고 항상 텍스트를 붙인다.

확정 상태:

- `미이행`
- `진행중`
- `완료`
- `해당없음`

`업무 업로드`로 문서와 업무단계를 연결하면 선택한 단계는 `진행중`이 된다. 관리자가 증빙을 확인해 `완료 처리`해야 `완료`가 된다. 완료된 업무의 파일이나 매핑을 담당자가 수정하면 완료를 유지하지 않고 `진행중`으로 되돌려 재확인을 받는다.

`기한초과`는 마감일/주기별 기준일 데이터가 있을 때만 파생한다. CSV에 없는 기한을 임의 생성하지 않는다.

### 5-5. 빈 상태·예외

- 검색 결과 0건: 적용된 필터 칩과 `조건 초기화` 제공
- 분류 기준에는 있으나 2025 문서가 없는 33개 단계: 정상적으로 표시
- 이행항목에 단계가 없는 비정상 데이터: 카드에 데이터 오류 안내
- 미분류 문서 35행: 별도 요약에서 업무 목록의 `미분류` 결과로 이동
- 로딩/오류/빈 상태가 카드 높이를 불필요하게 크게 만들지 않게 한다.

## 6. 이행 목록의 「업무 업로드」 흐름

### 6-1. 공통 원칙

- `업무 업로드`는 문서를 올리고 그 문서가 증빙하는 업무단계를 여러 개 선택하는 기능이다.
- 문서 1개를 여러 업무단계에 매핑할 수 있어야 한다.
- 선택한 모든 단계의 상위 이행항목을 자동으로 함께 알 수 있어야 한다.
- 기존 프로젝트의 단일 모달 불변식을 지킨다. 모달 위에 새 모달을 띄우지 않는다.
- `DYV2.openModal`, `DYV2.closeModal`, `DYV2.uploadDrop`, `DYV2.fileHint`, `DYV2.FILE_LIMITS`를 재사용한다.
- 단계가 많으므로 한 모달 안에서 본문을 교체하는 3단계 마법사로 구현한다.

### 6-2. STEP 1 — 문서·파일

입력:

- 파일 첨부: 다중 파일 가능, 공통 파일 제한 적용
- 문서명: 첫 파일명에서 확장자를 제외해 자동 채움, 수정 가능
- 보고일자
- 수발신자
- 담당부서/담당자: 기존 조직도 공통 컴포넌트 재사용
- 문서 출처: `직접 첨부` 기본
- 비고

검증:

- 파일 1개 이상
- 문서명
- 보고일자
- 담당부서·담당자 필수
- 동일 제목·수발신자·보고일자의 기존 문서가 있으면 중복 가능성을 경고하고 기존 문서에 파일을 추가할지 새 문서로 만들지 선택하게 한다.

### 6-3. STEP 2 — 업무단계 다중 선택

168개 단계를 하나의 긴 체크박스 목록이나 `select multiple`로 만들지 않는다.

권장 UI:

- 상단 통합검색: 이행항목명, 업무단계명, 코드, 법령근거
- 빠른 필터: 운영주기, 취합상태, 적용대상
- 본문: **이행항목별 아코디언**
  - 아코디언 헤더: 이행항목코드·명칭·하위 단계 수·현재 선택 수
  - 본문: 업무단계 체크박스 목록
  - 그룹 전체선택/해제 제공
- 우측 또는 하단 고정 선택 요약:
  - 선택한 업무단계 수
  - 선택한 이행항목 수
  - 선택 단계 칩/목록
  - 개별 제거와 전체 해제
- 검색 중에도 이미 선택한 단계는 유지
- 뒤로 갔다 돌아와도 선택 유지
- 선택 요약에서 긴 이름이 잘리지 않도록 툴팁이 아닌 실제 줄바꿈/확장 제공
- 체크박스와 라벨은 키보드로 조작 가능

선택 결과는 `stageIds[]`로 저장한다. 이행항목은 선택된 단계에서 파생하며 따로 중복 저장하지 않는다.

### 6-4. STEP 3 — 확인·상태 반영

요약:

- 문서명·파일
- 보고일자·담당자
- 선택한 이행항목/업무단계
- 각 업무단계의 변경 전 상태 → 저장 후 상태

저장:

- 문서 엔터티 1건 생성
- 파일 메타데이터 저장
- 선택한 단계 수만큼 `DocumentStageMap` 생성
- 해당 연도 `StageProgress` 갱신
- 저장 후 모달 닫기
- 이행 목록 카드·진행률·상태 태그 즉시 갱신
- 업무 목록에 새 문서 1건 표시
- 새로고침 후에도 유지

저장 직후 선택한 모든 업무단계는 `진행중`이 된다. 담당자는 자기 부서 문서를 수정할 수 있지만 `완료 처리`할 수 없다. 관리자의 `완료 처리` 이후에만 단계가 `완료`가 되고 이행항목 진행률이 올라간다. 상태 전이 함수는 한곳에 두고 UI 여러 곳에 하드코딩하지 않는다.

## 7. 전년도 프리셋

### 7-1. 목적

2026년 업무를 새로 만들 때 2025년에 사용한 업무단계 선택값을 다시 쓰고, 전년도 첨부파일을 새 연도로 복사해 그대로 사용하거나 새 파일로 교체할 수 있게 한다.

### 7-2. 진입

- 이행 목록 상단 `전년도 프리셋 불러오기`
- 업무 업로드 STEP 1의 `2025년 문서에서 가져오기`
- 두 진입점은 같은 프리셋 엔진과 UI를 재사용한다.

### 7-3. 확정 흐름

1. 원본연도와 대상연도 선택
2. 전년도 문서 검색/필터
   - 문서명
   - 이행항목
   - 업무단계
   - 주기
   - 보고일자
   - 수발신자
3. 한 건 또는 여러 건 선택
4. 가져올 값 확인
   - 문서명
   - 업무단계 매핑
   - 담당자
   - 첨부파일 처리 방식
5. 중복 검사 후 생성

단건과 다건을 서로 다른 화면으로 나누지 않는다. 하나의 문서 선택 목록에서 모두 처리한다.

- 체크박스를 한 건만 선택하면 하단 고정 영역에 `1건 가져오기`와 해당 문서의 빠른 설정만 표시한다.
- 두 건 이상 선택하면 `N건 선택`과 일괄 설정 막대를 표시한다.
- 선택한 문서는 필터나 페이지를 바꿔도 유지한다.
- 상단에 선택 건수, 하단에 선택 문서 요약을 지속적으로 보여 준다.
- `선택한 항목만 보기`, 개별 해제, 전체 해제를 제공한다.
- 다건 가져오기에서는 공통 옵션을 먼저 적용하고, 예외가 있는 문서만 행을 펼쳐 개별 수정한다.
- 모든 문서의 상세 폼을 한꺼번에 펼쳐 긴 화면을 만들지 않는다.

### 7-4. 복제 규칙

항상 복제:

- 업무단계 선택값(`stageIds[]`)
- 단계에서 파생되는 이행항목

사용자가 선택:

- 문서명 유지/연도 치환/직접 수정
- 담당자 유지/재지정
- 첨부파일 `그대로 사용`/ `파일 교체`

복제하지 않음:

- 전년도 진행상태
- 전년도 결재상태
- 전년도 보고일자
- 전년도 문서번호

같은 원본 문서에서 같은 대상연도로 이미 프리셋을 만든 경우 중복 경고를 제공한다. 다시 실행해도 조용히 중복 문서가 쌓이지 않도록 한다.

### 7-5. 첨부파일 복사 정책

- `그대로 사용`은 전년도 파일 ID를 계속 참조하는 방식이 아니다.
- 원본 파일 바이너리를 대상연도 저장소로 복사하고 **새 파일 ID**를 발급한다.
- 새 파일에는 `copiedFromFileId`, `sourceYear`, `targetYear`를 남겨 이력을 추적한다.
- 원본 파일과 원본 문서는 변경하지 않는다.
- 사용자는 복사 전에 전년도 첨부파일명·용량·등록일을 확인하고 미리보기/다운로드할 수 있다.
- `파일 교체`를 선택하면 전년도 파일 대신 새 파일을 첨부한다.
- 다중 첨부 문서는 파일별로 유지/교체를 선택할 수 있고, `모두 그대로 사용`, `모두 교체` 빠른 작업을 제공한다.
- 실제 서비스 API는 `copyAttachment(sourceFileId, targetYear)`처럼 복사 결과의 새 파일 ID를 반환해야 한다.
- 시연 환경은 제공되는 전년도 첨부파일 fixture를 사용해 복사 흐름을 재현한다. 파일이 누락된 항목은 깨진 다운로드 링크를 만들지 말고 `원본 파일 확인 필요`로 표시한다.

## 8. 화면 B — 업무 목록 전면 개편

### 8-1. 기본 단위

- 목록 1행 = 문서 1건
- 카드형, 세트형, PDCA 그룹형을 사용하지 않는다.
- 한 문서가 여러 업무단계에 매핑되어도 목록에는 1행만 표시한다.
- 업무단계는 `N개 단계` 요약으로 표시하고, 펼침/상세에서 전체를 본다.

### 8-2. 화면 구조

1. 페이지 제목·설명
2. 통합검색
3. 빠른 필터
4. 접을 수 있는 상세필터 패널
5. 적용 중인 필터 칩 + 전체 초기화
6. 결과 건수·정렬·페이지 크기
7. 문서 테이블
8. 페이지네이션

### 8-3. 통합검색

다음 필드를 부분일치 검색한다.

- 문서명
- 수발신자
- 담당자
- 담당부서
- 이행항목명
- 업무단계명
- 문서번호(값이 있는 경우)

입력 중 포커스와 커서를 잃지 않는다. 검색어는 URL 쿼리와 동기화해 새로고침·뒤로가기를 지원한다.

### 8-4. 빠른 필터

- 기준연도

  - 온나라 상신 PDF

### 8-7. 시연 상태와 실서비스 상태 분리

`문서 출처`와 `업무 흐름 상태`를 분리한다.

시연용 데이터는 CSV 문서 ID를 기반으로 **결정적으로** 출처와 상태를 배정한다. 같은 문서는 새로고침할 때마다 같은 상태를 가져야 하며 `Math.random()`을 사용하지 않는다.

시연 상태 도메인:

- 온나라: `결재중`, `결재완료`, `반려`
- 시스템 전자문서: `작성중`, `등록완료`, `확정`
- 직접 첨부: `검토대기`, `확인완료`

시연 레코드에는 `dataMode: "demo"`, `statusSource: "demo-seed"`를 저장해 실데이터와 구분한다. 문서 ID 해시 또는 고정 룩업 테이블로 출처·상태를 배정하고, 분포값과 생성 규칙을 데이터 파일 상단 주석에 기록한다.

실서비스에서는 화면이 시연 상태를 계속 사용하지 않는다. 온나라·전자문서·파일관리 각각의 어댑터가 다음 원천 필드를 제공한다.

```js
{
  sourceType: "onnara" | "electronic" | "upload",
  sourceDocumentId: "...",
  sourceStatusCode: "...",
  sourceStatusLabel: "...",
  statusUpdatedAt: "...",
  pdfFileId: null,
  attachmentIds: []
}
```

서로 다른 출처의 상태를 하나의 거짓된 공통 단계로 환산하지 않는다. 상세필터의 상태 옵션은 선택한 문서 출처에 따라 바뀐다. 화면 정의서에는 **시연 데이터 생성 규칙**과 **실서비스 원천 상태 계약**을 별도 절로 명시한다.

### 8-8. 온나라 PDF

- 프로그램에서 온나라로 상신한 문서가 PDF로 생성된 경우 문서 행과 상세에서 확인할 수 있어야 한다.
- PDF URL 또는 파일 ID가 실제로 있을 때만 `PDF 보기`를 활성화한다.
- 시연용 온나라 문서 일부에는 `시연용` 표시가 들어간 실제 로컬 PDF fixture를 연결해 목록→PDF 확인 흐름이 동작하게 한다.
- 시연 상태가 `온나라`라는 이유만으로 모든 문서에 가짜 PDF 링크를 만들지 않는다.
- PDF 미제공 문서는 버튼을 숨기거나 비활성 상태와 사유를 제공한다.
- 실서비스에서는 온나라 연계 어댑터가 반환한 `pdfFileId` 또는 안전한 다운로드 URL만 사용한다.

## 10. 상태·진행률 계산 모듈

상태와 진행률 계산을 렌더 함수마다 복제하지 않는다. 예를 들어 `js/document-progress.js` 같은 단일 모듈에 다음 함수를 둔다.

```js
statusOfStage(stageId, year)
progressOfItem(itemId, year)
completedStageCount(itemId, year)
totalStageCount(itemId)
hasOperatingCycle(itemId)
documentIdsOfStage(stageId, year)
itemIdsOfDocument(documentId)
stageIdsOfDocument(documentId)
```

`progressOfItem(itemId, year)`는 다음 계약을 지킨다.

```js
{
  visible: hasOperatingCycle(itemId),
  completed: completedStageCount(itemId, year),
  total: totalStageCount(itemId),
  percentage: Math.round(completed / total * 100)
}
```

완료 단계 수는 `status === "complete"`인 단계만 센다. 주기의 월·분기·반기 횟수는 퍼센트 분모에 곱하지 않는다. 전체 단계 수가 0인 비정상 항목은 0으로 나누지 말고 데이터 오류로 처리한다.

## 11. 기존 프로젝트 제약

### 11-1. 기술 구조

- 빌드 없는 정적 HTML + IIFE 전역 네임스페이스 구조를 유지한다.
- 새 프레임워크나 번들러를 도입하지 않는다.
- 기존 `DYV2`, `EDOC`, `DYREG`와 이름이 충돌하지 않게 한다.
- 새 데이터/로직의 전역 네임스페이스는 한두 개로 제한한다.
- 페이지마다 같은 상태 판정 로직을 복사하지 않는다.

### 11-2. UI

#### 11-2-1. 디자인 시스템 우선순위

UI 판단은 다음 순서의 기존 근거를 따른다.

1. `CLAUDE.md`의 MUST 규칙과 전역 UX 불변식
2. `docs/DESIGN-TOKENS.md`
3. `css/style.css`의 전역 토큰·기본 컴포넌트
4. `css/v2.css`의 v2 공용 컴포넌트·도메인 확장
5. 현재 동작 중인 유사 화면의 사용 패턴
6. SCR 화면 정의서

근거끼리 충돌하면 임의로 섞지 말고 현재 공용 컴포넌트와 MUST 규칙을 우선한다. 충돌 내용과 선택 이유를 UX 기획 문서에 기록한다.

#### 11-2-2. 구현 전 컴포넌트 재사용 조사

코드를 바꾸기 전에 다음 형식의 **재사용 매트릭스**를 작성한다.

| 필요한 UI/행동 | 기존 참조 파일·컴포넌트 | 그대로 재사용 | 공용 확장 | 신규 필요 | 판단 이유 |
|---|---|:--:|:--:|:--:|---|
| 예: 문서 상세필터 | `EDUFILTER.bar`, `.v2-toolbar` |  | ✓ |  | 필터 상태·초기화 패턴 재사용 |

최소 다음 기존 자산을 조사한다.

- 페이지 크롬·GNB·SNB·브레드크럼: `js/layout.js`
- 카드: `.card`, `.card-header`, `.card-body`, `.card-footer`
- 툴바·검색: `.v2-toolbar`, `.search-bar`, `.search-input`, `.search-submit`
- 필터: `EDUFILTER.bar`의 필드·결과건수·초기화·포커스 유지 패턴
- 테이블: `.table-figma`, `.table-compact`, `.table-nowrap`, 가로 스크롤 래퍼
- 버튼: `.btn`, `.btn-primary`, `.btn-secondary`, `.btn-outline`, `.btn-sm`
- 상태: `.chip-status`, `.chip-mini`, `DYV2.toneOf()`
- 진행률: `.progress`, `.progress-bar`
- 폼·오류: `.form-section`, `.form-field`, `.form-input`, `.form-select`, `.form-field-help`, `.form-field-error`
- 빈 상태: `.v2-empty`
- 모달: `DYV2.openModal()`, `DYV2.closeModal()`
- 업로드: `DYV2.FILE_LIMITS`, `DYV2.uploadDrop()`, `DYV2.fileHint()`
- 조직·담당자: `ORGPICK`, `DYV2.ORG`
- 토스트·접이식 안내: `DYV2.toast()`, `DYV2.notice()`
- 입력값 보존: 기존 `capture*()` 후 재렌더 패턴
- URL 상태: 기존 `URLSearchParams`·`history.replaceState` 패턴

이미 있는 컴포넌트와 같은 역할의 HTML/CSS/JS를 화면 전용으로 다시 만들지 않는다. 기존 컴포넌트가 80% 이상 맞으면 공용 확장을 우선한다. 신규 컴포넌트가 필요하면 “왜 기존 컴포넌트로 해결할 수 없는지”를 재사용 매트릭스에 남기고, 다른 화면도 쓸 수 있는 이름과 API로 만든다.

#### 11-2-3. 시각·상호작용 규칙

- 색상·폰트·간격·반경·그림자·z-index는 기존 토큰만 사용한다.
- 원시 브랜드 색상, 비캐논 글자 크기·굵기, 임의 반경·z-index를 하드코딩하지 않는다.
- 신규·수정 영역의 표현 스타일을 인라인 `style`에 흩뿌리지 말고 재사용 가능한 클래스에 둔다.
- 상태는 `DYV2.toneOf` 또는 공통 상태칩 규칙을 확장해 일관되게 표시한다.
- 상태·선택·오류를 색만으로 전달하지 않고 텍스트·아이콘·형태를 함께 사용한다.
- 아이콘은 기존 아이콘 체계를 사용하며 이모지·임시 SVG·CSS 그림을 UI 자산으로 쓰지 않는다.
- 한 시점에 모달은 하나만 열린다. 모달 안 추가 선택은 인라인 패널이나 같은 마법사의 단계 전환으로 처리한다.
- 필터는 페이지 안에서 펼치고, 업무단계 선택과 프리셋 가져오기는 같은 단일 모달의 단계형 흐름으로 처리한다.
- 업로드 제약 문구와 파일 검증 로직을 화면에서 복제하지 않는다.
- 목록 밀도는 기존 공공업무 화면 수준을 유지한다. 지나치게 큰 카드·과도한 여백·장식성 일러스트로 실제 데이터가 첫 화면 아래로 밀리지 않게 한다.
- 긴 한국어 문서명·법령명·업무단계명이 잘리지 않도록 가변 높이·줄바꿈·상세 펼침을 설계한다. 핵심 정보를 툴팁에만 숨기지 않는다.
- 클릭 가능한 요소는 hover만으로 구분하지 말고 기본 상태에서도 행동 가능성이 드러나야 한다.
- 버튼 라벨은 동사형으로 쓰고, 저장·완료 처리·삭제처럼 결과가 다른 행동을 모두 `확인`으로 뭉뚱그리지 않는다.

#### 11-2-4. 프로토타입 충실도

프로토타입이라는 이유로 핵심 CTA를 토스트만 띄우는 가짜 동작으로 만들지 않는다.

- 업로드, 단계 다중 선택, 저장, 관리자 완료 처리, 프리셋 단건·다건 가져오기, 파일 복사/교체, 필터, 정렬, 페이지 이동, 상세/PDF 진입은 실제 상태를 변경하거나 실제 화면으로 이동해야 한다.
- 새로고침 후에도 필요한 시연 상태가 유지되어야 한다.
- 취소·이전·닫기 후 데이터 보존/폐기 규칙을 흐름마다 일관되게 적용한다.
- 실제 연동이 범위 밖인 온나라·스토리지만 결정적 시연 어댑터로 대체한다. 시연값과 실서비스 계약을 같은 객체로 위장하지 않는다.
- 보조 기능이 시각 전용이면 사용자에게 클릭 가능한 것처럼 보이게 만들지 않는다.
- 발표자가 설명하지 않아도 주요 흐름을 이해할 수 있도록 현실적인 데이터·상태·성공·실패 피드백을 제공한다.

- `SCR-DOC-003`: 이행항목 카드, 완료 단계 수 기반 진행률, 단계별 상태, 관리자 완료 확인
- `SCR-DOC-007`: 파일 업로드, 업무단계 다중 선택, 단건/다건 프리셋, 새 연도 파일 복사, 권한별 액션
- `SCR-DOC-004~006`: 기존 문서 상세를 계속 사용한다면 새 문서 출처·상태·업무단계 매핑·첨부/PDF·권한 정책과 정합화
- `docs/screen-definitions/00_화면목록.md`
- `docs/README.md`

정의서의 화면명과 본문에 `세트 리스트`, `세트 격자 카드`, `PDCA 단계 선택` 같은 폐기 개념을 남기지 않는다. 파일명을 바꾸면 화면 ID는 유지하고 `00_화면목록.md`, 문서 링크, 생성 스크립트 입력 경로를 함께 갱신한다.

정의서 수정 후 `docs/screen-definitions/_build-data.py`를 실행해 `js/screen-defs-data.js`를 재생성한다. 기존 현행 기획 문서가 새 구조와 충돌하면 삭제하지 말고 `docs/archive/`로 옮기고 대체 사유를 기록한다.

### 11-4. 권한과 상태 변경 정책

기존 `DYROLE`과 메뉴·권한 체계를 사용하며 화면 안에 별도 역할 체계를 만들지 않는다.

| 행위 | 담당자 | 관리자 |
|---|---|---|
| 업무 목록·이행 목록 조회 | 메뉴 권한 및 자기 부서 범위 | 전체 범위 |
| 업무 업로드 | 자기 부서 가능 | 전체 부서 가능 |
| 진행중 문서·파일·단계 매핑 수정 | 자기 부서 가능 | 전체 가능 |
| 업무단계 완료 확인 | 불가 | 가능 |
| 완료 문서 수정 | 수정 시 진행중으로 환원 후 재확인 | 가능, 변경 이력 필수 |
| 문서·첨부·매핑 삭제 | 불가 | 가능 |
| 프리셋 가져오기 | 자기 부서 가능 | 전체 부서 가능 |

- 담당자가 완료된 업무의 파일이나 업무단계 매핑을 바꾸면 해당 단계는 자동으로 `진행중`으로 되돌아간다.
- 관리자의 완료 처리에는 확인자·확인일시를 남긴다.
- 삭제는 대상 문서명·영향받는 업무단계를 보여 주는 확인 절차를 거치며 변경 이력을 남긴다.
- 화면 정의서의 권한 절은 공통 권한정의와 메뉴 권한을 참조하고, 상태 전이 조건은 각 화면 §6 정책에 명시한다.

## 12. UX 기획·구현·검수 작업 게이트

각 게이트의 산출물과 통과 조건을 충족한 뒤 다음 단계로 진행한다. 체크리스트를 썼다는 사실만으로 통과 처리하지 말고 파일·브라우저 상태·검증값으로 증명한다.

### GATE 0. 현행 UX·디자인 시스템 베이스라인

목표: 무엇을 보존하고 무엇을 교체하는지 근거를 만든다.

수행:

1. 로컬 서버로 현행 프로토타입을 실행한다.
2. 현재 `docs-exec.html`, `docs-preset.html`, `doc-detail.html`을 연다.
3. 공용 패턴이 잘 적용된 유사 화면에서 다음을 추가 확인한다.
   - 고밀도 목록·필터
   - 카드와 진행률
   - 단계형 모달
   - 실제 파일 업로드
   - 조직도 선택
   - 권한별 액션
4. 각 화면을 데스크톱 기준 동일 뷰포트로 캡처하고 저장한 파일을 다시 열어 정상 캡처인지 확인한다.
5. §11-2의 컴포넌트 재사용 매트릭스를 작성한다.
6. 현행 문제를 다음 렌즈로 짧게 감사한다.
   - 업무 진입점과 발견 가능성
   - 정보구조와 용어
   - 흐름의 마찰과 불필요한 선택
   - 시각적 위계와 정보 밀도
   - 기본·빈·오류 상태
   - UX 문구와 CTA
   - 화면 간 일관성
   - 키보드·포커스·라벨·대비·반응형 위험

산출물:

- 베이스라인 캡처
- `docs/planning/기획-업무문서-이행목록-업무목록-UX설계-v1.md`의 `현행 진단`
- 컴포넌트 재사용 매트릭스

통과 조건:

- 새로 만들려는 UI마다 기존 재사용 후보가 확인되어 있다.
- 현행에서 유지할 디자인 언어와 폐기할 PDCA/세트 구조가 구분되어 있다.
- 캡처하지 못한 화면이나 상태는 이유가 기록되어 있다.

### GATE 1. 사용자·업무·정보구조 기획

목표: 화면 배치보다 먼저 사용자의 실제 업무를 정의한다.

기본 사용자:

- **담당자** — 자기 부서의 이행 현황 확인, 파일 업로드, 업무단계 매핑, 전년도 프리셋 가져오기, 진행중 자료 수정
- **관리자** — 전체 현황 확인, 증빙 검토, 완료 처리, 완료 후 변경 이력 확인, 문서 삭제

반드시 다음 핵심 시나리오를 사용자 흐름으로 작성한다.

1. 담당자가 이행항목과 미이행 업무단계를 찾는다.
2. 파일을 올리고 168개 단계 중 관련 단계 여러 개를 선택해 저장한다.
3. 관리자가 진행중 증빙을 확인하고 완료 처리한다.
4. 담당자가 완료된 문서를 수정하고 단계가 진행중으로 되돌아가는 것을 확인한다.
5. 전년도 문서 1건을 가져와 파일을 그대로 복사한다.
6. 전년도 문서 여러 건을 골라 공통 옵션을 적용하고 일부 파일만 교체한다.
7. 업무 목록에서 상세필터를 조합해 온나라·전자문서·직접 첨부 문서를 찾는다.
8. 온나라 PDF 또는 문서 상세를 확인하고 목록으로 돌아온다.
9. 관리자가 미분류·중복·원본 파일 누락 문서를 교정한다.

각 흐름에는 다음을 포함한다.

- 시작 위치와 진입 CTA
- 사용자가 현재 위치와 다음 행동을 이해하는 단서
- 필수·선택 입력
- 기본값과 자동 채움
- 이전·취소·닫기·재진입 시 데이터 유지 규칙
- 성공 피드백과 다음 행동
- 로딩·빈 결과·입력 오류·중복·권한 없음·파일 누락·부분 실패 처리
- 담당자/관리자 차이
- URL·새로고침·뒤로가기 동작

정보구조 산출물:

- 이행 목록과 업무 목록의 역할 구분
- 카드·행·문서 상세 간 계층
- 상세필터 분류와 종속 관계
- 업무단계 선택 구조
- 상태 용어와 출처별 상태 체계
- 데스크톱·태블릿·좁은 화면의 정보 우선순위

통과 조건:

- 한 기능이 어느 화면 소관인지 중복 없이 정해져 있다.
- 정상 경로뿐 아니라 실패·빈 상태·권한 차이까지 정의되어 있다.
- 확정된 6개 정책과 충돌하는 흐름이 없다.

한 번에 전 화면을 갈아엎지 말고 다음 순서로 구현하고 각 단계가 동작하는지 확인한다.

## 13. 수용 기준

### 13-1. 이행 목록

1. 카드 제목이 법정 이행항목명이며 총 78개 항목을 데이터에서 구성한다.
2. 카드 안에 168개 업무단계가 중복·누락 없이 배치된다.
3. PDCA, 세트명, P/D/C/A UI가 전면에 남아 있지 않다.
4. 운영주기가 없는 31개 이행항목에는 퍼센티지 바가 없다.
5. 운영주기가 있는 항목의 바는 `완료 업무단계 수 ÷ 전체 업무단계 수`로 계산되고 `완료 N / 전체 M개 단계`를 함께 보인다.
6. 업무단계마다 우측에 상태 태그가 있다.
7. 2025 문서가 없는 33개 단계도 표시된다.
8. 단계 행을 누르면 해당 단계로 필터된 업무 목록으로 이동한다.
9. 업로드 직후 진행중 단계는 분자에 포함되지 않고 관리자 확인으로 완료된 단계만 진행률에 반영된다.

### 13-2. 업로드

1. 파일을 1개 이상 첨부할 수 있다.
2. 168개 업무단계를 검색·그룹·다중 선택할 수 있다.
3. 검색/아코디언 조작 중에도 선택값이 유지된다.
4. 한 문서를 여러 업무단계에 저장한다.
5. 저장 후 이행 목록 상태와 업무 목록 문서가 즉시 갱신된다.
6. 새로고침 후에도 프로토타입 저장값이 유지된다.
7. 중복 문서 가능성을 경고한다.
8. 단일 모달 규칙과 파일 제한 공통 헬퍼를 지킨다.
9. 업로드 직후 선택한 단계는 `진행중`이며 담당자 화면에는 완료 처리 액션이 없다.
10. 관리자가 완료 처리하면 확인자·확인일시가 저장되고 카드 진행률이 갱신된다.

### 13-3. 프리셋

1. 2025 문서의 업무단계 매핑을 2026 문서에 재사용할 수 있다.
2. 단건과 다건 선택을 같은 흐름에서 처리할 수 있다.
3. 전년도 상태·날짜·문서번호를 그대로 복제하지 않는다.
4. 한 건 선택 시 빠른 설정, 여러 건 선택 시 일괄 작업 막대가 나타나며 필터·페이지 이동 중에도 선택이 유지된다.
5. `그대로 사용`한 파일은 새 연도 저장소에 복사되어 새 파일 ID를 가지며 전년도 원본과 ID를 공유하지 않는다.
6. 문서별·파일별로 그대로 사용 또는 교체를 선택할 수 있다.
7. 같은 프리셋을 재실행해도 무경고 중복이 생기지 않는다.

### 13-4. 업무 목록

1. 4,082 매핑행을 4,082개의 문서행으로 잘못 표시하지 않는다.
2. 복합키 기준 3,830개 문서 엔터티를 1행씩 표시한다.
3. 한 문서의 여러 단계 매핑은 한 행 안에서 요약된다.
4. 문서 출처·상태·연도·기간·이행항목·업무단계·부서·수발신자·첨부·매핑 상태를 조합 검색할 수 있다.
5. 적용 필터가 칩으로 보이고 개별/전체 해제할 수 있다.
6. 미분류 35행을 조회할 수 있다.
7. 시연 데이터의 출처·상태는 문서 ID 기반 고정값이며 새로고침해도 바뀌지 않는다.
8. 시연 상태와 실서비스 원천 상태 어댑터가 데이터 모델·화면 정의서에서 분리되어 있다.
9. 실제 PDF 또는 시연용 로컬 PDF fixture가 연결된 온나라 문서만 PDF 보기 동작이 활성화된다.
10. 문서 상세로 이동한 뒤 돌아와도 필터와 페이지가 유지된다.

### 13-5. 품질

1. 콘솔 오류가 없다.
2. 키보드로 검색·필터·아코디언·체크박스·마법사를 조작할 수 있다.
3. 1280·1024·768·560px 화면과 확대 상태에서 핵심 정보가 잘리거나 겹치지 않는다.
4. 검색 입력 중 리렌더로 포커스·커서가 사라지지 않는다.
5. 기존 기준문서함과 다른 주요 메뉴 링크가 깨지지 않는다.
6. 화면 정의서와 구현이 일치한다.
7. 담당자는 자기 부서 업로드·수정만, 관리자는 전체 완료 확인·삭제를 수행한다.
8. 완료된 업무를 수정하면 진행중으로 환원되고 재확인 이력이 남는다.
9. 컴포넌트 재사용 매트릭스가 작성되고, 기존 버튼·필터·테이블·상태칩·모달·업로드·조직도와 중복 구현이 없다.
10. UX 설계 문서의 핵심 시나리오와 요구사항 추적표가 화면 정의서·구현·검수 결과에 연결된다.
11. 현행 베이스라인과 구현 결과 캡처가 저장·검사되었고, 디자인 시스템 이탈이 없다.
12. 중대·높음 검수 이슈가 0건이며 모든 FT 시나리오가 통과한다.

## 14. 발주처 확정 결정사항

### D-01. 파일 업로드와 상태 전이

- 파일 업로드와 업무단계 매핑 직후: `진행중`
- 관리자 확인 후: `완료`
- 완료 업무 수정 후: `진행중`으로 환원하고 재확인
- 완료 진행률에는 관리자 확인을 마친 단계만 포함

### D-02. 이행항목 퍼센티지

- 노출 대상: 운영주기가 하나라도 있는 이행항목
- 분자: 해당 연도 `완료` 업무단계 수
- 분모: 해당 이행항목의 전체 업무단계 수
- 표시: `완료 N / 전체 M개 단계`
- 월·분기·반기 등 주기 횟수는 분모에 곱하지 않음

### D-03. 프리셋 범위와 UX

- 전년도 문서 1건과 여러 건 가져오기 모두 지원
- 하나의 선택 화면에서 단건·다건을 처리
- 한 건이면 빠른 설정, 여러 건이면 일괄 작업 막대 제공
- 선택 상태는 검색·필터·페이지 이동 중 유지
- 공통 옵션 일괄 적용 후 예외 문서만 개별 수정

### D-04. 전년도 첨부파일

- 전년도 첨부파일을 사용자에게 제공
- `그대로 사용` 또는 `파일 교체` 선택
- 그대로 사용하면 대상연도 저장소로 물리 복사하고 새 파일 ID 발급
- 전년도 원본 파일·원본 문서는 불변
- 다중 첨부는 파일별 유지/교체 가능

### D-05. 시연 상태와 실제 기획

- 프로토타입에는 시연용 가상 문서 출처·상태를 제공
- 시연값은 문서 ID 기반으로 고정 생성하고 `demo` 데이터임을 내부 메타데이터로 구분
- 실서비스는 온나라·전자문서·파일관리 원천 상태 어댑터를 사용
- 화면 정의서에는 시연 생성 규칙과 실서비스 상태 계약을 각각 명시
- 시연용 온나라 문서 일부는 실제 로컬 PDF fixture로 PDF 확인 흐름 제공

### D-06. 권한

- 담당자: 자기 부서 업무 업로드·수정·프리셋 가져오기
- 관리자: 전체 범위 조회·수정·완료 확인·삭제
- 담당자는 완료 처리와 삭제 불가
- 기존 `DYROLE`과 메뉴 권한 체계를 재사용
