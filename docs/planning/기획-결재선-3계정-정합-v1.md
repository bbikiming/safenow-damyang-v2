## 1. 확정된 것 (발주처 입력)

1. 상신은 **결재선 전체를 한 번에** 온나라로 보낸다(호출기안).
2. 그래서 **기안·검토·결재는 서로 다른 계정**이어야 한다. 같은 계정이 두 단계에 들어가면 결재선이 성립하지 않는다.
3. 전체 흐름을 확인하려면 **기안자 1(공용) · 검토자 1 · 결재자 1** 최소 3계정이 필요하다.
4. 도메인별 결재선(전달받은 정리):

| 도메인 | 전달된 결재선 | 단계 수 |
|---|---|:--:|
| 위험성평가 공문 | 기안 → 검토(팀장) → 결재(부서장) | 3 |
| 안전보건교육 공문 | 기안 → 검토 → 결재 | 3 |
| 예산총괄표 | 기안 → 팀장 → 과장 → 부군수 | 4 |
| 경영방침 | 기안 → 승인 | 2 |
| 평가 결재 | 기안 → 승인 | 2 |
| 도급 점검표 결재 | 기안 → 승인 | 2 |

> ⚠ **4번 표는 현행 코드와 세 곳이 어긋났다** — 경영방침·평가·도급이 코드에서는 2단계가 아니었다(§3 P-2). 계정 수가 여기서 갈려 §8 에서 되물었다.

5. **2026-08-27 확정 — 전 도메인을 「기안 → 검토 → 결재」 3단계로 통일한다.**

| 도메인 | 통일 전 | 통일 후 |
|---|---|---|
| 위험성평가 공문 · 안전보건교육 공문 | 기안 → 검토 → 결재 | 그대로 |
| 예산총괄표 | 기안 → 팀장 → 과장 → 부군수 (4) | **기안 → 검토 → 결재** |
| 경영방침 · 평가 · 도급 점검표 | 문구만 있고 데이터 없음 | **기안 → 검토 → 결재** |

통일하는 이유는 **담당자가 도메인마다 다른 결재선을 외우지 않게** 하기 위해서다. 결재권자를 코드에
고정하지 않는 원칙은 그대로이므로, 3단계는 **기본 형태**이고 위임전결규칙상 검토가 더 필요하면
그 건에서 단계를 늘린다(늘린 만큼 계정이 더 든다). → **필요 계정 3개**로 확정된다(§7).

## 3. 3계정 구조가 깨지는 지점

### P-1. 중복 검증이 없다 (최우선)

- `js/doc-flow.js:381` — 상신 직전 검사는 **빈칸 검사 하나뿐**이다.
  ```
  var blank = L.filter(function (s) { return !s.name; }).length;
  ```
- `js/rsk-doc.js:509` — 동일.
- `ORGPICK.toggle(…, 'member', …)` 는 **조직도 전원**을 후보로 준다. 기안자 본인도 목록에 있다.
- `addStep()` 은 단계를 무제한 추가하고, 같은 사람을 여러 단계에 넣어도 막지 않는다.

→ **기안자 = 결재자**, **검토자 = 결재자** 상태로 상신이 성립한다. 온나라에 그대로 넘기면 그 자리에서 거절된다.

### P-2. 도메인 3곳은 단계 수 자체가 전달 내용과 다르다

| 도메인 | 전달 | 코드 | 어긋남 |
|---|---|---|---|
| 경영방침 | 기안 → 승인 (2) | 팝업 4 / 이력 3 | 화면 안에서도 불일치 |
| 평가 결재 | 기안 → 승인 (2) | 평가자 → 부서장(검토) → 군수(결재) (3) | `evl-eval.html:1072·1098` |
| 도급 점검표 | 기안 → 승인 (2) | 팝업 4 (전자문서 공통 문구) | `edoc.js:79` |

### P-3. 결재선에 계정 식별자(uid)가 없다

`ORGPICK` `member` 모드는 **표시 문자열**만 돌려준다(`org-pick.js:10·90`).
```
onpick('부서 · 역할 / 이름')
```
`doc-flow.js` `parseMember()` 가 이를 `{role, name}` 으로 쪼개 저장한다. **uid 가 버려진다.**

- 동명이인·개명에 견디지 못한다.
- 온나라 결재선 payload 의 계정 키를 만들 수 없다.
- 「기안자 ≠ 결재자」를 **이름 문자열로** 비교하게 된다.

※ 이미 답은 있다 — `ORGPICK` 에는 uid 를 돌려주는 `memberUid` 모드가 있고(`org-pick.js:104`) 업무 배정이 그것을 쓴다. 결재선만 옛 모드에 남아 있다.

### P-4. 검토자 계정이 페르소나에 없다

기본 기안자는 **박안전**(`u_jjt2`, 재난안전과 중대재해팀)이고, 그 부서의 기본 결재선은 다음과 같다.

| 단계 | 사람 | uid | 페르소나 |
|---|---|---|:--:|
| 기안 | 박안전 | `u_jjt2` | ✅ `staff` |
| 검토 | 김중대 (중대재해팀장) | `u_jjt1` | ❌ **없음** |
| 결재 | 홍길동 (재난안전과장) | `u_safe1` | ✅ `safety` |

부서별로 보면 **3계정이 다 갖춰진 부서는 물순환사업소 하나뿐**이다.

| 부서 | 기안 | 검토 | 결재 | 3계정 |
|---|---|---|---|:--:|
| 재난안전과 | 박안전 ✅ | 김중대 ❌ | 홍길동 ✅ | ✖ |
| 물순환사업소 | 하정수 ✅ | 문정수 ✅ | 오순환 ✅ | **✔** |
| 환경과 | 정환경 ✅ | 조환경 ❌ | 차환경 ❌ | ✖ |

### P-5. 결재선 기본값이 11개 부서 중 4곳에서만 2단계로 나온다

`doc-flow.js:71~86` 의 파생 규칙은 `/팀장/` 과 `/(과장|소장|실장)/` 이다.

| 결과 | 부서 | 수 |
|---|---|:--:|
| 검토+결재 2단계 (정상) | 재난안전과 · 환경과 · 건설과 · 물순환사업소 | 4 |
| 결재 1단계 (검토 없음) | 기획예산실 · 회계과 · 보건소 · 공공시설사업소 | 4 |
| 전부 미지정 | 문화체육과 · 재무과 · **담양읍** | 3 |

- 담양읍이 비는 이유는 정규식이 **`읍장`·`면장`을 잡지 못하기** 때문이다.
- 문화체육과·재무과는 조직도에 주무관만 있어 팀장·과장이 없다.

**골격이 동결본보다 좁다** — `rsk-doc.js:54` 는 `/(과장|소장|실장|국장|읍장|면장)$/` 로 더 넓고, head 를 못 찾아도 `{role:'과장', name:''}` 자리를 남긴다. 골격을 뽑아낼 때 **규칙이 좁아진 채로 복제**됐다.

### P-6. 군수·부군수·국장을 결재선에서 고를 수 없다

`memberTree()`(`org-pick.js:79`)는 `DYV2.orgFlat()` 을 **옵션 없이** 부른다. `orgFlat` 은 `includeLeadership` 을 줘야만 `post`·`bureau` 노드를 넣는다(`common.js:240`). 그 옵션은 **저장소 전체에서 한 번도 쓰이지 않는다.**

→ 김담양(군수)·이부군(부군수)·박행정·정산업(국장)이 결재선 조직도에 **없다.** 예산총괄표의 부군수 결재, 인력평가의 군수 결재를 실제 사람으로 지정할 수 없다.

### P-7. 최소 단계가 1이라 「검토 없는 결재선」이 만들어진다

`doc-flow.js:123` / `rsk-doc.js` — `L.length <= 1` 일 때만 삭제를 막는다. 3단계 도메인에서도 검토 단계를 지우고 상신할 수 있다.

### P-8. 결재자 계층이 조작 권한 축에 막혀 있다

`DYROLE.canAct()`(`layout.js:147`)는 `tier !== 'staff'` 면 **무조건 false** 다. 그런데 결재자는 정확히 과장·소장(`super`)·군수(`head`)다.

- 지금은 결재 처리 행위가 시스템에 없어 충돌이 드러나지 않는다.
- 결재선 **확인·회신 등록** 같은 행위를 붙이는 순간 막힌다.
- 배정(`assignKind`)이 세 번째 축으로 신설된 것과 같은 근거로, **네 번째 축**이 필요하다(§4 D-5).

### P-9. 조회 범위에 「내가 결재선에 올라간 문서」가 없다

`DYROLE.scope()` 는 소속 부서만 본다. 타 부서 문서의 결재자로 지정되면 그 문서가 보이지 않는다. 지금은 결재선이 늘 기안자 부서 안이라 드러나지 않지만, 부군수·군수 결재가 붙는 순간 전부 범위 밖이다.

### P-10. 예산의 「모의 수신」은 3계정 구조와 모순이다

`bgt.js:898~900` — 상신자 본인 화면에 `[중간 승인 수신]`·`[최종 승인 수신]`·`[반려 수신]` 버튼이 있다. 기안자가 자기 결재를 승인하는 모양이라, 계정을 나누는 이 결정과 정면으로 어긋난다.

## 4. 기획 결정

### D-1. 결재선은 `DYDOC` 골격 하나로 모은다 — 단, 예외 둘을 명시한다

- **모으는 대상**: 예산총괄표(현 #3) · 전자문서 공통(#4) · 인력평가(#5).
- **예외 1 — 위험성평가(`DYRSKDOC`)는 동결 유지.** 화면 무변경이 전제이고(CLAUDE.md §7-1), 이번 변경도 **검증 규칙만** 동일하게 심는다. 지면·문구·순서는 손대지 않는다.
- **예외 2 — 전자문서 공통(`edoc.js`)은 «표시 문구» 를 지우고 결재선 «데이터» 로 바꾼다.** 지금은 팝업 텍스트뿐이라 고칠 데이터가 없다.

### D-2. 결재선 원소는 `{uid, name, role, deptId, deptName}` 으로 저장한다

- 선택은 `ORGPICK` **`memberUid` 모드**로 받는다(`member` 모드는 결재선에서 폐기).
- 판정·중복 검사·온나라 payload 는 전부 **uid** 로 한다. `name` 은 표시용이다.
- 기존 저장분(`{role,name}` 만 있는 sessionStorage)은 uid 를 못 찾으면 **미지정으로 되돌린다** — 이름으로 추정해 채우면 동명이인에서 엉뚱한 계정으로 상신된다.

### D-3. 중복 금지는 **데이터 계층 한 곳**에서 막는다

화면마다 검사하지 않는다(교육 `addEnroll` 중복 방지와 같은 근거 — 호출부가 여럿이면 반드시 빠뜨리는 곳이 생긴다).

- `DYDOC.validateLine(line, drafterUid)` 하나가 판정하고 `{ok, why}` 를 돌려준다.
- 검사 4가지: ① 미지정 단계 ② 기안자가 결재선에 포함 ③ 결재선 내 uid 중복 ④ 도메인 최소 단계 미달.
- **막는 자리는 셋이다** — `confirmSend`(상신 확인) · `send`(상신) 를 하드 게이트로 두고, 미리보기의 `[온나라로 결재 상신]` 버튼은 **내지 않고 사유로 바꾼다.** 버튼만 잠그면 전역 호출로 뚫리므로 세 곳 모두 같은 판정을 부른다(§4 교육 `canDraft` 선례).
- **미리보기 자체는 막지 않는다** — 결재선이 틀렸다고 문서를 못 보게 할 이유가 없다. 담당자는 본문을 확인하고 `[← 수정]` 으로 돌아간다.
- **알리는 자리는 둘이다** — ① 기안 폼의 결재선 아래에 **지금 무엇이 걸렸는지** 상시 표시(다 쓰고 나서야 알리면 처음부터 다시 확인해야 한다) ② 조직도에서 **이미 쓴 사람을 선택 불가로** 표시하고 이유를 그 행에 붙인다(`기안자` / `결재 지정됨`). 상신 직전에야 거절하면 조직도를 다시 열어야 한다.

### D-4. 단계 수는 골격이 정하고, 도메인은 예외일 때만 선언한다

전 도메인이 같아졌으므로(§1-5) **기본값이 정답**이고 도메인은 아무것도 선언하지 않는다.

```
lineShape: { min: 2, max: 4 }   // 기안 제외 단계 수 — 생략 시 이 값
```
- `min: 2` 가 곧 「기안 → 검토 → 결재」다. **검토 없는 결재선을 막는 것이 이 값의 전부**다.
- `max: 4` 는 위임전결규칙상 검토가 늘 수 있는 여지다. 무한히 열지 않는 이유는 **한 단계가 곧 계정 하나**이기 때문이다 — 늘리면 그만큼 계정이 더 필요하다는 사실이 화면에 드러나야 한다.
- `delStep()` 은 `min` 아래로 못 내려가고 `addStep()` 은 `max` 위로 못 올라간다. **min 일 때는 삭제 버튼 자체를 내지 않는다** — 누르면 거절하는 버튼을 남기지 않는다.
- `addStep()` 이 늘리는 것은 **검토**다(결재는 늘 마지막). 종전에는 끝에 붙여서 결재 단계가 검토로 밀렸다.
- 다르게 쓰려는 도메인은 **그 위임전결 근거를 정의서 §6 에 적는다.** 근거 없이 선언만 하면 통일한 의미가 없다.

### D-5. 결재는 **네 번째 권한 축**이다 — `DYROLE.canApprove(doc)`

- `scope`(무엇이 보이나) · `canAct`(무엇을 바꾸나) · `assignKind`(누가 할지 정하나) 에 이어 네 번째다.
- 판정: **그 문서 결재선에 내 uid 가 있는가** — 계층(tier)이 아니라 지명 여부로 본다.
- 근거: 결재는 「대신 서명」이 아니라 **자기 이름으로 하는 결재**라, `canAct` 가 막는 문서 위조 근거가 걸리지 않는다. 배정을 세 번째 축으로 연 것과 같은 논리다.
- `DYROLE.inScope()` 에 예외 한 줄을 더한다 — **결재선에 내 uid 가 있는 문서는 부서와 무관하게 보인다.** 결재를 요청받고 문서를 볼 수 없으면 그건 결재선이 아니다.

### D-6. **결재 처리 화면(결재함)은 만들지 않는다**

승인·반려는 온나라에서 일어난다. 이 시스템이 만들 수 있는 상태는 `결재중` 하나다(CLAUDE.md §4 「결재 완료·반려를 수기로 받지 않는다」 2026-08-13 확정).

- 검토자·결재자 계정으로 로그인해서 **이 시스템에서 할 일은 없다.** 그게 정상이다.
- 「3계정이 필요하다」는 것은 **온나라 계정**이 3개 필요하다는 뜻이지 이 시스템의 결재함이 필요하다는 뜻이 아니다. 이 시스템은 **서로 다른 3계정을 지정해 payload 를 만드는 것**까지가 몫이다.
- 대신 **막다른 길로 두지 않는다** — 결재선에 지명된 사람이 로그인하면 자기가 지명된 문서를 조회할 수 있고(D-5), 「진행 상황은 온나라에서 문서번호로 확인」이라고 밝힌다.

### D-7. 예산의 「모의 수신」 버튼 3종을 뺀다

기안자가 자기 결재를 승인하는 모양이고, 다른 도메인은 전부 「회신 연동 전에는 결재중 하나」로 통일돼 있다. 예산만 승인완료·반려를 자체 생성하면 **결재 상태의 정본이 둘**이 된다.

- 시드의 `승인완료` 2건은 남긴다 — **「예시 자료」 칩**을 붙인다(CLAUDE.md §15).
- 뺀 자리에는 온나라에서 확인하라는 안내를 둔다.

### D-8. 하드코딩된 이름 6종을 조직도 실인물로 교체한다

`이팀장`·`김과장`·`김담당`·`중대재해팀장`·`부군수`·`담양군수` → `DYV2.ORG` 의 실제 uid.
바꿀 곳: `bgt.js:90~143`(시드 이력) · `:434~437`(MID_STEPS) · `:893` · `menu.js:444` · `:1452~1453` · `edoc.js:79` · `evl-eval.html:1031·1057·1072·1098`.

## 7. 계정 수 — 3개 (2026-08-27 확정)

한 계정이 여러 도메인에서 같은 역할을 겸할 수 있으므로 필요한 계정 수는 **가장 긴 결재선의 단계 수**로 정해진다. 전 도메인이 3단계로 통일됐으므로(§1-5) **3개**다.

| 결재선 | 필요 계정 |
|---|:--:|
| 기안 → 검토 → 결재 (전 도메인) | **3** |

> 통일 전에는 예산총괄표만 4단계라 4개가 필요했다. 이 문서 초판의 「3이 아니라 4」는 그 상태를 가리킨 것이며, Q-1 확정으로 해소됐다.

**계정 세트** (조직도 실인물 기준)

| 역할 | 사람 | uid | 페르소나 | 상태 |
|---|---|---|---|---|
| 기안자(공용) | 박안전 · 안전관리 주무관 | `u_jjt2` | `staff` | 있음 |
| 검토자 | 김중대 · 중대재해팀장 | `u_jjt1` | `jjtlead` | **2026-08-27 신설(F-9)** |
| 결재자 | 홍길동 · 재난안전과장 | `u_safe1` | `safety` | 있음 |

부서 담당자 관점 검증은 **물순환사업소**를 쓴다 — 하정수(`wat`) → 문정수(`watteam`) → 오순환(`watlead`) 3계정이 조직도 파생만으로 그대로 나온다.

**단계를 늘리면 계정도 늘어난다** — 위임전결규칙상 검토가 하나 더 붙는 건은 그 건에서 4계정이 필요하다. 골격이 최대 4단계까지만 허용하는 이유가 이것이고(§4 D-4), 늘릴 때 그 사실이 화면에 뜬다.

- **없는 결재선을 지어내 채우지 않는다** — 팀장·과장이 없는 부서는 **미지정으로 드러낸다**. 위임전결규칙표를 받으면 채운다(§14-12).
- **`orgFlat()` 의 기본 동작을 바꾸지 않는다** — 소비처가 이미 여럿이다. leadership 은 옵션·별도 파생으로만 연다.

| 결재선 저장 | `{dept, role, name}` → **`{uid, dept, role, name}`**. `defaultLine()` 이 `orgFlat()`(uid 를 버린다) 대신 `orgMembers(deptId)` 에서 파생한다. **행 수·표시 문자열은 그대로**다 |
| 옛 저장분 | uid 없는 sessionStorage 는 통째로 기본값으로 되돌린다 — **이름으로 uid 를 추정하지 않는다** |
| 조직도 | `ORGPICK` `member` → **`memberUid`** + 지휘부 노출 + 이미 쓴 사람 선택 불가 |
| 검증 | `lineIssues()`/`lineReady()`/`lineDenied()` — 골격과 **같은 4종·같은 문구**. `confirmSend`·`send` 두 경로에 건다 |
| 최소 단계 | `MIN_STEP = 2` 신설. 종전 `delStep` 은 1단계까지 지울 수 있었다 |
| 기안자 uid | 저장 문서에 `byUid` 추가. **`rsk-data.js` `pushDoc` 의 화이트리스트에도 넣어야 한다** — 안 넣으면 조용히 버려진다(실측으로 확인) |
| 시드 문서 | 지난 공문의 결재선에 실인물 uid 부여(`u_jjt1`·`u_safe1`) |

**바꾸지 않은 것 (동결 조건)**

- 지면(`.pdf-gm`)·기안 폼 레이아웃·확인 모달의 항목 표(문서·유형·대상·붙임·결재선)·모든 안내 문구 — **한 글자도 바꾸지 않았다.**
- **인라인 경고 박스를 넣지 않았다.** 골격(교육)은 기안 폼에 「지금 무엇이 걸렸는지」를 상시 표시하지만, 이 화면에 넣으면 기안 폼이 달라진다. 대신 **조직도에서 먼저 막고**(사유 표시) 상신 경로에서 토스트로 알린다.
  - 그 결과 **안내 시점이 교육과 다르다** — 교육은 폼에서 미리, 위험성평가는 상신 때. Q-6 회신이 오면 붙일지 정한다.
- `MAX_STEP = 3` 유지(골격은 4). 규칙(≤4) 안이라 위반이 아니므로 동결을 존중해 그대로 뒀다.

**시각 변화 — 4가지가 전부다**

| # | 무엇이 달라 보이나 | 왜 |
|:--:|---|---|
| 1 | 조직도에 **군수·부군수·국장**이 나타난다 | 위임전결규칙상 결재권자로 설 수 있는데 종전엔 고를 방법이 아예 없었다 |
| 2 | 조직도에서 **기안자·이미 지정된 사람이 회색**(사유 표시) | 상신 직전에 거절하면 조직도를 다시 열어야 한다 |
| 3 | 결재선이 2단계일 때 **× 버튼이 사라진다** | 「검토 없이 결재만」을 막는다. 이 파일이 이미 쓰던 방식 그대로다(종전에도 1단계에서 × 를 감췄다) |
| 4 | 상신 확인 시 **거절 사유가 늘어난다** | 종전엔 빈칸만 봤다. 기안자 포함·중복·단계 미달이 추가된다 |

### 13-3. 이번 범위에서 뺀 것 (발견했으나 고치지 않음)

- **위험성평가 공문은 제목 없이도 전역 호출로 상신된다** — `preview()` 만 제목을 검사하고 `confirmSend`·`send` 는 검사하지 않는다. **종전부터 있던 구멍**이고 결재선 축이 아니라 이번 범위 밖으로 뒀다. 고치려면 한 줄이고 화면은 변하지 않는다 — 별건으로 판단할 사항이다.
- **의견청취 협의체 위원 명단의 `정안전 · 중대재해팀장`** — 조직도의 정안전은 건설과 안전관리팀장이다(§12-5).
