## 4. 정보구조 — '이행'을 말하는 3축을 분리한다 (C-03)

담양군 시스템에는 이미 이행을 판정하는 축이 둘 있다. 새 화면은 **세 번째 축**이고, 셋은 묻는 질문이 다르다.

| 축 | 화면 | 묻는 것 | 단위 | 완료 판정 |
|---|---|---|---|---|
| **증빙문서** (신설) | `업무문서 > 이행 목록` | 이 법정 이행항목의 **증빙이 갖춰졌나** | 이행항목 78 × 업무단계 168 | `StageProgress.status==='complete'` (관리자 확인) |
| **부서 점검** | `안전보건관리체계 > 이행관리` | **각 부서가** 반기 점검을 했나 | 부서 39 × 반기 | `DEPTCHK` `DONE` |
| **발행·배정** | `업무 관리 > 업무 발행 관리` | 발행된 업무를 **누가 맡아 끝냈나** | 템플릿 26 × 회차 × 부서 | `DYWORK.deptDone(t)` |

**규칙**

1. **기존 두 축은 한 줄도 고치지 않는다.** `DEPTCHK`·`DYWORK.deptDone` 은 각자의 MUST(CLAUDE.md §4-2·§14-2)를 그대로 유지한다.
2. **새 축은 남의 판정을 읽지도 쓰지도 않는다.** 증빙문서 축의 완료는 문서가 있고 관리자가 확인했는가 하나뿐이다. `DYWORK.deptDone` 을 호출하지 않는다 — 부르는 순간 §14-2의 단일 판정이 두 곳이 된다.
3. **화면이 서로의 역할을 한 줄로 밝힌다.** 이행 목록 안내에 *"부서별 반기 점검은 「안전보건관리체계 > 이행관리」, 업무 배정·회수는 「업무 관리」에서 봅니다"* 를 넣는다. 세 화면이 같은 단어(`이행`)를 쓰는 이상 관계를 말하지 않으면 담당자가 어디서 무엇을 하는지 못 고른다.
4. **168 업무단계 ↔ `DYWORKT` 26종 매핑은 이번 범위 밖이다.** 26종 전수 매핑은 사람 판단이 필요하고, 잘못 걸면 자동발행 대상 부서가 흔들린다(§14-2-1). 후속으로 남긴다.

### 4-1. 두 화면의 역할 구분

- **이행 목록** = 업무단계의 **이행 현황**을 보는 화면. 기본 단위 = 이행항목.
- **업무 목록** = **문서 자체**를 찾는 화면. 기본 단위 = 문서 1건.
- 같은 데이터를 공유하지만 진입 목적이 다르다. 이행 목록의 단계 행 → 업무 목록(그 단계로 필터)로 내려가는 **한 방향 연결**만 둔다.

### 5-2. 2025 진행상태는 파생이지 합성이 아니다 (C-05)

`STAGES[].st2025` 는 원자료 `취합상태` 컬럼의 투영이다.

| 취합상태 | 건수 | → 상태 |
|---|--:|---|
| 확인됨 | 119 | `complete` |
| 보완필요(3건 이하) | 16 | `in_progress` |
| 취합대상(문서 미확인) | 26 | `not_started` |
| 조건부(해당 시 취합) | 7 | `na` |

이 파생이 임의값이 아니라는 증거 — **확인됨 119 + 보완필요 16 = 2025 문서 확인 단계 135**, **취합대상 26 + 조건부 7 = 2025 문서 없는 단계 33**. 문서 존재 여부와 완전히 정합한다. 변환기가 매 실행마다 이 정합성을 검사한다.

```
   (not_started)   (in_progress)  +confirmedBy/At   (complete)

  해당없음(na) ← 관리자만 · 사유 필수 · 취합상태 '조건부' 항목에만
```

- **전이는 `DYDOCS.transition(stageId, year, to, ctx)` 한 곳에서만.** 화면 여러 곳에 하드코딩하지 않는다.
- **업로드 직후는 반드시 `진행중`.** 담당자 화면에 `완료 처리` 액션 자체가 없다.
- **완료된 건의 파일·매핑을 담당자가 바꾸면 자동으로 `진행중` 환원** + `재확인 필요` 표시 + 이력.
- **`해당없음`은 사유 없이 저장되지 않는다.** 근거: CLAUDE.md §4-2 — 발주처가 종이 서식에서 지목한 실패 모드가 미이행이 아니라 *'해당 없음으로 적고 빠져나가는 것'* 이었다. 사유 미기재 데이터는 행에 `사유 미기재 — 확인 필요`로 계속 드러낸다.
- **`기한초과`는 만들지 않는다.** 마감일 원자료가 없다. 없는 기한을 파생하지 않는다.

### 6-1. 진행률 (D-02)

```js
progressOfItem(itemId, year) → {
  visible:    hasOperatingCycle(itemId),        // 운영주기 있는 단계 1개 이상
  completed:  completedStageCount(itemId, year),// status === 'complete' 만
  total:      totalStageCount(itemId),          // 그 항목의 전체 단계 수
  percentage: Math.round(completed / total * 100)
}
```

- 월·분기·반기 횟수를 분모에 **곱하지 않는다**.
- `total === 0` 은 0으로 나누지 말고 **데이터 오류**로 처리한다(현재 데이터에는 없다).
- 바 옆에 `완료 N / 전체 M개 단계`를 항상 함께 낸다.
- **주기 없는 31개 항목은 바 자리에 `상시·수시 항목 — 정기 주기 없음`을 낸다.** 지시서 §5-3은 "자리 자체를 만들지 않는다"지만, 아무 설명 없이 31개 카드만 비면 담당자가 "왜 이것만"을 묻는다. 바를 그리지 않는다는 요구는 지키되 침묵하지는 않는다.
- **노출 조건과 분모의 축이 다르다는 사실을 화면이 밝힌다** — 주기 있는 단계 1개 + 없는 단계 7개인 항목은 그 1개를 끝내도 12%다. 바 아래 `정기 주기 N개 단계 포함`을 함께 적어 "왜 안 오르지"를 없앤다.

## 7. 권한 (D-06 · CLAUDE.md §12)

지시서 §11-4의 "담당자 / 관리자" 2계층을 기존 3계층에 얹는다. **화면 안에 별도 역할 체계를 만들지 않는다.**

| 지시서 용어 | 이 시스템의 판정 | 근거 |
|---|---|---|
| **관리자** | `DYROLE.current().tier==='staff' && deptId===DYROLE.OWNER_DEPT` (재난안전과 담당자) | `RSKLIST.canManage()` 선례. CLAUDE.md §12 **"관리·감독(head/super)은 조회만"** |
| **담당자** | `DYROLE.canAct(deptId)` 가 참인 그 밖의 staff | 〃 |
| 과장·소장·읍면장 | **조회 전용** — 완료 처리·삭제·업로드 액션 0개 | 담당자 이름으로 대신 등록하면 문서 위조다 |
| 군수 | **이 메뉴에 들어오지 않는다** — `ROLE_TIERS.head.hideNav` 가 `docs` 를 숨긴다 | 기존 설정. 이 개편에서 바꾸지 않는다 |

> ⚠ 계층 id 는 `DYROLE.current().tier` 다. `DYROLE.tier()` 는 `{label, tone, who, law, hideNav}` **서술 객체**를 돌려주므로 `=== 'staff'` 비교가 조용히 false 가 되어 권한 판정이 전부 무력화된다(구현 중 실제로 낸 결함).

| 행위 | 담당자 | 관리자(재난안전과 담당자) | 조회 계층(과장·소장) |
|---|:--:|:--:|:--:|
| 이행 목록·업무 목록 조회 | ✓ | ✓ | ✓ |
| 업무 업로드 | ✓ | ✓ | — |
| 진행중 문서·파일·매핑 수정 | ✓ (자기 등록분) | ✓ (전체) | — |

**조회 범위는 이 화면에 부서 축을 두지 않는다 (C-02)** — 원자료가 재난안전과 문서 원장이라 `scope()` 를 걸면 그 외 부서 담당자에게 **0건**이 된다. 대신:

- 화면 안내에 *"2025년 자료는 재난안전과 문서 원장입니다. 부서별 담당 정보는 새로 등록하는 업무부터 쌓입니다."* 를 명시한다.
- **담당부서 컬럼·필터는 두되 값의 출처를 드러낸다** — 2025 문서는 `(원장 미보유)`, 신규 업로드분은 실제 부서. 있는 척하지 않는다.
- 조작은 `canAct()` 로 정상 판정한다. 조회를 열어 둔 것이 조작을 여는 것은 아니다.
- 차단 문구는 `DYROLE.readOnlyNote(what)` 한 곳에서만 낸다.

## 8. 핵심 사용자 흐름 (GATE 1)

각 흐름의 공통 규약 — 진입 CTA · 필수/선택 입력 · 기본값 · 취소·이전 시 데이터 유지 · 성공 피드백 · 실패 처리 · 권한 차이 · URL 동작.

### UF-01 담당자가 미이행 업무단계를 찾는다
`이행 목록` 진입 → 연도 2026 → 상태 필터 `미이행` → 통합검색(항목명·단계명·코드) → 카드에서 단계 행 확인.
데이터 없음: `조건에 맞는 이행항목이 없습니다` + 적용 칩 + `조건 초기화`. URL: `?year=&status=&q=` 동기화.

### UF-02 파일을 올리고 여러 단계에 연결한다
`[업무 업로드]` → **STEP1** 파일(1개↑·`FILE_LIMITS`)·문서명(첫 파일명 자동채움)·보고일자·수발신자·담당부서/담당자(`ORGPICK`)·출처(`직접 첨부` 기본)·비고 → 중복 후보(제목+수발신자+보고일자 일치)가 있으면 **기존 문서에 파일 추가 / 새 문서로 생성** 선택 → **STEP2** 168단계 아코디언 다중선택 → **STEP3** 변경 전→후 상태를 단계마다 보여주고 저장.
저장 결과: 문서 1건 + 매핑 N건 + 선택 단계 전부 `진행중`. 모달 닫힘 → 카드·진행률 즉시 갱신 → 업무 목록에도 1행. 새로고침 후 유지.
이전·취소: STEP 간 이동은 입력 보존, 모달 닫기는 **폐기 확인** 후 폐기.

### UF-03 관리자가 증빙을 확인하고 완료 처리한다
`이행 목록`에서 `진행중` 단계 행 → 증빙 문서 목록 인라인 펼침 → 문서 확인 → `[완료 처리]`.
`confirmedBy`/`confirmedAt` 저장 → 단계 `완료` → 카드 진행률 갱신. 담당자에게는 이 버튼이 **없다**(숨김 + `readOnlyNote`).
반대 행위 `[확인 반려]`는 사유 필수이고 단계를 `진행중`으로 남긴다.

### UF-04 완료된 문서를 수정하면 진행중으로 돌아온다
담당자가 완료 단계의 파일 교체·매핑 변경 → 저장 시 **경고**(영향받는 단계 목록) → 확인 시 해당 단계 전부 `진행중` 환원 + `재확인 필요` 배지 + 이력 1건.

### UF-05 전년도 문서 1건을 가져온다
`[전년도 프리셋 불러오기]`(또는 STEP1의 `2025년 문서에서 가져오기`) → 2025 문서 검색·필터 → 체크 1건 → 하단 고정 영역에 **빠른 설정**(문서명 유지/연도 치환/직접수정 · 담당자 · 첨부 그대로 사용/교체) → 중복 검사 → `1건 가져오기`.
`그대로 사용`은 **새 파일 ID 발급** + `copiedFromFileId`·`sourceYear`·`targetYear` 기록. 원본 문서·파일 불변.

### UF-06 여러 건을 골라 공통 옵션 + 일부만 교체
2건↑ 선택 → 상단 선택 건수 + 하단 **일괄 설정 막대** → 공통 옵션 적용 → 예외 문서만 행을 펼쳐 개별 수정 → 생성.
선택은 필터·페이지 이동 중 유지. `선택한 항목만 보기`·개별 해제·전체 해제 제공. 모든 문서의 상세 폼을 한꺼번에 펼치지 않는다.
**부분 실패**: 파일 3개 중 1개 복사 실패 → 문서는 생성하고 실패 파일만 `원본 파일 확인 필요`로 남긴다. 전부 실패면 문서를 만들지 않는다.

### UF-07 업무 목록에서 상세필터를 조합한다
통합검색 → 빠른필터(연도·출처·보고일자 기간) → 상세필터 펼침(이행항목→업무단계 종속·법령근거·주기·취합상태·적용대상·이행주체·담당부서·담당자·수발신자·첨부/PDF 유무·매핑 상태·등록자) → 적용 칩 → 정렬·페이지 크기.
**상태는 상세필터에만 둔다** — 출처에 따라 옵션이 바뀌므로 빠른필터에 둘 수 없다(§11-10).

### UF-08 문서 상세·온나라 PDF 를 보고 돌아온다
문서명 클릭 → `doc-detail.html?id=` → 출처별 본문(첨부=미리보기 / 전자문서=EDOC 폼 / 프로그램=전용 화면 안내 / 온나라=지면).
`PDF 보기`는 **실제 상신 산출물이 있을 때만 활성**. 없으면 비활성 + `원본 PDF 미연계 — 온나라 연동 후 제공` 사유.
목록 복귀 시 필터·정렬·페이지·스크롤 복원(URL 쿼리 + `history`).

### UF-09 관리자가 미분류·근사중복을 교정한다
요약의 `미분류 34건` → 업무 목록 `매핑 상태=미분류` → 문서 선택 → 업무단계 지정 → 저장.
`근사중복 2쌍` → 두 문서를 나란히 보여주고 `같은 문서로 병합` / `다른 문서로 유지`(사유). 병합은 매핑·첨부를 합치고 이력을 남긴다.
