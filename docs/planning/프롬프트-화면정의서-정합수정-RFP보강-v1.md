## 0. 판단 원칙 (전 지시 공통)

1. **RFP(SFR-001~021)가 명시한 요구는 전부 정의서에 거처가 있어야 한다.** 수용은 기존 화면 §4·§6 확장으로 하고 **신규 화면·신규 화면 ID를 만들지 않는다.**
2. **프로토타입 미구현은 "구현 차이 — 본개발 구현 범위"로 명시한다.** "잔여 후속"·"다음 단계 결정"·"개발 시 반영" 같은 미룸 표현을 쓰지 않는다.
3. **본개발 계약과 프로토타입 시연 동작을 구분해 적는다** — 시연 장치(물리 삭제·시뮬레이션)는 폐기하지 않고 시연 장치임을 밝힌다.
4. 발주처 재량 표현("발주처 확인 대상")은 쓰지 않는다 — 99 §1 원칙(기본값 확정, 발주처가 다르게 정하면 그 값만 교체)이 전 항목에 이미 적용된다.

## PART 1 — 정합 수정 (문구 확정, 14건)

### 1-1. 알림 외부 채널 "이번 범위 아님" 정정 — `SCR-ADMIN-002_알림관리.md`

- §3 분기 로직의 "채널을 이벤트마다 고른다 — 다만 이번 범위에서 실제로 쓰는 것은 시스템 내부 알림이다. 문자·메일은 비용·개인정보 처리·수신 동의가 얽혀 별도 결정이 필요하므로…" 와 §6의 "외부 채널은 이번 범위가 아니다" 문단, §7의 "외부 채널의 범위" 표현을 다음 취지로 전면 교체한다:
  - **외부 채널(SMS·메일·Push)은 본개발 구현 범위다**(RFP SFR-017 필수 · 원천은 문자발송체계·통신사 모듈 연계, 99 §4).
  - **연계 전에는 내부 알림만 실발송**하며, 외부 채널 설정 항목은 노출하되 `연계 전` 상태를 표시하고 발송 성공을 가장하지 않는다(_규칙 §5 알림 계약 그대로).
  - "별도 결정이 필요하다"는 서술 삭제 — 결정은 끝났다(구현한다). 비용·수신 동의는 연계 협의에서 다루는 운영 조건이지 범위 조건이 아니다.
- §7 마지막 줄 "외부 채널 도입은 미결이 아니라 **다음 단계 결정**이며…" → "외부 채널은 본개발 연계 구현 범위이며, 연계 전에는 내부 알림으로 동작한다"로 교체.

## PART 2 — RFP 수용 스펙 보강 (기획 확정값, 9건)

각 항목의 기획은 아래에 확정돼 있다. 작업자는 이를 해당 정의서의 §3·§4·§5·§6 형식으로 풀어 쓴다. **전부 "프로토타입 미구현 — 본개발 구현 범위" 표시를 단다**(프로토타입 코드 수정은 이 지시 범위 밖).

### 2-1. SFR-017 통합알림 — `SCR-ADMIN-002_알림관리.md`에 「외부 발송 관리」 구획 신설

- **채널**: 내부 알림(기본·항상 켜짐) · SMS · 메일 · Push(URL response 방식 — 앱·exe 설치 없음). 이벤트 규칙별 채널 선택은 기존 구조 유지.
- **SMS 발송 관리**: ① 발송 구분 — 전체 / 개인 / 기관 총괄 / 기관 담당자 ② 즉시·예약 발송(예약 취소 가능, 발송 후 취소 불가) ③ 엑셀 업로드 발송 — 수신번호·내용 서식, 일괄등록 공통 검증(_규칙 §5) 적용, 오류 행은 로그로 제공 ④ 발송 이력에서 분류·수신번호·내용 검색.
- **수신번호는 조직도 연계 값을 쓰고 화면에는 마스킹 표시**. 수기 번호 입력은 엑셀 발송 경로에만 허용(출처 표시).
- **실패 처리**: 외부 연계 공통 계약 준용(자동 3회 재시도 → 담당자 재처리 전환, 성공 가장 금지).
- **바탕화면 바로가기 아이콘 생성 안내** 제공(RFP 문구 수용 — 설치 없는 방식).
- 발송 이력 대장(무상한·불변) 원칙은 기존 §6 그대로.

### 2-2. SFR-001 기능 활용 점검 — `SCR-ADMIN-005_메뉴관리.md`에 「메뉴 이용 현황」 구획 신설

- 메뉴별 **이용 건수(기간 조회) · 최종 이용일 · 기간 내 미사용 표시**. 기간 기본값은 최근 90일.
- 사용자·부서 단위 상세 분석은 두지 않는다(최소 — RFP는 "기능별 활용 여부 점검"만 요구). 근거 데이터는 접속·화면 이용 기록이며 수집은 본개발 구현 범위(SCR-ADMIN-001의 접속 기록과 같은 축).

### 2-3. SFR-006 조직 직접 등록 — `SCR-ADMIN-001_사용자권한관리.md`에 「조직 직접 등록」 구획 신설

- **행정포털에 없는 조직만** 직접 등록한다: 부서(노드) 추가·수정·사용중지. 필수값 — 부서명·상위 노드·유형. **삭제는 없다**(참조 보존 — 사용중지만).
- 모든 조직 노드에 **출처(연계 / 직접 등록)** 를 저장하고 관리 화면에서 구분 표시. 연계 원천 값은 읽기 전용.
- **병합 규칙**: 연계 수신 시 직접 등록 부서와 이름이 일치·유사한 후보를 제시하고 담당자가 병합/유지를 선택한다. **자동 병합 금지.** 병합 시 소속 인원·권한·참조(deptId)를 승계하고 이력을 남긴다.
- `SCR-SBM-002_조직.md`에는 "직접 등록·병합의 정본은 SCR-ADMIN-001"이라는 상호 참조 한 줄만 추가(표시 화면과 관리 화면의 분리 유지).

### 2-4. SFR-010 배치 기준 자동 체크·공사별 축 — `SCR-SBM-002_조직.md` 선임 현황 보강

- **선임 상태 판정**: 직역(안전관리자·보건관리자·산업보건의)별 법정 배치 기준 인원 대비 현재 선임 수를 비교해 `충족 / 미달 / 공백`을 자동 표시하고 미달·공백에 경고 배지. **기준 인원값은 법령 조문(산안법 시행령 배치 기준) 수집 후 확정**하며, 수집 전에는 기준 미등록으로 표시하고 지어내지 않는다(§10 원칙 준용).
- **"진행 중단"의 해석(확정)**: 미달 상태에서는 선임 현황 점검을 `완료`로 확정할 수 없다(차단+사유 표시). 다른 업무 화면의 진행을 막지는 않는다 — 과잉 차단은 RFP 취지(배치 관리)를 넘는다.
- **공사별 안전관리자 선임 현황**: 발주처·공사명·공사기간·공사금액·안전관리자 정보. 원천은 차세대 e호조 연계(99 §4), 연계 전 직접 등록 + 시연용 더미 표시. 점검 결과는 완료/진행/미시행 상태로 기존 점검표 축 재사용.

### 2-5. SFR-021 워터마크·위조방지 — `SCR-RPT-002_보고서제증명.md` §6 보강

- **모든 출력물에 워터마크**: 기관명·출력자·출력일시·발급번호를 지면에 표시한다.
- **발급번호**: 공통 식별 규칙(접두어·연도·연속번호) 준용, 출력 이력과 1:1 연결.
- **진위확인(최소)**: 발급번호로 출력 이력을 조회해 발급 사실·발급일·문서 종류를 대조한다(시스템 내 조회 — 외부 공개 검증 페이지는 범위 밖).
- **위조방지 솔루션**(복사 방지 용지 패턴 등)은 RFP 허용대로 **임대 방식 제안 가능**으로 두고, 기본 구현은 워터마크+발급번호 조회다.

### 2-6. SFR-012 매뉴얼 점검 수용 근거 — `SCR-DOC-001` · `SCR-SBM-006` §6에 각 한 줄

- 매뉴얼·업무처리절차의 **제정·개정·버전 관리는 기준문서함(SCR-DOC-001)**, **제정·조치 여부 점검은 이행관리(SCR-SBM-006) 점검 축과 이행 목록 증빙**이 수용한다는 근거를 §6에 명시하고, 00_화면목록의 두 행 "기존 SFR" 컬럼에 SFR-012를 병기한다.

### 2-7. SFR-019 신고 관리 수용 근거 — `SCR-OPN-001` · `SCR-RPT-001` §6에 각 한 줄

- 유해·위험요인 **신고·개선제안 등록은 의견청취의 4분류(위험신고·안전제안)** 가 수용한다는 근거를 OPN-001 §6에 명시.
- **접수 건수·조치율 통계**: 현황 통계(SCR-RPT-001)에 의견청취 축 집계(분류별 접수 건수·조치완료율)를 추가한다. 조치완료율 분모는 접수 건, 분자는 추진결과가 등록된 건.
- 00_화면목록의 두 행에 SFR-019 병기.

### 2-8. SFR-011 온라인 접수 복원 — `SCR-OPN-001_의견청취.md` OPN-05 개정

- OPN-05를 다음으로 교체: **온라인 접수는 본개발 구현 범위다**(RFP 명시 요구). 방식은 **SSO 실명 접수** — 로그인한 종사자 본인이 의견·신고를 직접 등록하고 소속·성명은 계정에서 자동으로 온다. 접수 경로 값에 `온라인(본인 등록)`을 추가하고 담당자 대리 등록 경로는 유지한다.
- **익명 접수는 두지 않는다**(확정) — 익명 보호 설계는 별개 기획이라는 기존 논리는 익명 축의 제외 근거로만 남긴다. 실명 접수의 신고 위축 우려는 열람 권한(처리 담당자만 신고자 식별정보 열람)으로 완화하며 이를 §6에 명시한다.

### 2-9. SFR-020 대시보드 필수 블록 — `SCR-DASH-001_통합현황대시보드.md` §4·§6 보강

- **총괄(군수) 구성에 관리대상 기본현황 카드**를 추가: 공중이용시설 개소 · 원료·제조물 개소 · 공중교통수단 개소. 공중교통수단은 EXT-09 확인 전 `자료 미수신`으로 표시(0으로 표시 금지). 원천은 관리대상 현황 화면과 같은 집계.
- **중대재해예방활동·시기도래 업무현황·알림 메시지 내역**은 기존 구성(계층별 카드·기한 구간·전역 알림)이 수용함을 §6에 매핑으로 명시한다 — 시기도래 구간은 공통 기한 구간(_규칙 §5)과 RFP 예시(1개월 이내·오늘 마감·1주일 이내·기한 초과)의 대응을 적는다.
- 계층별 화면 분리 원칙은 유지한다(모든 블록을 전 계층에 강제하지 않는다).
