## 1. 계정 — 테스트 계정으로 할지, 실제 계정으로 할지

### 결론: 두 갈래로 나눈다

| 갈래 | 계정 | 무엇을 하나 | 이유 |
|---|---|---|---|
| **A. 기능 설명 · 단위 테스트**(등록 · 수정 · 삭제 · 상신 · 독촉) | **테스트 계정** (QA박안전N · QA하정수N) | 본 체크리스트 §4 전부 | 운영 DB에 남는 기록·알림을 통제할 수 있다 |
| **B. 실제 계정 확인**(읽기 전용) | **주무관님 본인 실제 계정** (+ 가능하면 부서 담당자 실제 계정 1개) | 로그인 · 내 이름/부서/직위 표시 · 보이는 메뉴 · 조회 범위 · 조직도에서 본인 찾기 · 내 할일 | 실제 권한 등급과 조직 연계가 맞는지는 **실제 계정으로만** 확인된다 |

**실제 계정으로 «조작」을 하지 않는 이유** — 운영 서버라 되돌릴 수 없는 것이 많다.

| 실제 계정으로 조작하면 | 왜 문제인가 |
|---|---|
| 이력에 주무관님 실명이 남는다 | 이력은 감사 기록이라 지우지 않는 것이 원칙이고, 테스트 기록이 실제 업무 이력과 섞인다 |
| 독촉·재촉·알림이 실제 직원에게 간다 | 6인 엑셀 안내도 «실제 직원에게 가고 되돌릴 수 없다»고 적고 있다 |
| 정기 위험성평가는 **한 해 1건** | 테스트로 2026년 평가를 만들면 실제 평가 자리를 차지한다(삭제는 개발자만) |
| 공문 상신 | 지금은 «내부 처리»로 바로 결재완료지만, 온나라 연계가 켜져 있다면 실제 결재 문서가 생긴다(§2 요청 6번으로 확인) |
| 근로자 명단 · 건강검진 | 개인정보 화면에 테스트 사람이 섞인다 |

**실제 계정 확인이 꼭 필요한 이유** — 테스트 계정은 개발자가 권한을 직접 붙인 계정이라, 다음은 테스트 계정으로 아무리 눌러도 확인되지 않는다.

- [ ] 주무관님 계정이 **«재난안전과 · 담당자」(전 부서 조회 · 확인 · 상신)** 로 잡혀 있는가 — 과장 등급으로 잡히면 조회만 된다
- [ ] 화면 오른쪽 위 이름 · 부서가 실제와 같은가
- [ ] 결재선 [조직도]에 실제 팀장·과장이 나오는가(테스트 때는 QA박안전2·3을 골랐다)
- [ ] 부서 담당자 실제 계정이 **자기 부서 것만** 보는가
- [ ] 실제 계정에 «시스템 관리»가 보이는가/안 보이는가가 의도대로인가

### 계정 결정이 바뀌는 조건 (개발자 답에 따라)

| 개발자 답 | 그러면 |
|---|---|
| 실제 계정이 아직 발급되지 않았다 / 조직도 연계 전이다 | B는 하지 않는다. 대신 «실제 계정 발급 · 권한 매핑 일정»을 현장에서 함께 정한다 |
| 운영과 같은 **검증(스테이징) 서버**가 있다 | 조작 테스트도 거기서 실제 계정으로 해도 된다. 가장 좋은 방법이다 |
| 로그인이 행정포털 SSO다 | 테스트 계정이 SSO 밖에서 따로 로그인되는지 먼저 확인(안 되면 A가 막힌다) |
| 알림·독촉이 실제 직원 계정에도 간다 | 독촉은 테스트 부서·테스트 사람 1건만, 또는 시연에서 뺀다 |

### 현장에서 쓸 테스트 계정 (최소)

| 역할 | 계정 예 | 쓰임 |
|---|---|---|
| 재난안전과 담당자 | QA박안전1 | 대부분의 시연(전 부서 조회 · 등록 · 확인 · 상신 · 독촉) |
| 부서 담당자 ① | QA하정수1 (물순환사업소) | 부서 쪽 처리 · «내 부서만 보인다» |
| 부서 담당자 ② | QA하정수3 (공공시설사업소) | 두 부서가 서로 안 보이는지 |
| 결재선 검토 · 결재 | QA박안전2 · QA박안전3 | 고르기만 한다(로그인 안 함) |

노트북 1대에서 **일반 창 = 재난안전과, InPrivate 창 = 부서 담당자**로 나란히 띄워 두면 계정 전환 없이 «주는 쪽 / 받는 쪽»을 바로 보여드릴 수 있다.
