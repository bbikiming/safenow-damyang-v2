# 분석 — 계약정보시스템 → e호조+ API 대체 설계 v1

> 작성 2026-09-21 · 근거: 담양군 수신 「이호조 연계 가이드」(API URI 목록 v3.7 · 인터페이스 정의서 291건 · 연계개발 가이드 v1.16)
> 대체 대상: `99_미결사항목록` **EXT-15**(계약정보시스템 연계 가능 범위) · **EXT-14**(도급 점검 대상 선별 기준)
> 기능 정의 정본: `SCR-SBM-004 §6·§7` · 외부연계 정본: `기획-외부연계-기능정의-v1 §3`

## 0. 한 줄 결론

**EXT-15 에서 «화면에서 확인되지 않았다»고 적어 둔 3건이 전부 e호조에 있다.** 다만 셋 중 하나(사업자등록번호)는 **암호화 필드**라 복호화 키가 없으면 값이 아니라 48자 문자열이고, 계약 **상대 업체**는 계약대장이 아니라 **다른 테이블**에 있어 조인이 하나 더 붙는다.

| EXT-15 미확인 항목 | e호조 필드 | 판정 |
|---|---|---|
| 사업자등록번호 | `ecrpBno` 암호화사업자등록번호 (48) | **있음 — 단 암호화**. 복호화 키는 별도 수령 |
| 해지·해제 표시 | `ctrtCnltYn` 계약해지여부 (1) | **있음** |
| 「번호」의 불변성 | `ctrtLdgrMngNo` 계약대장관리번호 (12, PK) + `frstCtrtLdgrNo` 최초계약대장번호 | **있음** — 공개목록의 「번호」보다 강한 키 |

그리고 **EXT-14 의 제약이 성질을 바꾼다.** 종전 근거는 *"공개 목록에 계약기간 열이 없어 4,173건을 손으로 옮길 수 없다"* 였는데, e호조는 착공일·준공예정일·준공일을 전부 주고 최종수정일자 증분 조회까지 된다. **「손으로 못 옮긴다」는 제약은 사라진다.** 남는 것은 «무엇을 점검 대상으로 볼 것인가»라는 담양군의 판단뿐이고, 그건 여전히 우리가 만들 수 없다.

## 1. 이 문서가 다루지 않는 것

- **연계를 하기로 확정했다는 뜻이 아니다.** 가이드를 받아 «무엇을 받을 수 있는지»가 확인된 것이다. EXT-15 의 갈래는 C(외부 연계 규격)에서 **«규격 수신 · 채택 여부 미정»** 으로 한 칸 움직인다.
- **화면에 연계 전제를 만들지 않는다.** `99_미결사항목록 §4-9` 의 확정 동작(*"「연계 전」 상태조차 두지 않고 직접 등록으로만 동작한다"*)은 실제 연계가 붙기 전까지 그대로다.
- **아래 매핑을 화면·정의서에 「받아올 항목 확정 목록」으로 옮겨 적지 않는다.** 실제 호출로 검증되기 전까지는 설계 근거이지 약속이 아니다.

## 2. e호조+ 가 제공하는 것 — 전체 지형

291종 · 9개 주제영역. 우리에게 의미 있는 것은 **3개 영역**이다.

| 주제영역 | 종수 | 우리 관련성 |
|---|---:|---|
| **FC(계약관리)** | **35** | **도급관리·조직(공사별 선임)의 원천** — 이 문서의 본론 |
| **CM(공통관리)** | 68 | 부서코드·거래처코드·공통코드 — 위 데이터를 **해석**하는 데 필수 |
| **BM(예산관리)** | 68 | 예산현액 → 안전보건 예산 **편성액** |
| **FE(지출관리)** | 51 | 지출원인행위 → 안전보건 예산 **집행액** |
| PM(사업관리) | 20 | 세부사업 단위 — 예산 축의 보조 |
| FM(자금)·SA(결산)·ST(통계)·AM(자산) | 49 | 해당 없음 |

### 2-1. 호출 규격 (전 API 공통)

- **엔드포인트** `http://{별도공지 URL}:{포트}/{영역}/openAPI/{테이블명}`
  - ⚠ **FC(계약관리) 테이블의 URL·인터페이스ID 는 `FE` 계열이다** — `/FE/openAPI/TFC1250M`, `LR_FE_LAF_SA_00067`. 영역 접두어를 테이블명에서 추측하면 전건 404 가 난다.
- **헤더 필수** `ifId`(인터페이스ID 18) · `tranId`(42) · `trnmtInstCd`/`rcptnInstCd`(기관코드 3) · `trnmtInstSysCd`/`rcptnInstSysCd`(시스템코드 3)
- **바디 공통** `curPage`·`pageSize` 필수. **1회 최대 3,000건**
- **증분 조회** `lastMdfcnBgngYmd`·`lastMdfcnEndYmd`(YYYYMMDD) — 전 테이블 공통. **일 배치의 근거**
- **회계연도** 일부 API 는 `fyr` 필수(TFC1250M·TFC1490L 등) — 연도별로 나눠 호출
- **응답코드** `00000` 정상 / `42901` 정보제공 요청한도 초과 / `40101` 유효하지 않은 API 키 / `40102` 권한 없음

### 2-2. 선행 확보 3건 (없으면 호출 자체가 안 된다)

| 항목 | 상태(화면) | 어디서 |
|---|---|---|
| 서비스 URL·포트 | **미설정** | 별도 공지 |
| **API 인증키** | **미설정** | e호조+ 자치단체게시판(**81707**) → 「자체시스템 API 연계 관련 파일 배포」(2022-09-13). 첨부가 안 보이면 **기준정보관리자**가 81708 에서 첨부파일 사용여부를 「사용」으로 바꿔야 한다 |
| **암복호화 키** | **미설정** | 동상. 문서 암호는 통합콜센터 **1522-7536** 또는 ITSM |

자치단체코드는 `DAM`(담양)으로 이미 설정돼 있다.

### 3-2. ⚠ 계약 상대 업체 — 계약대장에 없다 (가장 중요한 구조 발견)

`TFC1250M` 70필드 어디에도 업체명·사업자등록번호가 없다. `TFC1710L 입찰내역` 46필드에도 없다(참가업체 **수**와 낙찰 **금액**만 있고 낙찰자명이 없다). 업체는 **세 갈래**로 들어온다.

| 경로 | 테이블 | 업체 필드 | 성격 |
|---|---|---|---|
| **① 계약 상대자** | **`TFC1420L 공동계약내역`** | `cltNm` 거래처명 · `ecrpBno` 암호화사업자등록번호 · `rprsvNm` 대표자명 · `rprsTelno` 대표전화번호 · `mnrcrYn` **주계약자여부** · `cprtCtrtAmt` 공동계약금액 · `cprtCtrtRt` 공동계약비율 · `zonEnprYn` 지역기업여부 | **검증 필요 — §6** |
| ② 하도급 | `TFC1820M 하도급계약` | `mtltNm` 상호명 · `ecrpBno` · `rprsvNm` · `sbcEnpAddr` 하도급업체주소 · `sbcCtrtAmt` 하도급계약금액 · `sbcRt` 하도급비율 · `ognCnrNm` 원본계약자명 | **중처법 §5 제3자 확장의 실자료** |
| ③ 대금 수령자 | `TFC2200L → TFC2270M 계약대금지급채주` | `cltNm` 거래처명 · `ecrpBno` · `rprsvNm` | 대금을 지급해야 생긴다 — **착공 시점엔 없을 수 있다** |

**① 을 채택한다.** 이유: ②는 하도급만, ③은 **지급이 일어난 뒤에야** 행이 생겨 «계약했는데 업체를 모르는» 구간이 생긴다. ①은 계약 체결 시점에 들어가는 자리다.

> **⚠ 검증 전제** — 테이블명이 「공동계약내역」이라 **단독계약에도 행이 생기는지**가 이 설계의 전제다. e호조 구조상 단독계약은 `주계약자여부='Y'`·`공동계약비율=100` 한 행으로 들어가는 것이 표준이고, `TFC1250M` 이 `cprtCtrtDvCd` **공동계약구분코드**를 따로 들고 단독/공동을 가르는 것이 그 방증이다. **다만 실제 호출로 확인하기 전까지는 추정이다.** 이 전제가 틀리면 **업체명을 얻을 경로가 ③밖에 없고**, 그러면 «계약은 있는데 업체가 빈» 행이 생긴다.

**대안 축** — `TCM6060C 거래처코드`(40필드: `cltCd`·`cltNm`·`cltEcrpBno`·`rprsvNm`·`btId` 업종ID·`bzclCd` 업태코드·주소). 계약↔거래처를 잇는 `cltCd` 를 위 세 테이블 중 하나에서 얻어야 하므로 **단독으로는 쓸 수 없다.**

### 3-3. 조직 — 공사별 안전관리자 선임 현황 (`ORG_CONSTRUCTION_STATE`, `js/menu.js:948`)

SFR-010 의 5열이 거의 1:1 로 채워지는데 **마지막 한 열이 비어 있는 것이 결론이다.**

| 화면 열 | e호조 | 판정 |
|---|---|---|
| 발주처 | `lafCd` 지방자치단체코드 = 담양군 | 고정값 |
| 공사명 | `TFC1250M.ctrtTrgtNm` | ✅ |
| 공사기간 | `bgcsYmd ~ cmcnScdYmd` | ✅ |
| 공사금액 | `smzCtrtTottAmt` | ✅ |
| **안전관리자** | ✗ | **e호조에 없다 — §5** |

**다만 사람 축 두 개가 새로 들어온다. 둘 다 안전관리자가 아니다.**

- **`TFC1910L 현장대리인내역`** — `siteTagnNm` 현장대리인명 · `jbttlNm` **직책명**(100) · `skllQlfcTyNm` **기술자격유형명**(100) · `skllQlfcNo` 기술자격번호 · `siteAgntBgngYmd ~ siteAgntEndYmd` 현장대리 기간 · `ecrpRrno` 암호화주민등록번호
  - 건설기술진흥법상 **현장대리인**이고 산안법 **안전관리자와 다른 지위**다. 그대로 「안전관리자」 열에 넣으면 **선임 공백을 선임된 것으로 표시**하게 된다 — §14-2 「대상이 아닌 부서를 완료로 세지 않는다」와 같은 실패다.
  - 다만 `jbttlNm`·`skllQlfcTyNm` 에 「안전관리자」·「산업안전기사」가 실제로 들어오는지는 **확인 가치가 있다**(§7 확인항목 ③).
- **`TFC1190L 계약감독자내역`** — `spvsrUsrId` 감독사용자ID · `supvDeptCd` 감독자부서코드 · `supvPosCd` 감독자직급코드 · `chrgBgngYmd ~ chrgEndYmd` 담당기간
  - **감독공무원**이다. 현재 시드 `CONST-01` 의 *"감독공무원 지명 및 임명"* 이 계약 건명에 들어 있을 만큼 실무에서 붙어 다니는 축인데 화면에 자리가 없다. **담양군 측 책임자**를 실자료로 특정할 수 있는 유일한 경로다.

### 3-4. 예산관리 (`js/bgt.js`) — 부수 효과, 그러나 크다

현재 편성액·집행액을 **전부 손으로 입력**하고 있고, 그래서 §7-1 에 *"상신하면 결재중에서 나올 길이 없어 집행액을 영영 입력할 수 없다"* 는 구조 문제가 남아 있다.

| 화면 값 | e호조 | 조인키 |
|---|---|---|
| 편성액 | **`TBM2550M 예산현액`** `bdgCamtAmt` 예산현액금액 | `fyr` + `deptCd` + `aneStmkCd` 세출통계목 + `dbizCd` 세부사업 |
| 집행액 | **`TFE2401M 지출원인행위`** `ecaAmt` 지출원인행위금액 (+`supAmt` 공급금액·`vatAmt` 부가세) | `fyr` + `deptCd` + `dbizCd` |
| **계약↔집행 연결** | **`TFE2401M.ctrtLdgrMngNo`** | **지출원인행위가 계약대장관리번호를 들고 있다** |

마지막 줄이 핵심이다 — **「어느 안전보건 계약에 얼마가 집행됐나」가 조인 하나로 나온다.** 지금은 계약과 예산이 화면상 남남이다.

**단, 「안전보건 예산」이라는 과목이 e호조에 없다.** 세출통계목(`aneStmkCd`) 중 무엇이 시설·장비·안전장구류 3대 분야인지는 **담양군이 지정해야 한다** — §5 의 갭이다.

## 4. 호출 설계

### 4-1. 조인 그래프

```
TCM2060C 부서코드 ─┐
                   ├─ deptCd
TFC1250M 계약관리대장 ──ctrtLdgrMngNo──┬── TFC1490L 당년도계약내역   (차수·변경)
   │  fyr, deptCd, lctnNm             ├── TFC1420L 공동계약내역     (업체 ★)
   │  bgcsYmd~cmcnScdYmd              ├── TFC1910L 현장대리인내역   (현장 사람)
   │  smzCtrtTottAmt, ctrtCnltYn      ├── TFC1190L 계약감독자내역   (감독공무원)
   │                                  ├── TFC1820M 하도급계약       (제3자)
   │                                  └── TFE2401M 지출원인행위     (집행액)
   └─ ctrtKndCd ── TCM3030C 공통상세코드 (코드 해석)
                   TCM6060C 거래처코드 ── cltCd (업체 상세)
```

### 4-2. 일 배치 순서

1. **기준정보(월 1회면 충분)** — `TCM2060C` 부서코드 · `TCM3030C` 공통상세코드 · `TCM6060C` 거래처코드
2. **계약 본체(일)** — `TFC1250M`, `fyr`=당해연도 + `lastMdfcnBgngYmd`=전일
3. **계약 부속(일)** — `TFC1420L`·`TFC1490L`·`TFC1910L`·`TFC1190L`·`TFC1820M`, 같은 증분창
4. **예산·집행(일)** — `TBM2550M`·`TFE2401M`

3,000건 상한이라 **`totalCnt` 를 보고 `curPage` 를 끝까지 돌리는 루프가 필수**다. 첫 페이지만 받고 끝내면 조용히 잘린다.

### 4-3. 우리 쪽에서 먼저 정해야 하는 것 — 부서코드 매핑

e호조 `deptCd` 는 **7자리**, 우리 `DYV2.ORG` 의 id 는 `safety`·`water` 같은 문자열이다. **`DYV2.ORG` 노드에 `ehojoDeptCd` 를 추가하는 것이 단일 출처 원칙(§3)에 맞는 자리**다 — 변환표를 연계 모듈 안에 따로 두면 조직도와 갈린다.
⚠ 현재 `DYV2.ORG` 에 등록된 부서는 **11개**이고 담양군 과·사업소는 **39개**다(§4-2). 계약은 39개 부서 전부에서 나오므로, **매핑이 없는 부서의 계약을 버리지 말고 「조직도 미등록」으로 드러낸다**(`DYCMP.deptList()` 가 원장∪조직도를 쓰는 것과 같은 방식).

## 5. 남는 갭 — 연계해도 채워지지 않는다

**지어내 채우지 않는다.** 아래는 e호조를 붙여도 비어 있는 자리다.

| 갭 | 왜 | 지금 동작 유지 |
|---|---|---|
| **안전관리자 선임** | e호조는 재정 시스템이라 산안법 선임 정보를 담지 않는다. 현장대리인·계약감독자는 **다른 지위**다 | 직접 등록(`ORG_APPOINT_STATE`) |
| **안전보건 예산 과목 지정** | 세출통계목 중 무엇이 안전보건인지는 담양군의 편성 판단 | 직접 입력 |
| **점검 대상 선별 기준** (EXT-14) | 금액·기간·구분은 다 오지만 «무엇을 점검 대상으로 볼 것인가»는 운영 판단 | 등록한 사업만 대상 |
| **사업자등록번호 평문** | `ecrpBno` 는 암호화(48). 복호화 키 미수령 | 미표시 |
| **서약서·점검표·교육 이수** | 도급 안전보건 관리의 실체. e호조에 축 자체가 없다 | 직접 등록·첨부 |
| **계약 상세 첨부파일** | `atflGrpId` 첨부파일그룹ID 만 오고 **파일 본체 API 가 없다** | 직접 첨부 |

마지막 줄을 특히 주의 — `TFC1250M.atflGrpId` 가 있어 「첨부도 온다」고 읽기 쉽지만, 291종 어디에도 파일 내용을 내려받는 인터페이스가 없다. **ID 만 오고 파일은 안 온다.**

## 6. 검증 계획 — 붙이기 전에 확인할 것

`https://safety.damyang.go.kr/admin/ehojo` 화면에 **[호출]** 버튼이 있고 *"호출하면 첫 행의 실제 값이 함께 표시됩니다"* 라고 돼 있다. 인증키·복호화키·URL 설정 후 아래 순서로 **실호출 검증**한다.

| # | 호출 | 확인할 것 | 실패 시 영향 |
|---|---|---|---|
| ① | `TFC1250M` (fyr=2026) | `totalCnt` 가 공개목록 4,173건 축과 맞는가 · `cmcnScdYmd` 채움률 · `lctnNm` 채움률 | 기간이 비면 **반기 점검 대상 판정이 여전히 불가** |
| ② | **`TFC1420L`** | **단독계약 건에도 행이 있는가**(§3-2 전제) · `cltNm` 채움률 | 없으면 업체 경로가 ③(지급 후)뿐 — 설계 재검토 |
| ③ | `TFC1910L` | `jbttlNm`·`skllQlfcTyNm` 에 「안전관리자」류가 실제로 들어오는가 | 안 들어오면 선임 열은 갭 확정 |
| ④ | `TFC1190L` | 감독공무원 `spvsrUsrId` 가 `TCM4040M 사용자`로 이름 해석되는가 | 담양군 책임자 특정 불가 |
| ⑤ | `TCM2060C` | 부서코드 7자리 체계 · 담양군 실제 부서 수 | §4-3 매핑 설계 불가 |
| ⑥ | `ecrpBno` 복호화 | 키로 실제 사업자등록번호가 나오는가 | 업체 동일성 판정을 상호명에 의존 → 동명이인 위험 |
| ⑦ | `TFE2401M` | `ctrtLdgrMngNo` 채움률 | 계약↔집행 연결 불가 |

**②가 가장 중요하다** — 이 설계에서 유일하게 추정 위에 서 있는 전제다.

## 8. 착수 판단

**지금 코드를 고치지 않는다.** 선행 3건(URL·인증키·복호화키)이 전부 미설정이고 EXT-15 의 확정 동작이 *"연계 전제를 화면에 만들지 않는다"* 이기 때문이다. 순서는 이렇다.

1. 인증키·복호화키·URL 수령 (담양군 기준정보관리자 → 81707 게시판)
2. §6 검증 ①~⑦ 실호출
3. **②의 결과에 따라 업체 축 설계 확정**
4. EXT-14 선별 기준 수령 (문서 분류 이후)
5. 그때 `SCR-SBM-004 §6·§7` 개정 → 화면 착수

**2번과 3번 사이에서 설계가 갈린다** — 그 전에 화면을 만들면 되돌리게 된다.
