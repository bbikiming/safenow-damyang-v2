# 담양군 중대재해 통합관리시스템
## 이행관리 프로토타입 구현 참고 문서

> 목적: 첨부된 `이행관리_화면_와이어프레임_1 (1).html`을 기반으로 실제 프로토타입을 수정·구현할 때 필요한 기획 의도와 구현 기준을 전달한다.  
> 이 문서는 화면을 그대로 복제하기 위한 명세가 아니라, 회의에서 확정된 구조를 기준으로 기존 프로토타입에 적용하기 위한 참고 문서다.

---

# 1. 구현 목적

이번 개편의 핵심은 기존의 **문서 목록 중심 관리**에서 벗어나 아래 구조로 시스템을 재편하는 것이다.

```text
법령
  ↓
이행항목
  ↓
업무단계
  ↓
업무 수행
  ↓
증빙문서 / 시스템 결과
  ↓
이행상태 판단
```

즉 사용자가 단순히 문서를 등록하는 시스템이 아니라,

- 어떤 법적 의무가 있는지
- 그 의무를 이행하기 위해 어떤 업무를 해야 하는지
- 해당 업무를 어디에서 수행하는지
- 어떤 문서 또는 결과물이 증빙으로 남는지
- 현재 이행 / 미이행 상태가 무엇인지

를 한 흐름으로 확인할 수 있어야 한다.

---

# 2. 이번 회의에서 확정된 기본 방향

## 2.1 법령 중심 이행구조 적용

시스템 기본 구조는 아래 관계를 따른다.

```text
법령 1
 └ 이행항목 N
     └ 업무단계 N
         └ 증빙문서 N
```

주의할 점:

- 하나의 업무단계가 하나의 법령만 의미하지 않을 수 있다.
- 하나의 문서가 여러 업무단계의 증빙이 될 수 있다.
- 따라서 `업무단계 ↔ 문서`는 1:1이 아니라 **다중 매핑 가능 구조**로 설계한다.
- 문서 수와 업무단계 연결 수는 동일하지 않다.

---

## 2.2 이행 여부는 증빙과 연결

기본적으로 업무단계별 현재 연도 이행상태를 보여준다.

예:

```text
위험성평가 실시
법정주기: 연 1회
2026년 결과: 완료
증빙: 위험성평가 결과 1건
```

또는

```text
산업안전보건위원회 개최
법정주기: 분기/반기 등 해당 기준
현재 결과: 미이행
증빙문서: 0건
```

단, 단순히 문서 `0건 = 무조건 미이행`으로 하드코딩해서는 안 된다.

업무 종류에 따라 결과가:

- 시스템 내부 데이터
- 결재 문서
- 첨부파일
- 외부 수행 결과

형태일 수 있으므로 업무단계별 **완료 판단 기준**을 둘 수 있는 구조가 필요하다.

# 3. HTML 와이어프레임을 보는 기준

첨부 HTML은 아래 6개 화면으로 구성되어 있다.

1. 단계별 이행현황
2. 이행 상세·문서등록
3. 작년 문서 불러오기
4. 업무문서
5. 지난연도 문서 상세
6. 누락 점검

이 중 **전체 화면을 그대로 최종 기능으로 확정한 것은 아니다.**

HTML에서 가장 중요하게 참고해야 하는 것은:

- 이행업무 중심의 정보구조
- 군 / 부서 / 관리대상 단위 구분
- 업무단계별 이행상태
- 법령 및 주기 정보
- 업무단계와 문서의 다중 연결
- 이전연도 업무 참고 구조
- 미이행 항목 확인 구조

이다.

반면 아래는 추가 검토가 필요한 부분이다.

- 작년 문서를 올해 문서로 그대로 불러오는 UX
- 모든 업무에서 공통적으로 `새 문서 등록` 버튼을 사용하는 구조
- 별도 `기존 문서` 메뉴 유지 여부
- 프로그램형 업무와 일반 문서형 업무의 처리 방식

---

# 4. 메뉴 구조 적용 방향

회의 기준 우선순위는 다음과 같다.

```text
이행관리
 └ 이행 목록
     └ 이행 상세

업무관리
 └ 업무 목록

시스템관리
 └ 법령 관리
```

## 제거 또는 통합 검토

기존 프로토타입에 별도 `기존 문서` 성격의 메뉴가 있다면 제거하거나 업무목록에 통합한다.

핵심 메뉴 우선순위:

1. 이행 목록
2. 업무 목록
3. 각 프로그램형 업무 메뉴
4. 시스템관리 > 법령 관리

# 5. 이행 목록 화면

HTML의 `① 단계별 이행현황` 화면을 기본 참고한다.

## 5.1 역할

사용자가 자신에게 적용되는 법적 업무와 현재 이행상태를 한 번에 확인하는 메인 화면.

## 5.2 기본 분류

와이어프레임과 같이 다음 수준으로 구분 가능하다.

### L1. 군 단위
담양군 전체에서 한 번 수행하는 업무.

예:
- 안전보건 경영방침
- 전담조직 운영
- 군 전체 계획
- 경영책임자 보고

### L2. 부서 단위
각 실과·사업소가 개별 수행해야 하는 업무.

예:
- 부서별 의무이행 점검
- 종사자 교육
- 도급·용역 관련 관리

### L3. 관리대상 단위
시설·공사·사업장 단위로 수행하는 업무.

예:
- 소방시설 점검
- 특정 시설 안전점검
- 개별 관리대상 점검

---

## 5.3 표시 필드

최소 다음 정보가 있어야 한다.

| 필드 | 설명 |
|---|---|
| 업무단계명 | 실제 수행해야 하는 업무 |
| 이행주기 | 연/반기/분기/월/수시 등 |
| 회차 | 필요 시 현재 회차 |
| 이행상태 | 충족/진행/지연/미이행/비해당 |
| 수행주체 | 담당 부서 또는 역할 |
| 증빙 | 연결된 문서/결과 수 |
| 법령 | 해당 업무 법적 근거 |

필터:

- 연도
- 법령
- 부서
- 주기
- 상태
- 업무단계명

# 6. 이행 상세 화면

이 화면은 이번 프로토타입에서 가장 중요하게 수정해야 한다.

HTML에서는 기본적으로:

```text
이행 상세
 ├ 법령정보
 ├ 주기
 ├ 적용대상
 ├ 수행주체
 ├ 현재 이행상태
 └ 등록문서
```

구조인데, 최종 구현에서는 여기에 **업무 수행 방식**이 포함되어야 한다.

---

## 6.1 업무 유형 분기

모든 업무를 단순히 `새 문서 등록`으로 처리하지 않는다.

최소 아래 3가지 유형으로 분류한다.

### A. PROGRAM

시스템 내부 기능에서 직접 수행하는 업무.

예:
- 위험성평가
- 개선조치
- 안전보건교육
- 시스템 내 별도 프로그램으로 구현된 점검 업무

CTA 예:

```text
[위험성평가 실시]
[교육 등록]
[개선조치 관리]
```

버튼 클릭 시 일반 문서등록 팝업이 아니라 **해당 업무 메뉴로 이동**한다.

---

### B. ELECTRONIC_DOC

공문·결재문서를 작성하거나 등록하여 수행하는 업무.

예:
- 계획 수립
- 결과 보고
- 위원회 결과 보고
- 부서별 이행점검 결과 제출

CTA:

```text
[업무문서 작성]
```

업무문서 등록 시 해당 업무단계가 기본 매핑되어 있어야 한다.

---

### C. ATTACHMENT / RESULT

외부에서 업무를 수행한 뒤 결과물만 등록하는 형태.

예:
- 외부기관 점검결과
- 용역 결과보고서
- 외부 시스템에서 수행한 점검결과

CTA:

```text
[결과 등록]
[증빙 첨부]
```

---

# 7. 가장 중요한 처리 흐름

## 7.1 PROGRAM형 업무

예: 위험성평가

```text
이행 목록
 ↓
위험성평가 실시
 ↓
[위험성평가 실시] CTA
 ↓
위험성평가 메뉴
 ↓
평가 수행
 ↓
개선조치
 ↓
결과 또는 결재문서 생성
 ↓
원래 이행 업무와 자동 연결
 ↓
이행상태 갱신
```

핵심:

**프로그램 메뉴에서 수행한 결과가 다시 이행관리로 돌아와야 한다.**

단순 화면 링크만 연결하면 안 된다.

---

## 7.2 ELECTRONIC_DOC형 업무

```text
이행 목록
 ↓
업무 상세
 ↓
[업무문서 작성]
 ↓
업무문서 작성
 ↓
결재
 ↓
완료 문서 생성
 ↓
해당 업무단계 증빙으로 연결
 ↓
이행상태 갱신
```

---

## 7.3 한 문서가 여러 업무단계에 해당하는 경우

예:

```text
2026년 중대재해 예방 종합계획
```

한 문서 안에 다음이 모두 포함될 수 있다.

- 경영방침
- 조직
- 위험성평가
- 교육
- 점검

따라서 업무문서 등록 화면에서:

```text
연결 업무단계
☑ 경영방침 수립
☑ 안전보건관리체계 구축
☑ 위험성평가 계획
☑ 안전보건교육 계획
```

형태로 여러 업무단계를 매핑할 수 있어야 한다.

# 9. 프로그램형 업무 매핑 작업

프로토타입 수정 전 반드시 현재 CSV 데이터를 기준으로 아래 매핑을 확인한다.

| 업무단계 | 유형 | 연결 메뉴 | 결과 | 완료조건 |
|---|---|---|---|---|
| 위험성평가 실시 | PROGRAM | 위험성평가 | 평가결과 | 평가 완료 |
| 개선조치 | PROGRAM | 개선조치 | 조치결과 | 조치 완료 |
| 안전보건교육 실시 | PROGRAM | 안전보건교육 | 교육결과 | 교육 완료 |
| 작업환경측정 | 검토 | 기존 기능 또는 문서 | 결과보고 | 결과 등록 |
| 산업안전보건위원회 | ELECTRONIC_DOC | 업무문서 | 결과보고 | 결재 완료 |

Claude는 임의로 유형을 확정하지 말고 CSV의 업무단계와 현재 프로토타입 메뉴를 비교하여:

```text
1. 이미 프로그램 메뉴가 존재
2. 문서로 처리 가능
3. 결과 첨부만 필요
4. 현재 어떤 메뉴와 연결해야 할지 불명확
```

중 하나로 표시한다.

`4. 불명확` 항목은 임의 구현하지 않고 별도 목록으로 남긴다.

# 10. 기존 프로그램 메뉴 점검

회의에서 명확하다고 판단된 대표 항목:

- 위험성평가
- 안전보건교육

추가로 현재 프로토타입에 별도 기능화되어 있는 업무가 있다면 모두 CSV와 비교한다.

확인할 내용:

```text
업무단계
→ 현재 메뉴 존재 여부
→ 생성되는 결과 데이터
→ 전자결재 발생 여부
→ 결과 문서 존재 여부
→ 이행관리와 연결 가능 여부
```

특히 **작업환경측정 등 CSV에 존재하지만 현재 연결 관계가 명확하지 않은 항목**을 찾아야 한다.

# 11. 작년 문서 기능

HTML에는 다음 기능이 구현되어 있다.

```text
작년 문서 검색
 ↓
문서 선택
 ↓
업무단계 매핑 상속
 ↓
올해 문서 생성
```

하지만 이 방식은 최종 확정 기능이 아니다.

따라서 프로토타입에서는 우선 아래 수준으로 처리하는 것을 권장한다.

```text
2025년 동일 업무 실적

- 문서 A
- 문서 B
- 문서 C

[지난해 문서 보기]
```

이후 `올해 문서로 복사`를 지원하더라도 다음 항목은 별도 검토가 필요하다.

- 제목 복사 여부
- 수발신자 복사 여부
- 업무단계 매핑 상속 여부
- 첨부파일 복사 여부
- 결재문서 복제 가능 여부

따라서 현재 HTML의 `올해 문서로 등록` 기능을 최종 스펙으로 간주하지 않는다.

# 12. 누락 점검

HTML의 `⑥ 누락 점검`은 유지 가능한 개념이다.

목적:

```text
법적으로 필요한 업무
-
현재 등록된 결과
=
미이행/확인필요 업무
```

표시 대상:

- 정기 업무인데 현재 연도 결과가 없는 항목
- 이전연도에도 결과가 없었던 항목
- 현재 부서가 해당/비해당인지 확인이 필요한 항목

사용자는 항목별로:

```text
[업무 수행]
[결과 등록]
[비해당 처리]
```

할 수 있다.

비해당 처리는 사유를 필수 입력하는 구조가 적합하다.

# 13. 법령 관리 화면

기존 프로토타입의 `법령 관리` 화면을 그대로 사용하지 않는다.

이번 구조에서 법령관리는 단순 법령 목록 관리가 아니라 **법적 의무와 시스템 업무를 연결하는 마스터 관리**에 가깝다.

권장 테이블:

| 구분 | 필드 |
|---|---|
| 법령 | 법령명 / 조문 |
| 이행항목 | 법에서 요구하는 의무 |
| 업무단계 | 실제 수행 업무 |
| 이행주기 | 연/반기/월/수시 |
| 수행조건 | 발생조건 |
| 적용수준 | 군/L1, 부서/L2, 관리대상/L3 |
| 적용대상 | 대상 부서/시설 |
| 수행주체 | 담당 역할 |
| 업무유형 | PROGRAM / ELECTRONIC_DOC / ATTACHMENT |
| 연결메뉴 | 시스템 내 수행 위치 |

# 14. 화면 디자인 적용 원칙

## 유지

기존 프로젝트의:

- 디자인 시스템
- 컬러
- 컴포넌트 스타일
- 테이블 디자인
- 버튼 스타일
- 레이아웃 규칙

은 최대한 재사용한다.

## 변경

HTML의 정보구조를 현재 프로토타입 디자인에 맞춰 재구성한다.

즉:

```text
HTML 디자인을 그대로 복제 X
HTML의 구조와 UX 개념을 기존 디자인에 이식 O
```

회의 기준으로 **화면의 판/구조는 HTML 방향으로 변경하되 기존 디자인 언어는 유지**한다.

---

# 15. 역할별 화면 범위

## 전담조직 / 관리자

- 전 부서 이행현황 조회
- 군 단위 업무 관리
- 부서별 이행률 확인
- 미이행 현황 확인
- 법령/업무단계 기준 관리

## 부서 담당자

- 자기 부서 이행업무 조회
- 해당 업무 수행
- 업무문서/결과 등록
- 미이행·누락 확인
- 자신의 관리대상 조회

권한에 따라 동일 화면에서 조회범위만 달라지는 방식을 우선 검토한다.

# 16. 데이터 구조 참고

Claude가 프로토타입 상태관리 또는 mock data를 작성한다면 아래 정도의 구조를 기준으로 한다.

```ts
interface ComplianceTask {
  id: string

  // 법적 구조
  lawId: string
  lawName: string
  lawArticle: string

  complianceItemId: string
  complianceItemName: string

  taskName: string

  // 이행 조건
  cycleType: 'YEAR' | 'HALF' | 'QUARTER' | 'MONTH' | 'EVENT'
  cycleLabel: string
  condition?: string

  // 대상
  level: 'L1' | 'L2' | 'L3'
  applicableTarget: string
  owner: string

  // 업무 수행
  taskType: 'PROGRAM' | 'ELECTRONIC_DOC' | 'ATTACHMENT'
  targetMenu?: string

  // 현재 상태
  status: 'DONE' | 'IN_PROGRESS' | 'LATE' | 'NOT_DONE' | 'N_A'

  // 증빙
  evidenceCount: number
  evidenceIds: string[]
}
```

문서는 복수 업무에 연결 가능해야 한다.

```ts
interface WorkDocument {
  id: string
  title: string
  department: string
  date: string

  taskIds: string[]

  approvalStatus?: string
  attachmentIds?: string[]
}
```

# 17. 프로토타입에서 우선 구현할 화면

우선순위는 아래 순서로 본다.

## Priority 1

### 이행 목록
전체 구조를 이해할 수 있는 핵심 화면.

### 이행 상세
업무정보 + 수행 CTA + 증빙현황.

---

## Priority 2

### 업무 목록
문서/프로그램 결과 통합 관리.

### 프로그램형 업무 연결
위험성평가, 교육 등 기존 메뉴 이동.

---

## Priority 3

### 법령 관리
법령 ↔ 이행항목 ↔ 업무단계 연결 구조.

### 누락 점검
미이행 업무 관리.

---

## Priority 4

### 지난연도 문서
현재는 참고 기능 수준으로 구현.

# 18. Claude 작업 절차

프로토타입을 바로 수정하기 전에 다음 순서로 확인한다.

## STEP 1
현재 프로젝트의 전체 IA와 메뉴 파일 확인.

## STEP 2
첨부 HTML의 6개 화면 구조 확인.

## STEP 3
현재 프로토타입에서 다음 기능 위치 확인.

- 위험성평가
- 개선조치
- 안전보건교육
- 작업환경측정 관련 기능
- 업무문서
- 법령관리

## STEP 4
HTML의 업무단계를 현재 메뉴와 매핑.

## STEP 5
아래 항목을 별도 정리.

```text
[명확]
업무단계 → 기존 프로그램 메뉴 연결 가능

[문서]
업무단계 → 업무문서 작성으로 처리 가능

[첨부]
업무단계 → 외부 결과 업로드 방식

[확인 필요]
어디서 수행하는지 현재 프로토타입만으로 판단 불가
```

## STEP 6
이행 목록과 이행 상세부터 프로토타입 구현.

## STEP 7
프로그램 메뉴로 이동한 뒤 다시 이행상태가 갱신되는 흐름까지 연결.

## STEP 8
기존 `법령관리`와 `문서` 메뉴를 새 구조에 맞게 정리.

# 19. Claude가 임의로 확정하면 안 되는 항목

다음 내용은 현재 단계에서 임의로 정책을 만들어 구현하지 않는다.

- 법적 주기 자체의 변경

```text
TODO / 기획확인 필요
```

상태로 표시한다.

# 21. 최종 UX 목표

사용자 입장에서 최종적으로 아래 질문에 모두 답할 수 있어야 한다.

```text
1. 내가 해야 하는 업무가 무엇인가?
2. 왜 해야 하는가? → 법령
3. 언제 해야 하는가? → 주기/시점
4. 어디에서 해야 하는가? → 프로그램/문서/결과등록
5. 지금 했는가?
6. 무엇이 증빙인가?
7. 빠진 업무가 무엇인가?
```

이 흐름이 명확하면 이번 프로토타입의 핵심 목적은 달성된 것으로 본다.
