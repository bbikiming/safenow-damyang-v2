# 위험성평가 — 조치 완료 확인 → 공문 기안 → 온나라 이관 (v1)

> 근거: 2026-07-30 회의 녹취 · `docs/planning/기획-2026-07-30-회의반영-v1.md` · 코드 전수 조사(2026-07-31)
> 요구: *"위험성평가든 재난안전과 담당자는 완료된 걸 확인하고 문서 처리 해서 온나라 넘기는 단계가 필요해"*

---

## 0. 지금 무엇이 비어 있나

부서 담당자가 개선조치를 완료하면 **아무도 확인하지 않고 평가까지 끝난다.**

`completeImprovement()`가 사진·조치내용·서명 3요건만 보고 `status='DONE'`을 확정하고([js/rsk-data.js:648](../../js/rsk-data.js)), 그 자리에서 `refreshAssessmentStatus()`가 마지막 1건이면 평가를 `by:'시스템'` 이력과 함께 `COMPLETED`로 바꾼다(:392-397). 주관부서(재난안전과)에 남은 수단은 **재촉뿐이고, 재촉 버튼은 DONE이 되는 순간 사라진다.**

즉 현재 구조에서 부서의 **자기 선언이 곧 평가 완료**다. 그 뒤에 무엇을 대외로 내보내는 절차도 없다.

빠진 것은 두 단계다.

| 단계 | 주체 | 현재 |
|---|---|---|
| ① 조치 완료 **확인** | 재난안전과 | **없음** — 부서 선언이 곧 확정 |
| ② 확인 결과의 **공문 기안 → 온나라 이관** | 재난안전과 | **없음** — 대외 문서 자체가 없음 |

## 1. 설계를 구속하는 사실 (지어내면 안 되는 것)

조사에서 확인된, 이 설계가 반드시 따라야 할 제약이다.

### 1-1. 발주처가 이미 부정한 것

| 부정된 안 | 근거 |
|---|---|
| **`공문 및 결재` 대메뉴 신설** | 참석자1 *"공문만 이렇게 분류만 해놔… 도움도 하나도 안 되는데"*(714~720). 요약 문서의 구조안은 회의 산출물이 아니라 창작이다 |
| **공문 본문 자동 입력**(업무명·기간·부서) | 참석자4 *"이게 다 직접 타이핑 하셔야 돼. 이거는 자동으로 못 만들어드리고"*(822). **자동 연결 합의는 붙임파일뿐** |
| 공문 작성 화면 **선착수** | 양식 실물 3~4건 미수령(8월 둘째 주) · 온나라 문서대장 화면 미확인 |

→ 그래서 이번 구현은 **새 대메뉴가 아니라 위험성평가 화면 안**이고, **본문은 사람이 친다**. 시스템이 자동으로 하는 건 붙임 연결과 수치 계산뿐이다.

### 1-2. 순서가 틀렸다는 지적을 반복하지 않는다

교육의 `[결재 상신]`은 발주처가 두 번 지워 달라고 해서 `EDUAPV.SUBMIT_ENABLED = false`로 꺼져 있다. 기능이 틀린 게 아니라 **공문 작성 단계 없이 결재만 올라가는 순서**가 틀렸기 때문이다 — *"왜 갑자기 뜬금없이 결재 상신이 있지"*.

발주처가 그린 순서: *"결재 상신을 눌러요. 그럼 공문 내용이 있을 거 아니에요? **작성을 하고** … 붙임 파일에 넣어놨었잖아요. 그러면은 끝나는 거죠"*

→ **1차 진입점은 `[공문 기안]`이고 `[상신]`은 미리보기 화면에만 있다.** 기안 폼에서 바로 상신할 수 없다.

### 1-3. 법령 근거는 **뒷단에 붙일 수 없다**

- `osh-36⑤`는 *"고용노동부령으로 정하는 바에 따라 기록하여 보존"*으로 **위임만** 한다([js/law-map.js:378](../../js/law-map.js)).
- 위임받은 **산안법 시행규칙 §37(위험성평가 실시내용 및 결과의 기록·보존)은 DYLAW 스냅샷에 미수록**이다. `oshr` 수록분은 §190·§197·별표4 3건뿐. *(주의 — 스냅샷의 '제37조'는 `oshe-37` 산안법 **시행령** §37 산업안전보건위원회 회의로 완전히 다른 조문이다.)*
- 공문 시행·문서관리 근거(행정업무의 운영 및 혁신에 관한 규정 · 공공기록물법 · 위임전결규칙)는 **스냅샷에 한 건도 없다**(전 파일 grep 0건).
- 선례가 있다 — `'edu-approval': []`(js/law-map.js:848), 사유 *"결재 이력은 조회 전용 시스템 기능"*.

→ **검증 6문 #2**(그 의무의 직접 이행 수단인가) 기준으로 공문 기안·온나라 이관은 **근거 없음**이다. 결재는 의무 이행의 *형식*이지 이행 수단이 아니다.
→ 그래서 **새 page id를 만들지 않는다.** rsk-list 안의 모달로 두면 `DYLAW.MAP` 추가가 불필요하고 LAWADM '미판단' 집계도 발생하지 않는다.
→ 지면의 `관련 근거` 절은 담당자가 rsk-list 근거 3건(`cse-4-3`·`osh-36`·`rae-15`) 중 **고른 것만** 찍고, 아무것도 안 고르면 절 자체가 사라진다. 문자열 하드코딩 금지(§10 — [js/edu-approval.js:300](../../js/edu-approval.js)이 교육 조문을 평문으로 박은 것이 위반 선례).

### 1-4. `improvement.status`는 건드릴 수 없다

`status === 'DONE'` 이분법으로 세는 곳이 **8군데**다 — `deptImpCount` · `assessmentProgress` · `IMPCARD` 완료율 · `rsk-imp` 필터 · `dashboard staffCounts` · `my-work` 마감/완료 탭 · `rsk-my` · `refreshAssessmentStatus`.

여기에 4번째 값(`CONFIRMED` 등)을 넣거나 완료를 확인 이후로 미루면 **8곳이 동시에 어긋난다.**

## 2. 채택 설계

### 2-1. 확인은 `status`가 아니라 **별도 축**이다

```js
improvement.confirm = {
  state : 'WAIT' | 'OK' | 'RETURNED',   // 없으면(undefined) WAIT 로 파생
  by, at,                                // 확인/반려한 사람·일자
  reason,                                // RETURNED 일 때 필수
  round                                  // 제출 회차 (재제출마다 +1)
}
```

**핵심 판단 — 반려해도 `status`를 `IN_PROGRESS`로 되돌리지 않는다.**

되돌리면 (a) `refreshAssessmentStatus`가 `COMPLETED`를 되돌리지 못해([js/rsk-data.js:381](../../js/rsk-data.js) early return) 평가가 잠긴 채 개선조치만 미완료인 모순이 생기고, (b) 옛 세션 데이터에 `confirm`이 `undefined`라 완료율이 조용히 떨어지므로 SKEY를 범프해야 하며, (c) 범프하면 시연 데이터가 날아간다.

대신 **반려 건은 `confirm.state='RETURNED'`로 두고 화면이 이 축을 읽어 드러낸다.** 실질 제재는 두 가지다.

1. **공문 기안이 막힌다** — 전 건 `confirm.state==='OK'` 여야 기안 진입점이 열린다.
2. **담당자 화면에 반려 배너가 뜨고 재제출 버튼이 살아난다** — 내 할일·rsk-my·개선조치 상세 3곳이 `DYRSK.needsAction(m)`(= `status !== 'DONE' || confirm.state === 'RETURNED'`)으로 '할 일' 여부를 판정한다. 반려 건은 완료 탭이 아니라 **마감 할일로 되돌아오고** 버튼 라벨이 `재제출`로 바뀐다.

> ⚠️ **집계는 이 함수를 쓰지 않는다** — `deptImpCount`·`assessmentProgress`·`refreshAssessmentStatus` 는 `status` 기준 그대로다. 완료율은 유지하고 **할 일 노출만** 확인 축을 본다.

이렇게 하면 **기존 집계 8곳 전부 무변화 · SKEY 범프 불필요 · `COMPLETED` 불변식 유지**다.

> **감수한 대가** — 반려 건도 완료로 집계된다(완료율 100%인데 확인 반려 2건). 감추지 않고 `확인 반려` 배지와 요약 배너로 드러내는 것으로 갚는다. 완료율 게이지를 확인 기준으로 바꾸면 담당자 화면에서 *"내가 다 했는데 100%가 아닌"* 문제가 생겨 일부러 바꾸지 않았다.

### 2-2. 공문은 도메인 밖 **키드 스토어**

결재 축은 평가와 1:1이 아니다(재상신 누적 · 대상이 평가 1건일 수도 부서 1건일 수도). `assessment` 안의 필드로 넣으면 스키마가 곧 어긋난다.

```js
// DYRSK 스토어 안 최상위 배열 — 새 스토리지 키를 늘리지 않는다(reset 도 함께 처리됨)
db.docs = [{
  sid, kind:'assessment', target:'A|RA-2026-16', aid, deptId:'',
  no,                       // 임시 채번 — '실제 번호는 온나라가 부여' 라벨을 떼지 않는다
  title, to, body,          // ★ 전부 사람이 직접 타이핑
  basis: ['osh-36'],        // DYLAW 조문 **키**만 (문자열 금지 §10)
  attach: [{label, auto}],  // 자동 2건 + 수동 추가
  line:   [{dept, role, name}],
  status: '미상신'|'결재중'|'결재완료'|'반려',   // STATUS_TONE 기존 어휘만
  at, log: [{at, st, by, memo}]
}]
```

- **재상신은 덮어쓰지 않는다** — 새 `sid`를 쌓고 같은 `target`의 마지막이 현재 상태다. 최신이 아닌 건은 상태 변경이 막힌다(이력 변조 방지, CLAUDE.md §4와 같은 규칙).
- 상태 전이는 시스템이 스스로 하지 않고 **수신**한다 — `receive(sid, 'approve'|'reject', reason)`. 화면에 "온나라 연동 미구현 — 결과 수신 시연"을 명시한다.
- `lockOf(kind, id)` — **모듈 전역 state를 읽지 않는다.** EDUAPV는 `state.year`가 `lockOf`의 target 키까지 좌우해 이력 화면에서 과거 연도 문서를 한 번 열면 잠금이 조용히 풀리는 결함이 있다([js/edu-approval.js:111·190](../../js/edu-approval.js)). 인자만으로 target을 만든다.

### 2-3. 화면 흐름

```
[부서] 개선조치 완료(사진+서명)
   ↓
[재난안전과] ① 완료 확인          ← IMPCARD 카드 안 인라인 패널 (§1 적층 금지)
   ├─ 확인 → confirm.state=OK
   └─ 반려 → RETURNED + 사유 → 담당자 화면에 배너 → 재제출(기존 경로)
   ↓ (전 건 OK)
[재난안전과] ② 공문 기안          ← 제목·수신·본문 타이핑 / 붙임 자동 / 결재선 ORGPICK
   ↓
[재난안전과] ③ 문서 미리보기      ← .pdf-paper.pdf-doc 기안문 지면 · PDF 저장/인쇄
   ↓
[재난안전과] ④ 온나라 상신        ← 확인 모달 → 잠금 → 상태 카드 · 시연 회신
```

**진입점은 전부 rsk-list 안**이다. 새 화면·새 메뉴 없음.

| 단계 | 진입점 | 조건 |
|---|---|---|
| ① 확인 | 개선조치 상세(IMPCARD) 카드 footer `[완료 확인]` | `canManage()` · `status==='DONE'` |
| ①-요약 | 부서별 조치 탭 최상단 배너 `[확인 대기 N건만 보기]` | 확인 대기 ≥ 1 |
| ② 기안 | 요약 카드 우측 `[공문 기안]` | 전 건 확인 완료 |
| ③ 미리보기 | 기안 모달 `[문서 미리보기]` | — |
| ④ 상신 | 미리보기 하단 `[온나라로 결재 상신]` | 결재선 전 단계 지정 |

### 2-4. 지면은 **표준 공문 서식**이다 (v1.1 정정)

> **v1 의 오류** — 초판은 지면을 `Ⅰ. 관련 근거 / Ⅱ. 본문 / Ⅲ. 부서별 조치 확인 결과` 절 구분 + KPI 카드 4개로 그렸다. **그건 공문이 아니라 보고서다.** 또 "공문 양식 실물 미수령이라 임시 레이아웃"이라고 배너를 달았는데, 이것도 과도하게 보수적이었다.

대한민국 행정기관 공문서 서식은 **「행정업무의 운영 및 혁신에 관한 규정 시행규칙」 별지 제1호서식**(기안문·시행문)으로 정해져 있고 **전 행정기관 공통**이다. 담양군 고유 양식이 따로 있지 않다. 발주처도 *"기본적인 담양군청 공문 양식대로 간다"* 고 했다.
→ **서식 구조는 지어내는 게 아니라 이미 정해져 있으므로 그대로 따른다.** 실물이 필요한 것은 서식이 아니라 **담양군 고유값**(처리과 기호·주소·전화·팩스·전자우편·공개구분·관인 이미지)뿐이고, 이건 지면에 `미등록`으로 표시한다.

> **다만 이 규정을 근거 칩으로 인용하지는 않는다** — DYLAW 스냅샷에 없다(§1-3). **서식을 따르는 것과 조문을 인용하는 것은 다른 문제다.**

**표준 구성 요소와 구현 매핑**

| # | 표준 요소 | 구현 |
|---|---|---|
| ① | 행정기관명 (중앙) | `.pdf-gm-org` — `담 양 군` |
| ② | 수신 (경유) / 제목 | `.pdf-gm-head` — 상하 괘선, 라벨 고정폭 |
| ③ | 본문 (항목 `1. → 가. → 1) → 가)`) | `.pdf-gm-body` `white-space: pre-wrap` 로 **사람이 친 들여쓰기를 그대로 보존**. 기안 폼에 항목 삽입 버튼 제공 |
| ④ | 붙임 + `끝.` | `.pdf-gm-attach` — `붙임  1. ○○ 1부.` + 마지막에 `끝.`. **붙임이 없으면 본문 끝에 `끝.`** |
| ⑤ | 발신명의 + 관인 | `.pdf-gm-issuer` — **외부발송만** |
| ⑥ | 기안자/검토자/결재권자 서명 | `.pdf-gm-sign` — **하단**(표준은 상단 결재란이 아니다). 칸 수는 결재선에서 파생 |
| ⑦ | 협조자 · 시행/접수 | `.pdf-gm-frow` — 접수는 외부발송만 |
| ⑧ | 우편번호·주소·홈페이지 / 전화·팩스·전자우편·공개구분 | `.pdf-gm-frow2` — 외부발송만, 미확정값은 `미등록` |

**내부결재 / 외부발송은 지면이 실제로 다르다** (회의 미결이었으나 표준상 구조가 다르므로 분기가 맞다)

| | 내부결재 | 외부발송(시행문) |
|---|---|---|
| 수신 | `내부결재` | 수신자 지정 + `(경유)` |
| 발신명의·관인 | **없음** | `담 양 군 수` + 관인 |
| 접수란 | **없음** | 있음 |
| 기관정보(주소·전화) | **없음** | 있음 |

**부서별 결과표는 붙임 별지로 뺀다** — 표준 공문 본문에 큰 표를 넣지 않는다. `.pdf-gm-annex` 두 번째 지면(`[붙임 1] 부서별 개선조치 확인 결과표`)이고 인쇄 시 `break-before: page` 로 새 장이 된다. 담당자가 고른 근거 조문도 이 별지에 온다.

### 2-5. 문서 미리보기 — 표준 지면 위에 공문 modifier

> **v1 의 서술은 폐기했다.** 초판은 "새 CSS 계열 0개"라고 적었지만, v1.1 에서 지면을 표준 공문 서식으로 전면 교체하면서 `.pdf-gm-*` 계열을 **실제로 신설했다**. 문서가 코드와 반대를 말하고 있었다.

**지금의 구조**
- 모달·인쇄·표 파이프라인은 **기존 표준 그대로** — `DYV2.openModal(..., {variant:'wide', headHtml})` · `@media print` 의 `body:has(#v2-modal.modal-wide)` · `.table-figma.table-doc` · `.pdf-tablewrap`.
- 지면만 `.pdf-paper.pdf-doc` 에 **`.pdf-gm` modifier** 를 얹는다. 하위 조각(`.pdf-gm-org` · `-head` · `-row` · `-body` · `-attach` · `-issuer` · `-sign` · `-frow` · `-annex` 등)은 **공문 서식 전용 구조**라 기존 클래스로 대체할 수 없다(중앙 기관명·상하 괘선 수신란·하단 서명줄·시행/접수 칸).
- 새 계열을 만든 것은 §7 위반이 아니다 — §7 이 막는 것은 **같은 요소를 화면 접두어로 다시 만드는 것**이고, 공문 지면은 기존에 없던 요소다. 다만 **위험성평가 전용이 아니라 도메인 무관 이름(`pdf-gm`)** 으로 두어 교육 결재문서도 나중에 같은 지면을 쓸 수 있게 했다.

**인쇄 훅** — 편집 크롬은 `.pdf-noprint` 를 단다. 기존 `.eduapv-*` 하드코딩 4줄은 남아 있고(교육 모듈이 아직 쓴다), 신규 모듈은 훅만 쓴다.

## 5. 스스로 지적하는 약점

1. **온나라 결재 구현이 이 코드베이스에 이미 3벌**(`EDOC.onnaraPopup` · `EDUAPV` · `DYBGT`)인데 이걸로 4벌이 된다. 상태 어휘는 EDUAPV와 맞췄지만(미상신·결재중·결재완료·반려) 문서번호 체계는 여전히 갈려 있다.
   → **공용화를 지금 하지 않은 이유**: 교육 결재가 꺼져 있는 상태에서 EDUAPV를 수술하면 되살릴 때 리스크가 겹치고, 공문 양식이 8월에 오면 지면 상당 부분이 어차피 교체된다. **양식 수령 후 공용화가 맞다.** 첫 번째로 합칠 대상은 결재선이다.
2. **결재선이 두 벌**이 된다(교육 `dy-edu-apprline-v1` / 위험성평가). 위 1의 직접적 대가다. 키 이름을 도메인 중립(`dy-apprline-v1`)으로 두어 합칠 때 수렴점을 미리 잡았다.
3. **반려 건이 완료로 집계된다**(§2-1의 감수한 대가). 배지·배너로 드러내지만 숫자만 보면 안 보인다.
4. **재제출 시 같은 사진을 다시 올리는 것을 막지 않는다**(파일명이 같아도 재촬영일 수 있어서). 확인자에게 경고만 띄우므로, 확인자가 그냥 넘기면 반려가 형식적으로만 돈다. 시스템이 할 수 있는 것은 *'열람했다' 체크와 이력 기록*까지다.
5. `rsk-detail.js`가 **별도 전달 경로**(`deliverDept`)를 갖고 있어 확인 단계를 rsk-list에만 붙이면 두 경로가 갈린다. 이번 범위 밖 — 기존 결함으로 남긴다.
6. **공문 양식이 오면 지면 마크업 상당 부분이 버려진다.** 지금 만드는 것은 '서식'이 아니라 **'지면을 그리는 배관'**(모달·인쇄·표·결재란 파생)이라는 전제로 투자를 최소화했지만, 재작업은 확정적이다.
